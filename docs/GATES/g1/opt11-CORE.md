# OPT11, агент CORE: логика тика, звук, software, темп кадров (отчёт, реестр PS2-200..229)

Ветка `worktree-agent-a401b66ae9f5c91a7`. Единицы: такты COP0 EE (294.912 М/с), PCSX2 2.6.3 (32 МБ, программный GS, не железо), **релизная LTO-сборка `--prof`** полной конфигурации
(`SRB2_PS2_NO= SRB2_PS2_HW=1 python3 tools/ps2/build.py --jobs 2 --prof`, обе версии рендерера в одной ELF; рендерер по умолчанию — software), `-timedemo DEMO_00n.lmp -ps2prof`,
среднее окон 1..9 по 105 кадров (945 кадров). Все A/B — **одно дерево, две ELF**, отличающиеся только макросом `PS2_NOOPT_CORE` (`SRB2_PS2_NOOPT=core` собирает прежний код); числа — `tools/ps2/core_tick.py`.
Новые группы кода: `PS2_OPT_CORE` (`src/m_fixed.h`), отладочные ключи `-DPS2_POLYCHECK`, `-DPS2_NEGCTL=18`.

## 1. Сделано (этап 1)

1. **Измерение «логики тика» отдельно от кадра** (PS2-200, инструмент). В LTO-профиле `--prof` кадр делится прямыми чтениями COP0 в `D_RunFrame` (без линкерных обёрток и проб в движке): `TryRunTics` (тик), `D_Display`
   (рендер + HUD + `I_FinishUpdate`), `S_UpdateSounds`+`LUA_Step`, остаток; плюс счётчики «тиков запрошено часами / выполнено», самый длинный кадр, гистограмма интервалов кадров по периодам 1/60 с и их разброс.
   Строки `TICK win=...` в `boot.txt`, свод — `python3 tools/ps2/core_tick.py build/runs/<имя>/boot.txt`.
   **Главное, что это показало: настоящая стоимость тика сильно меньше, чем «не-рендер часть кадра» из брифа (она включала звук-декодер, HUD, `I_FinishUpdate`).**
2. **Software в двухрендерерной ELF был медленнее на 1.5–2.4 М/кадр из-за лишнего вытеснения кэша** (PS2-201). Каждый 3D-кадр начинается с `Z_PurgeLock` → `Z_EnsureFree(zheadroom)`: зона освобождает самый дешёвый непрерывный блок
   в 4 МиБ вытеснением кэша (текстуры, флэты). На арене 23.2 МиБ (HW-код съедает 1.3 МиБ статических данных: арена 24.5 → 23.2 МиБ) кэш DEMO_003/004 не помещается, и каждый кадр заново строятся текстуры
   (`LZ4_decompress_safe` 1.4 М + `Picture_TextureToFlat` 1.2 М + `Z_MakeRoomWalk` на кадр по сэмплеру). Заголовок по умолчанию 4 МиБ → **2 МиБ** (`Z_HEADROOM_DEFAULT`, только профиль 32 МБ; на 128 МБ — как было).
   `-zheadroom 512 / 1024 / 2048` дают **одинаковые** такты на DEMO_003 (11.86 М), 4096 — 14.19 М. Самый большой запрос одного кадра в прогонах — 512 КиБ (`PU_RENDERWORK`, конвертация флэта), 2 МиБ — запас 4×.
3. **Ящик ячеек полиобъектов** (PS2-200). `P_CheckPosition` обходил ячейки блокмапа полиобъектов для каждого вызова (≈1500 вызовов за тик на DEMO_003). `Polyobj_linkToBlockmap` теперь ведёт `ps2_polycells[4]`
   (объединение ячеек всех когда-либо привязанных полиобъектов уровня; растёт, сбрасывается со сменой уровня), `P_CheckPosition` обходит пересечение своего прямоугольника с ним. Ячейки вне ящика заведомо пусты → результат тот же
   (обработка полиобъектов от порядка не зависит: max/min с обнулением наклона). Теневая проверка `-DPS2_POLYCHECK` (хост и EE) проверяет инвариант «каждая привязанная ячейка внутри ящика» при каждой привязке и «каждая непустая ячейка
   запроса внутри ящика» при каждом запросе; негативный контроль `-DPS2_NEGCTL=18` (ящик короче на колонку) её срабатывание на DEMO_002/003 показывает (у DEMO_001/004 полиобъектов нет).
4. **PS2-177 (двухпроходный цикл стен, `tools/ps2/sw_segloop2.patch.py`) применён и проверен, но не оставлен**: побитно верен (хост A/B 4×1050 кадров идентичен, негативные контроли 16/17 краснеют, EE: golden `ps2-head` 0 differ на 4 демо,
   FNV всех 1050 кадров идентичны), но **выигрыша нет** (раздел 2.3). Код возвращён (`git checkout src/r_segs.c`), патч-скрипт оставлен с пометкой.

### 2.3 PS2-177 (двухпроходный цикл стен) — измерено
`python3 tools/ps2/sw_segloop2.patch.py` на HEAD, `--prof` LTO: DEMO_001 8.68 → 8.64, DEMO_002 8.90 → 8.88, DEMO_003 14.19 → 14.14, DEMO_004 13.76 → **13.94**. Сэмплер DEMO_001 (`build.py --sample`, `tools/ps2/sw_sample.sh`):
`R_RenderSegLoopX` 1545.7 → 1300.7 К тактов на кадр, но новые `R_SegMarkPass` 89.7 + `R_SegDraw` 64.5 + `R_SegTex1` 38.9 + ... возвращают почти всё: итог −0.05 М (0.5 %). Причина: «простые текстурированные» колонки — малая доля цикла
(основное время `R_RenderSegLoopX` — в ветках 3D-плит и световых списков, `!plain`, и в самом рисовании; оценка «344 такта на колонку вне рисования» взята из `--subprof`-замера, который сам искажает цикл), а там, где колонки рисуют (DEMO_004),
двухпроходная схема медленнее (+0.18 М). Не принято; патч-скрипт сохранён для истории.

## 3. Не проверено / упёрлось (на этом этапе)
* Настоящее железо не проверялось; PCSX2 не моделирует D-кэш: цена опроса каждого mobj на настоящей PS2 больше, чем здесь.
* Замеры в `-timedemo` не отражают игру: в демо `R_PrecacheLevel` не вызывается (`demoplayback`), текстуры строятся при первом показе (DEMO_003: один кадр 340 мс в окне 6); в игре кэш предзаполняется до половины свободной арены.
* HW-код оставляет в software-режиме **1316 КиБ арены** (918 КиБ статического BSS драйвера/движка HW + 420 КиБ кода): на DEMO_003 software-режим двухрендерерной ELF дороже software-only ELF на 2.3 М даже при 2 МиБ заголовка,
  если арена не вмещает кэш; при заголовке 2 МиБ DEMO_003 в двухрендерерной ELF 11.77 М (против 11.86 М у software-only ELF с 4 МиБ), то есть потеря снята, но запас арены остался меньше на 1.3 МиБ
  (чем больше карта, тем раньше это снова проявится). Решение «HW-буферы в зону при включении HW» — за STAB/VU (файлы `src/hardware`, `src/ps2/hw`).
* Тик D3 = 5.64 М: ровный профиль (1883 объекта, ≈ 960 тактов на вызов `P_MobjThinker`/`P_SceneryThinker`), точных ускорений на 30 % не найдено — раздел «следующие шаги».
