сбрасывает данные и пересобирает составную текстуру), `batch` 83 М, `clear` 51 М (предположительно регены внутри этих фаз — проверяется).

Разбор причин (код, `ps2_hw_tex.inc`/`hw_batching.c`):
* ключ сортировки батчей = FNV(указатель текстуры, polyflags, PolyColor): батчи одной текстуры (по уровням света/режимам смешивания) разбросаны по кадру, при пуле < рабочего набора текстура грузится заново для каждого батча;
* вариант с ключом (chroma key) и без — две отдельные записи и два набора блоков VRAM с одинаковыми текселями (`T:GFZWALL2 1024x512 clut 1` и `clut 2` — по 2048 блоков);
* копирование текселей в кольцо (`fill_*`, `tex` 10.8 М тактов/кадр при 2 МБ/кадр), `SyncDCache` кольца, 128-КБ буферы;
* вытеснение: «уже нарисованные в этом кадре» весят одинаково (40), без порядка → случайная жертва;
* `flipwait` (1–3 М/кадр) — не работа GS, а ожидание EE vblank-а: кадр N+1 не начинается, пока кадр N не показан (2 буфера кадра), в среднем полвертикальной развёртки ≈ 2.4 М тактов.



## 1. Измерение: что именно входит в рабочий набор (DEMO_001, GFZ1, окна 1–4, без ограничения текстур, сборка HT s1–s4)

Новые средства (HT): `-hwdbg 0x100000` — строки `HWTEX` (по окну 105 кадров: `need` — уникальные образы VRAM, нужные кадру, блоки/штук; `up_map/up_flat/up_t8o/up_ct32` — загрузки по видам (штук/блоков за кадр);
`reup` — повторные загрузки одной текстуры в одном кадре; `shared` — варианты с общим образом; `regen` — штук / тактов за кадр на повторную сборку данных движком; `lod=` — рабочий набор при хранении каждого образа на нужном уровне MIP, `lvl=` — по уровням);
`-hwdbg 0x400000` — `HWBO` (порядок текстур батчей одного кадра на окно: hit/UPLOAD); `-hwdbg 0x200000` — без zero-copy; `-hwdbg 0x800000` — старый старт кадра (ожидание flip); `-hwdbg 0x1000000` — сверка быстрой сборки текстур с исходной (hw_cache.c).

Пул GS = 12 032 блока: рабочий набор кадра в 2.0–2.2 раза больше пула, загружается почти всё (`reup`=0: внутри кадра повторов нет — порядок «по текстурам» работает).
* **Главный потребитель — три «облачных» плоскости горизонта `F:GFS_CLD1..3` (flat 1024×1024 PSMT8 = 4096 блоков каждая, итого 12 288 блоков = 3 МБ = больше всего пула GFZ1)**: это `horizonSpecial`-полигоны, движок
  рисует их ПЕРВЫМИ (ключ сортировки отрицательный, порядок подачи), в видимой части кадра они занимают небольшую область неба. Поэтому при LRU они — самые старые после отрисовки и вытесняются первыми, а в следующем кадре нужны первыми.
* Попытки сократить набор «без потерь» по текстуре в целом дали мало: ограничивающий прямоугольник реально используемых текселей = 22 927 из 26 099 блоков (повторы по ширине/высоте), «по уровням MIP» с грубой оценкой (лицом к камере) — 22 884. Т.е. не прямоугольник, а правильная
  экранная оценка плотности текселей (анализ Якобиана видимой части полигона) может дать выигрыш только для плоскостей, видимых далеко/скользяще (облака).
* Быстрая сборка составных текстур (PS2-HW-36): побайтово совпала с исходной на 1 200+ текстурах GFZ1 (`HWC composite check ... 0 differ`).
* Заметка для S: движок зовёт `Z_ChangeTag(data, PU_HWRCACHE_UNLOCKED)` на каждый GetTexture; блок, который драйвер держит под DMA, надо вырывать у движка (см. §2).
