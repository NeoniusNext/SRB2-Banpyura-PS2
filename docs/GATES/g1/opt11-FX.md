# OPT11, агент FX: GS Hardware Renderer — вода, полнота эффектов, артефакты картинки (отчёт, дописывается по этапам)

Ветка worktree: `worktree-agent-a01526fe0d8d89e7e`. Реестр отличий: `PS2-HW-120..139`. Окружение как в `docs/OPT11_BRIEF.md` (PCSX2 2.6.3, программный GS; ПК-эталон `build/pc-ref`, OpenGL под Xvfb/llvmpipe).

## 0. Инструменты этапа (новые, закоммичены)

* `tools/ps2/fx_pair.py` — одна сцена двумя рендерерами: ПК-OpenGL (эталон, кэш `build/ref/fx_<имя>`) и PS2-HW (PCSX2) в одном кадре; панель `ПК | HW | разность` и метрики в `build/fx/<имя>.png`.
  Камера: `--pre 'teleport~-nop~-ang~270~-aim~-40'` (консольная команда после первого снимка; `devmode` включается сам); `--addon X.wad` — один и тот же аддон на обеих сторонах; `--hwargs=-hwdbg N` — флаги драйвера.
  `fx_scenes.sh` — список сцен; `fx_crop.py` — увеличенные вырезки нескольких снимков рядом; `fx_edge.py` — сходство границ (корреляция градиентов) ПК/HW; `fx_region.py` — средний цвет области; `fx_ab.py` — A/B двух прогонов `-ps2prof` (среднее и максимум по окнам, цена воды).
  `make_fxflat.py` — PWAD, заменяющий плоские текстуры воды (`DSWATER1/2`) контрастной сеткой: рябь, швы и сдвиги текселей видны глазом и числом.
* `-hwlt N` (PS2-HW-121, диагностика, `ps2hwd_force_lt`): фаза ряби воды как на тике N, какой бы кадр ни рисовался. Кадр PS2 идёт не на тике ПК: в прогонах PCSX2 тик снимка на PS2 — 300–304 при заказе `k300`, а фаза ряби меняется на 2 рад за тик.
  **Снимок ПК-движка `k300` берётся на кадр позже** (хук `src/ps2ref.c` ставит `takescreenshot` в кадре с `leveltime=300`, GL читает кадр на следующем): совпадает фаза `-hwlt 301` (измерено перебором 297..303, корреляция границ максимальна на 301); `fx_pair.py` ставит `tick + 1` сам.
* Строка `VIDSHOT ... lt=N` печатает `leveltime` снимка (`src/ps2/i_video.c`).
* Хост-тест `tools/ps2/hg_hosttest.c` (`python3 tools/ps2/hg_hosttest.py [--negative-controls]`): починен под палитровый код OPT10 (он не собирался на HEAD: `ps2_hw_pal.inc` не подключался) и расширен группой `ripple` (раздел 1) с отрицательным контролем 7.

## 1. Вода (PF_Ripple), PS2-HW-120

### 1.1 Что было неверно (измерено)

* Рябь шейдера ПК: `tex(s - sin(a)*0.025, t - cos(a)*0.025)`, `a = -pi*(z/2*0.025) + leveltime*2`, z = глубина фрагмента (период по глубине 160 единиц, амплитуда 0.025 повтора текстуры = 0.025 x ширина плоской текстуры в единицах карты).
* OPT10 резал полигон на полосы по глубине, каждой полосе — **постоянный** сдвиг UV: на границе полос текстура скачет на разность сдвигов (до 0.6 тексела у плоских 64x64, **до 2.5 тексела у `DSWATER1/2` 256x256 в Deep Sea**) — это и есть швы; полосы кончались на z = 320, дальше ряби нет (у 256-й плоской текстуры там ещё 3 пикселя смещения); полигоны, у которых больше 4096 тексел по UV (`big`), шли вообще без ряби.
* Хост-тест `ripple` (ошибка в пикселях экрана: смещение тексела относительно шейдера, 3527 случайных точек 179 полигонов, три размера плоской текстуры): **OPT10: среднее 1.4–3.7 px, 77 % точек хуже 0.7 px, максимум 31 px**.

### 1.2 Решение

`src/ps2/hw/ps2_hw_water.inc` (раздел «PS2-HW-120»), правка `emit_piece` (`piece_t.ripple` = «вершины — полоса треугольников»):
* смещение считается **в вершинах** по глубине самой вершины и интерполируется GS (S/Q, T/Q линейны вдоль плоского полигона, глубина — аффинная функция положения): между плоскостями выборки сдвиг линеен по глубине (хорда синусоиды), на плоскости точен, **общая точка двух кусков и двух соседних полигонов имеет на обеих сторонах одно значение — C0, швов нет**;
* плоскости выборки — глобальная таблица на класс текстуры (ширина 32..512) и фокус вида; шаг по глубине из ошибки хорды `amp_px(z) * (K dz)^2 / 8 <= RP_EPS/2` пикселя (S = 256: 12 единиц при z = 100, 25 при z = 400); узлы рисуются с амплитудой `(1 + (K dz)^2/16)` (минимакс: хорда синусоиды лежит внутри него в `1 - (K dz)^2/8` раз; число проверено перебором: оптимальный коэффициент совпадает до h = 1.2 рад) — ошибка вдвое меньше;
* амплитуда плавно гаснет между глубинами, где она равна 1.5 и 0.8 пикселя (глубины `zfull` / `zend` у таблицы; дальше рябь не рисуется: **отличие PS2-HW-120a**, величина < 0.8 px) — вместо жёсткого z = 320 для всех текстур: теперь предел зависит от размера плоской текстуры (64: 320, 256: 1280, 512: 2560);
* планы ближе 3 px друг к другу на экране пропускаются (правило `RP_GAP`; -10 % плоскостей на GFZ1; `-hwdbg 131072` отключает);
* полигон — **одна полоса треугольников на серию интервалов одного класса темноты**: две цепочки (от ближней вершины к дальней) идут по плоскостям, каждая точка (вершина полигона или пересечение цепочки с плоскостью) сразу становится вершиной полосы, без копий; где одна цепочка идёт дважды подряд — повтор переднего ребра (два вырожденных треугольника, пикселей не покрывают); одна GIF-посылка;
* значение сдвига на плоскости таблицы считается один раз за уровневое время (кэш `ver`), поэтому обе точки плоскости и все полигоны кадра берут его готовым;
* полигоны за `zend` рисуются обычным путём света (`lit_fast_poly`: втрое дешевле `cut_and_emit`);
* общий путь `water_generic` (более 24 вершин, не монотонные цепочки, не степень двойки, > 4096 тексел, не светлая лестница): плоскости через `clip_attr`, кусок получает сдвиг своих вершин (тоже непрерывно, медленнее); `big`-полигоны теперь тоже с рябью (`emit_poly` не пропускает их мимо воды; запас на сдвиг 0.07 повтора в оценке `big`: валидатор GIF видел размах 4101 тексел, теперь 0 нарушений).
* A/B флаги `-hwdbg`: `65536` (0x10000) — прежний свип OPT10 (постоянный сдвиг на полосу), `1073741824` — ещё прежний полосный путь, `131072` — без правила экранного расстояния.

### 1.3 Числа

Хост-тест (`hg_hosttest.py`: 7 групп, 0 ошибок, отрицательный контроль 7 краснеет), ошибка в пикселях экрана против шейдера, зона полной амплитуды (z от 25 до `zfull`):

| плоская текстура | новая рябь: среднее / макс | OPT10: среднее / макс |
|---|---|---|
| 64 | 0.42 / 1.65 px | 1.42 / 12.6 px |
| 128 | 0.29 / 1.65 px | 2.24 / 20.9 px |
| 256 | 0.41 / 4.99 px | 3.66 / 31.5 px |

Распределение: новая — 68 % точек лучше 0.4 px, 0.85 % хуже 2 px; OPT10 — 77 % точек хуже 0.7 px.

PS2 (PCSX2), одна сцена, ПК-эталон и HW на одной фазе (`-hwlt 301`), сетка `FXFLAT.wad` на воде DSZ1: у прежнего свипа линии сетки сломаны на границах полос, у нового — гладкие кривые, как на ПК (`build/fx/crop*.png`). Валидатор GIF (`-hwdbg 536870912`) на сцене с полосами: 0 нарушений (524 974 вершины).

Цена (A/B на одной ELF, `-ps2prof`, `DEMO_001` (GFZ1, вода есть), окна 1..9, `tools/ps2/fx_ab.py`; новая против `-hwdbg 65536`, обе в `build/out-prof/SRB2.ELF` от одного коммита):

| поле | OPT10 (A: `-hwdbg 65536`) | новая (B) | B/A |
|---|---|---|---|
| ветка воды `emit_poly` (циклов EE на кадр) | 343 290 (макс 491 706) | 364 911 (макс 453 490) | **1.063** |
| `wall` (HWPROF) | 99 126 | 100 867 | 1.018 (шум: несвязанные поля `bsp` 1.055, `nodes` 0.890) |
| время демо (1051 тик) | 1263 реальных тика | 1286 | 1.018 |

Первая версия была 1.317 (448 156): ужаты упаковка вершин (`ws_pack`: константы плана в регистрах, пакеты бит-в-бит как у `put_vertex`, проверено хост-тестом), кэш начала ребра цепочки, дальние полигоны (z0 >= zend) идут `lit_fast_poly` без прохода по таблице, сдвиг плоскости из кэша `ver`. Было 448 156 -> 364 911 (-18.6 %).
**Цена воды осталась выше OPT10 на 6.3 % ветки воды = +21.6 тыс. циклов на кадр ≈ +0.27 % кадра (единица `wall` ≈ 82 цикла; разброс несвязанных полей в этих прогонах 5–13 %, `wall` лежит внутри него): требование «не расти» выполнено в пределах шума замера, но не нулевое.** Выпустить воду без приращения можно только понизив точность (см. ниже) — не сделано.
Разбивка тактов `water_sweep` на DEMO_001 (счётчики `HW_FXPROF` внутри `ps2_hw_water.inc`, выключены; окно 105 кадров, типичное: 1727 полигонов, 31 097 плоскостей, 87 503 вершины полос): подготовка плоскостей 3.8 М (2184 цикла на полигон), генерация вершин 10.6 М (121 на вершину), упаковка в GIF `emit_piece` 13.4 М (153 на вершину); всего 27.8 М / 105 = 265 тыс. на кадр с накладными замера.
Попытка снизить цену параметрами: `RP_EPS` 0.7 -> 0.9, `RP_GAP` 3 -> 3.5 даёт всего -6 % плоскостей на полигон (8.5 -> 8.0, их определяют вершины полигонов и классы темноты, не только таблица), а ошибка растёт (среднее 0.37 -> 0.47 px, > 2 px: 0.85 -> 1.16 % точек, критерий < 1 % не проходит): оставлено 0.7 / 3.0.

### 1.4 Не закрыто / риски воды

* Цена воды +6.3 % ветки (≈ +0.27 % кадра). Дальше только за счёт упаковки (путь у VU): полоса вершин одного цвета не нуждается в RGBAQ на каждую вершину (GIF-тег ST+XYZ2, цвет один раз A+D: Q приходит вместе с ST) — на треть меньше пакетов и записей на вершину, около 6 % воды; в `emit_piece` (файл VU), не сделано.
* Цвет воды против ПК: ПК после смеси прозрачности квантует кадр в палитру (3D-таблица 64³ в шейдере палитровой постобработки), GS так не умеет; средний цвет воды DSZ1 отличается на (-5, +7, +5) уровней, GFZ1 — на (0, -4, 0) (измерено `fx_region.py`; HF записал это как PS2-HW-78).
* Подводная камера (`PostImgRedraw` heat/water), наклонные плоскости, 3D-полы: этап 2 отчёта (ниже, по мере прогона).

## 2. Найденные и исправленные ошибки картинки (не вода)

* **PS2-HW-123: «серо-зелёный мир» после смерти / рестарта уровня / следующей карты** (DSZ1: `teleport` в бездну на кадре 20, респаун; `fx_pair.py`, `build/runs/fx_death/death.png`).
  Причина измерена: таблицы света (`CreateLightTable`) нумеруются в порядке первого использования (карта 1-я загрузка: id 1 = синий colormap, id 2 = обычная таблица, id 3 = подводный; после респауна id 1 = обычная таблица, id 2 = подводный), а ключ CLUT строки света
  `(id, поколение, строка)` после `ClearLightTables` совпадает с ключом прежнего уровня — CLUT, построенный из таблицы прежнего уровня, использовался заново, и мир рисовался colormap'ом другого уровня. Исправление: `lt_clear` увеличивает `H.pal_gen` (CLUT, зависящие от палитры, пересобираются при следующем использовании).
  Проверено: тот же сценарий до/после (`build/runs/fx_death2/d2.png`: цвета стен и воды как на ПК). Цена — одна пересборка CLUT на смену уровня.
