### 3.2 PS2-160: `R_IsPointInSector` без 64-битного деления (`ps2_rdraw.h:PS2_EdgeXLess`, `r_main.c`)
Условие `(fixed_t)(v1x + (INT64)a*b/d) < x` при `0 < b <= d` заменено точным сравнением 64-битных произведений (`a*b < t*d` при a >= 0, `a*b <= (t-1)*d` при a < 0; охранные условия на переполнение, иначе исходное выражение).
Хост-тест `tools/ps2/sw_hosttest.py`: 119 796 367 случайных/граничных проверок, 0 расхождений, негативный контроль краснеет. Замер DEMO_003: 16.02 → 15.63 М/кадр (−0.39).

### 3.3 PS2-161: `R_SortVisSprites` и узлы `R_CreateDrawNodes` (`ps2_nodescan.h`, `r_things.c`, `r_things.h:drawnode_t.order`)
* Сортировка спрайтов: выборка минимума за O(n²) заменена устойчивой сортировкой слиянием по (sortscale, dispoffset) — тот же порядок (первый минимум при равенстве); при sortscale == INT32_MAX (оригинал такой спрайт не выбирает) кадр идёт старым циклом.
* Узлы: для каждого спрайта оригинал обходит весь список узлов (≈223) и сначала выполняет проверку отсева. Теперь список узлов дублируется таблицей прямоугольников `INT16 x1,x2,y1,y2[]` (порядок создания), отсев — 8 узлов за шаг инструкциями MMI (`pcgth`),
  для прошедших отсев вызывается исходная проверка (тело цикла один-в-один, `R_DrawNodeClaims`); из претендентов берётся стоящий в списке раньше (метки порядка `drawnode_t.order`, середина между соседями, перенумерация при исчерпании промежутка).
  Спрайты-«splat», координаты вне ±30000, узлы без типа — через исходный обход/полный прямоугольник. Новая вставка — O(1) (первая версия сдвигала массивы `memmove` и стоила 3.3 М — см. 2.4).
* Тесты: `sw_hosttest.py` (60 000 сортировок против исходной выборки с большим числом равных ключей; 3.1 М запросов таблицы с ростом/повтором), хост A/B на 4 демо ×1049 кадров идентичен, негативные контроли NEGCTL=7 (сдвиг в x-тесте) и 8 (неустойчивая сортировка) обнаружены,
  стресс-вариант `-DPS2_NODE_ORDER_MAX=4096` (постоянная перенумерация) идентичен; на EE (MMI-путь): PS2REF golden 4 демо — `golden/ps2-head` 0 differ + все 1050 кадров FNV идентичны. Теневая проверка EE `-DPS2_NODECHECK` (сравнение векторного сканирования со скалярным) — в коде (`PS2NS_Next`).
* Замер (`--prof`, LTO): DEMO_004 14.89 → **13.75** М/кадр (−1.14, −7.7 %) на первой версии (остаток: сканирование MMI ≈0.4 М, построение таблицы, `R_DrawNodeClaims`).

### 3.4 PS2-162: `P_MobjFloorZ/CeilingZ` — плоский путь вставкой (`p_local.h`, `p_mobj.c`)
callgrind DEMO_003: 5.46 М вызовов за 1050 тиков (≈25 % `P_CheckPosition`). Для сектора без наклона (`f_slope == NULL`) результат — `sector->floorheight`; проверка и возврат теперь `static inline` в `p_local.h`,
функции с наклоном переименованы в `P_MobjFloorZSlope/P_MobjCeilingZSlope` (тело то же, под `PS2_OPT_REND`). Побитно (детерминированная подстановка), A/B 4 демо идентичен.

### 3.5 PS2-163: быстрые `memcpy`/`memset` на 128-битных `lq/sq` (`src/ps2/ps2_memops.c`, `--wrap` в `tools/ps2/build.py`)
newlib на EE копирует по 8 байт (≈1.25 такта/байт) выровненное и побайтно невыровненное. Блок ≥ 64 байт с обоими указателями, выровненными на 16, копируется 64 байта за проход (4×`lq`, 4×`sq`, ≈3.5 такта на 16 байт),
остаток — `__real_memcpy`; `memset` — `sq` с шаблоном байта (`pextlw/pcpyld`). Остальные случаи — исходные функции newlib, результат байт-в-байт тот же (непересекающиеся блоки; цикл на asm, чтобы компилятор не превратил его обратно в вызов `memcpy`).
Включено `-Wl,--wrap=memcpy,--wrap=memset` (`SRB2_PS2_FASTMEM=0` — выключить; `--memprof` сборка со своими обёртками не затрагивается). Тот самый «water» экран (R_DrawSinglePlane) и очистка буферов: `memcpy` 0.16–0.26 М/кадр → ≈0.05.

### 3.6 PS2-164: плоские записи рёбер для `R_IsPointInSector` (`r_main.c`, `p_setup.c`: `R_ResetSectorEdgeCache`)
`P_MobjFloorZSlope/CeilingZSlope` зовёт `R_IsPointInSector` для каждого объекта на наклоне; цикл по рёбрам сектора читал на каждое ребро 6 зависимых указателей (`line→sector×2, vertex×2`). Для сектора при первом обращении строится
плоский массив `{x1,y1,x2,y2}` (только рёбра, у которых стороны различны и не горизонтальные, v1 ниже v2, порядок прежний); подсчёт пересечений — по этому массиву, условие то же (`PS2_EdgeXLess`). Секторы с линией полиобъекта (вершины движутся) идут исходным циклом.
Память: `Z_Calloc/Z_Malloc` `PU_LEVEL` (таблицу освобождает уровень, `R_ResetSectorEdgeCache()` из `P_LoadLevel` обнуляет указатель). Сам по себе выигрыш мал (`R_IsPointInSector` в DEMO_003: профиль 0.55 → 0.54 М на кадр: основная цена — цепочка проверок и 64-битные произведения `PS2_EdgeXLess`, а не загрузки); остаток снят памятью ответов, см. 3.14.

### 3.7 PS2-165: смещения текстур стен (`r_segs.c`, три места `R_StoreWallRange`)
`FixedMul(slide, diff)` не вызывается при `slide == 0` (результат 0 при любом diff). ≈ −0.02 М на DEMO_001.

### 3.8 PS2-166: интерполяция динамических наклонов без soft-double (`r_fps.c: R_ApplyLevelInterpolators`, `PS2_LerpDoubleOne`)
В DEMO_001/003 за кадр применяется 97/90 динамических наклонов; каждый — 7 значений `double` через `R_LerpDVector3`×2 и `R_LerpDouble` (по три soft-float операции libgcc, ≈20 000 тактов на наклон; ≈0.4–0.5 М/кадр в этих демо).
Без интерполяции кадров (`frac == FRACUNIT`) результат одного значения — `from + (1.0 * (to - from))`. Если старое и новое значение побитно равны (и это ноль или нормализованное), результат — само `from` (−0 становится +0:
−0−(−0)=+0, −0+(+0)=+0 по IEEE и по libgcc fp-bit). Иначе — исходная арифметика (сдвинувшиеся значения, субнормальные, inf/NaN). Эквивалентность по построению; теневая проверка `-DPS2_NODECHECK` (хост и EE) сравнивает биты с исходной формулой на каждом значении.
Диагностика `-DPS2_INTERPSTAT`: DEMO_001 679 из 679 значений за кадр не менялись; DEMO_003 538.5 из 630 не менялись, 91.5 сдвигались (арифметика). Хост-сборка использует исходный наклон (не `PS2_OPT_SLOPE`) и вектора `double` на картинку не влияют, поэтому проверка PS2-166 на хосте — теневая; на EE (`PS2_OPT_SLOPE`) их читает `RQ_LoadSlope`, и golden 4×1050 кадров идентичен.

### 3.9 PS2-167: память ответов `R_PointInSubsector` (`r_main.c`)
За 1050 тиков DEMO_003: 2.3 М вызовов `R_PointInSubsector`, из них 67 % повторяют координаты неподвижного объекта (`P_CheckPosition(mobj, mobj->x, mobj->y)` в каждом треде). Ответ — чистая функция (x, y) при неизменном массиве узлов, поэтому небольшая
прямая память (4096 записей × 12 байт в статическом `.bss`, сравниваются обе координаты, индекс подпространства+1, 0 = пусто) возвращает прежний ответ; обнуляется при смене уровня (`R_ResetSectorEdgeCache`) и при пересборке кеша BSP.
Хост: доля попаданий 67–76 % на всех четырёх демо; самопроверка `-DPS2_BSPCHECK` (ответ памяти сверяется с полным спуском) — без расхождений; негативный контроль 10 (сравнение только x) расходится на DEMO_003.

### 3.10 PS2-168: цикл по ячейкам полиобъектов в `P_CheckPosition` (`p_map.c`)
Цикл читал `bmapwidth/bmapheight/polyblocklinks` заново на каждую ячейку и проверял границы. Теперь: целиком пропускается в уровне без полиобъектов (`polyblocklinks == NULL`, PS2-88), иначе границы приводятся к блоковой карте один раз, строка массива — в локальной переменной; тело цикла то же. Побитно.

### 3.11 PS2-169: HUD `V_DrawStretchyFixedPatch` (`v_video.c`)
Внутренний цикл по пикселям: `screens[]`, `vid.width`, `v_colormap`, `v_translevel`, `post->length` перечитывались после каждой записи байта (char-указатель), функция пикселя вызывалась через указатель. Инварианты — в локальные переменные, четыре функции пикселя
(`standardpdraw/mappedpdraw/translucentpdraw/transmappedpdraw`) развёрнуты в четыре цикла (`switch` один раз за пост); выражения те же. DEMO_004 (HUD-тяжёлый кадр): `V_DrawStretchyFixedPatch` 0.39 → 0.26 М на кадр (профиль), DEMO_001 0.17 → 0.12 М.

### 3.12 PS2-170: ранний выход из просмотра drawseg'ов в `R_ClipVisSprite` (`r_things.c`)
Просмотр отрезков для спрайта (PS2-90: по порядку убывания индекса, через битовые маски колонок) только заполняет `clipbot/cliptop` там, где стоит −2. Хост-счётчик `-DPS2_CLIPSTAT` (убран после замера): 39 % (DEMO_001), 48 % (DEMO_002),
21 % (DEMO_004), 33 % (DEMO_003) кандидатов просматривались уже после того, как все колонки спрайта заполнены (из них 55–81 % «перед спрайтом»). Теперь счётчики незаполненных колонок (`unsetbot/unsettop`, уменьшаются при записи
значения ≠ −2) останавливают просмотр, когда обе нули — дальше ничего не может измениться. Побитно; негативный контроль 11 (остановка на одну колонку раньше) расходится на всех демо.

### 3.13 PS2-171: рисовальщики спанов (`r_draw8.c`: `R_DrawSpan_8`, `R_DrawTranslucentSpan_8`, `R_DrawWaterSpan_8`, `R_DrawTiltedSpan_8`)
Дизассемблирование `R_DrawSpan_8`: после каждой записи байта в экран перечитывались `nflatyshift/nflatxshift/nflatmask` (три `lw` на пиксель), компилятор пересобрал сложение шагов в `x + k·step` и разлил регистры в стек;
~25 тактов на пиксель вместо расчётных 14. `R_DrawTiltedSpan_8` ещё читал `planezlight`, `tiltlighting`, `ds_colormap`, `colormaps`, `ds_x1` (с записью!) на каждый пиксель — 59 тактов на пиксель.
Инварианты в локальных переменных (`ds_x1` записывается обратно в конце: состояние глобалов прежнее), шаги — последовательные сложения (пустой `asm` против пересборки). Те же выражения, `UINT32`-арифметика. Теперь 8 АЛУ + 2 `lbu` + `sb` на пиксель.

### 3.14 PS2-172: четыре мелких точных ускорения (`r_slopeq.h`, `ps2_rdraw.h`, `r_main.c`)
* **`RQ_Div128`** (деление 128/64 в пересечении луча со стеной-наклоном, `r_slopeq.h`): цикл из 64 итераций начинался с битов, где остаток заведомо меньше делителя. Пропускаются первые k итераций, k — наибольший сдвиг с `(hi+1) << k <= d`
  (все промежуточные остатки не больше `((hi+1) << j) − 1 < d`, вычитаний нет и биты частного нули): остаток сразу `hi << k | lo >> (64−k)`. Числитель ~82 бита, делитель ~50: пропускается примерно половина итераций.
  Хост-тест `sw_hosttest.py` (40 М случаев, формы hi/lo/d, граничные и насыщение) 0 расхождений, негативный контроль `NEGCTL=12` (пропуск на одну итерацию больше) обнаружен.
* **`PS2_Fill16`** (сброс клипа visplane: 2×640 байт на каждую новую плоскость): после выравнивания на 8 байт ещё один 64-битный `sd` выравнивает на 16, основная часть — парами `sq` (2 `sq` вместо 4 `sd` на 32 байта).
* **Память `R_IsPointInSector`** (`r_main.c`, как PS2-167): ответ — чистая функция (сектор, x, y) при неподвижных линиях (сектора с линией полиобъекта в память не попадают), а `P_MobjFloorZSlope/CeilingZSlope` из `P_CheckPosition` спрашивают угол
  каждого неподвижного объекта на каждом тике. Прямая память 4096×12 байт (`.bss`), сравниваются обе координаты и сектор, сбрасывается вместе с таблицей рёбер при смене уровня. Хост: 93.5 % (DEMO_003: 1.98 М вызовов), 95.9 % (DEMO_001), 97.6 % (DEMO_002), 97.4 % (DEMO_004) попаданий;
  самопроверка `-DPS2_BSPCHECK` (ответ памяти против полного обхода линий) без расхождений; негативный контроль `NEGCTL=13` (сравнение только x) расходится на DEMO_003. `R_IsPointInSector` 0.54 М → ~0.05 М на кадр DEMO_003.
* **Проверка ключа кеша BSP** (`R_PointInSubsector`): вместо шести сравнений корневой линии на каждый вызов (`R_BSPCacheSigEq`, ~40 тактов × 2300 вызовов на кадр) ключ — указатель и размер массива узлов; смену уровня отмечает `R_ResetSectorEdgeCache` из `P_LoadLevel` (`R_ResetBSPCacheKey`).
  Единственное место, подменяющее массив узлов, — загрузка уровня.

### 3.15 PS2-173: ранний отсев FOF-плит в `P_CheckPosition` и `P_AdjustMobjFloorZ_FFloors` (`p_map.c`, `p_mobj.c`)
Обе функции для каждой существующей плиты сначала считали `topheight/bottomheight` (две чистые функции со слоем `P_MobjFloorZ/CeilingZ`), а потом проверками флагов отбрасывали большинство плит (вода, декор). Перед расчётом поставлен чистый предфильтр, `continue` для тех же плит,
которые отбросила бы цепочка ниже (одни и те же условия: goo-вода, лава/вода игрока, исключение MT_SKIM, solid для этого типа, quicksand; `P_CheckSolidLava`/`P_CanRunOnWater` — чистые). Остальной код не тронут. Побитно.

### 3.16 Отвергнутые эксперименты (измерено, не принято)
* `-O3` для горячих юнитов (`r_segs/r_plane/r_draw8/r_things/r_main/r_bsp/p_map/p_mobj/p_maputl`, `SRB2_PS2_UNIT_FLAGS`): DEMO_001 8.82 → 8.74 (−0.9 %), DEMO_002 9.10 → 9.08, DEMO_003 12.94 → 13.01 (+0.5 %), ELF +103 КБ — не принято.
* `-O2 -fno-tree-reassoc` для всего движка (после находки пересборки сумм в спанах): 8.83 / 9.12 / 13.05 против 8.82 / 9.10 / 12.94 — нет выигрыша.
