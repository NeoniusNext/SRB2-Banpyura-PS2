Ветка `opt12-hwdrv`, worktree `/home/user/wt/hwdrv`. Реестр отличий PS2-HW-440..479. Единицы: такты COP0 EE на кадр (`HWPROF wall`), PCSX2 **2.8.2** (программный GS, 32 МБ), `--prof` + LTO,

## 2. Этап 1: темп кадров, vsync, flip (задача 1)
### 2.1 Что оказалось (измерено)
* **Режим вывода в этой среде — PAL, 50 Гц** (BIOS «Europe v02.00», `pcsx2.log`: `Set GS CRTC configuration. PAL 640x512 @ 50.000`). Один vblank = 5.898 М тактов EE, а не 4.92 М. Поэтому `flipwait` ≈ 2.7 М из 5.95 М
  в лёгких окнах D1 — это не простой «из-за квантования 60/30», а ровно запас до следующего vblank: окно 3 D1: 105 кадров за 106 vblank (`vbl=106`), работа EE ≈ 3.2 М из 5.9 М. «60 FPS = 4.9 М» верно только для NTSC;
  на PAL-консоли предел показа 50 кадров/с (`I_GetRefreshRate` = 50: интерполяция идёт до 50, а не до 60).
* **Схема flip («gate», `ps2_hw_gs.inc`)**: два буфера цвета + один Z. `frame_end` кадра N ждёт flip кадра N-1 (`flip_wait`), потом ставит `pend`; DMA кадра N+1 удерживается (`dma_start_locked`) до flip кадра N
  (кадр N+1 рисуется в буфер, который показывается до этого flip). Следствие: пока работа EE `w` меньше периода vblank `P`, период кадра ровно `P` (EE ждёт); при `w > P` EE не ждёт совсем (`flipwait = 0`) и период кадра = `w`,
  а не `2P`. То есть **квантования 60/30 нет** (в окнах с `w` чуть больше `P`: wall 6.45 при `flipwait` 0.17 и `vbl` = 114/105 кадров).
* Тройная буферизация не даёт выигрыша по тактам EE при таких работе и GS: GS (и в PCSX2, и по оценке для железа: 320x224 с перекрытием 3–4, 3 МБ текстур, 3 К полигонов — единицы мс) успевает за vblank.
  Она дала бы только сглаживание выбросов (кадр 9 М после кадров по 4 М) и стоила бы 280 КБ VRAM (+1 буфер 320x224 CT32) из 3.2 МБ пула текстур.

### 2.2 Что добавлено для измерения темпа (PS2-HW-440)
* Строка **`HWPROF0 win=N work=.. wall=.. sleep=.. cad=a/b/c/d/e vbl=.. flips=..`** (после каждого окна в 105 кадров): `work` = wall минус ожидания драйвера (`wait` кольцо/GS, `flipwait`) минус сон главного цикла (`I_Sleep`/`I_SleepDuration` в `i_system.c`
  считают такты в `ps2prof_sleep_cyc`, только `PS2_PROFILE`); `cad` = гистограмма «сколько vblank картинка оставалась на экране» (бин 0 = заменена в пределах vblank, 1, 2, 3, 4+; считается в `do_flip`).
  `tools/ps2/hwsum.py` печатает `work` и `cad`; `tools/ps2/hwdrv_ab.py RUN...` — одна строка на прогон (wall, макс, work, FPS, flipwait, драйвер+планировщик, выселения, тяжёлые пересборки текстур, потерянные рисования).
* D1 (ELF `e1`, окна 1..9): work среднее **6.11** М / макс 8.98 при wall 6.70; `cad` окна 3 (лёгкое): 0/104/0/1/0 (каждая картинка один vblank = полные 50 Гц), окно 1 (тяжёлое, wall 8.99): 0/53/50/2/0 (кадр = 1.5 vblank). Кадры не квантуются
  по 60/30: период кадра = max(работа, vblank).
* Реальное время с интерполяцией (`--playdemo --cfg 'fpscap "Match refresh rate"'`, D1, `p_d1i`): окна по 105 кадров идут за 82/76/79 тика (35.0 TPS: `tics = real`), кадров 105 → ≈ 50 FPS при work < 5.9 М и 37–42 FPS в тяжёлых окнах,
  потерь тиков нет (`TICK ... tics=82 real=82`).

## 3. Этап 2: провалы D2 («нет данных → чтение патчей из PAK»), кэш данных текстур LRU (PS2-HW-441, 442)
### 3.1 Находка (измерено)
* DEMO_002 в ELF LTO даёт окна по 14–24 М тактов на кадр (окна 2, 7, 9; в базе `b_d2`: wall среднее 10.30, максимум 23.71): `HWPROF22 SetTexture` = 15.3 М на кадр. Новые строки **`HWREGEN`** (PS2-HW-441, драйвер, печатается
  пересборка текстуры дороже 2 М тактов: имя, такты, «сколько раз заливалась» `uploads before`, «чем сброшена из VRAM» `dropped by`: 1 вытеснена, 2 повышение уровня плана, 3 понижение, 4 смена лимита, 5 прочее) показали причину:
  **пересборка составной текстуры стоит 4 М тактов на каждую лумпу-патч, которой нет в кэше зоны** (чтение одной лумпы из PAK стоит одинаково для 2 КБ и 60 КБ: `THPIPMT3` 24 патча 97 М, `THROCKM3` 67 патчей 261 М, `THROCK4` 81 патч 315 М = ≈1 с,
  `SKY4` 151 патч 26 М пока патчи в кэше). Первая сборка при загрузке кадра дешёвая (патчи прекэшированы: `THROCK4` 3.9 М), последующие (после выселения из VRAM, повышение уровня плана) — 260–320 М тактов.
* Причина «нет данных»: данные составной текстуры у движка имеют тег `PU_HWRCACHE_UNLOCKED` (102 ≥ `PU_PURGELEVEL`): «выгружаемо в любой момент». Зона (`Z_AllocBlock`) освобождает **все** блоки таких тегов на любом выделении, которое не
  поместилось сразу (в HW нет `Z_PurgeLock`), и в начале 3D-вида; кэш уровней текстур драйвера (`dc`, 4 МБ) имеет тот же тег и живёт не дольше одного кадра. То есть при каждом сбросе текстуры из VRAM данные уже пропали, а патчи —
  в зависимости от давления на зону. Появляется «обрыв» по размеру арены: тот же код в ELF без LTO даёт D2 7.1 М (патчи в кэше), в LTO 10.3 (патчи сброшены); `-zreserve 1664` воспроизводит обрыв и без LTO.
* Побочный эффект того же правила: **патч спрайта/HUD** (`regen_kind 0`) после выгрузки не восстанавливается при рисовании пачки: рисования пропускаются («HWD texture not resident ... no data (purged) patch», 3–6 раз за прогон; спрайт/тень/плашка
  пропадает на кадр) — это и есть мигание, видимое на картах у границы памяти.

### 3.2 Что сделано
* **`PU_HWRCACHE_LRU` (новый тег 27, `z_zone.c`/`z_zone.h`, переключатель `-hwkeep N`, 0 = включено по умолчанию, 1 = прежнее правило)**: пока `Z_SetHWCacheLRU` включён, `Z_ChangeTag(.., PU_HWRCACHE_UNLOCKED)` блока с владельцем делает блок
  кэшем LRU (в реестре кандидатов вытеснения, возраст как у `PU_CACHE`: сначала самые старые, и только когда нужно место), а `Z_AllocBlock` в последнюю очередь, когда другие кэши и хук не помогли, освобождает такие блоки все сразу
  (как раньше их освобождал первый же промах) — без этого уровни у границы памяти падают («Out of memory allocating 4000 bytes» на MAP10 в первом кадре: кэш-блок текущего кадра зона не трогает). `HWR_PS2_AllocData/StealData/UnlockData` (кэш
  уровней драйвера) и данные мипмапов патчей (`HWR_PATCH_UNLOCKED` в `hw_cache.c`, 4 места) идут тем же путём. Условие преобразования: свободной арены не меньше 128 КБ (`-hwkeepfree KB`), необязательный предел байт «больших» блоков (> 32 КБ) за кадр (`-hwkeepcap KB`, 0 = нет).
* Первые две версии, **отброшенные** по измерению: (а) «список удержания» дорогих текстур с `Z_Touch`/`Z_ChangeTag(PU_CACHE)` в конце кадра (на `-zreserve 1664` выигрыша 0: тег `UNLOCKED` движок ставит при каждом выборе текстуры); (б) то же правило без предела
  и без последней очистки — MAP10 уровень не загружается (OOM). Список удержания убран из кода (с LRU-тегом +0.0 М).
* Поле `GLMipmap_t.ps2_nup/ps2_drop/ps2_cost` (диагностика `HWREGEN`), `HWSKIP` (первые 40 пропущенных рисований реальной потерей текстуры), `HWPROF46`.

## 4. Этап 3: точность текстур — проход верности плана (PS2-HW-443, `-hwfid 1` выключает)
### 4.1 Находка
* Кадр 0 (`k100`) DEMO_002 в HW против ПК-OpenGL того же кадра: **MAD 5.74, 5705 пикселей из 64000 с разностью > 48** (при совпадении состояния игры: кадр от кадра), а при `-hwdbg 33554432` (без плана, все текстуры полного размера) **MAD 0.85, 596 пикселей**.
  Причина: «точный» план кадра (`ps2_hw_plan.inc`) хранит образ на уровне, где тексель ≈ 1 пиксель (стена с текселем 1/8 пикселя идёт уровнем 3); из каждого блока 8x8 берётся один тексель (самый контрастный: `dec_level`), и
  решётка выборки ПК (nearest по полному размеру: на мелких серых панелях видны линии-муар) заменяется шумом. Кроме того в этом кадре у плана **пропадали тени под объектами** (на двух ELF `e1`, не воспроизводится на
  других раскладках памяти; после смены тега патчей на LRU и этого прохода тени есть: 364 тёмных пикселя в полосе тени против 273).
* Бюджет плана (75 % пула минус резерв) почти не использовался: уровень выбирался «точным» всегда, а полный размер — только при превышении бюджета, где его отнимали.

### 4.2 Что сделано
* После цикла бюджета в `PS2HWD_PlanEnd`: пока сумма плана ниже `PLAN_FID_PCT` = 85 % бюджета, образы с большей видимой площадью (сначала ≥ 1500 пикселей², потом остальные) возвращаются на **самый тонкий уровень, который помещается** (до 0 = полный размер).
  Образы, уже лежащие в VRAM грубее, остаются (`plan_too_coarse`, допуск 1.5: без повторной заливки и мигания), полный размер занимает место образа, когда он делается заново. Стоимость кадра на такт не растёт (`level 1/2/3 made ...` из `dec_level` дороже заливки по ссылке).
* Нагрузка: `-hwfid 0` / `-hwfid 1`, одна ELF без LTO, окна 1..9, wall среднее: D1 6.79 / 6.77, D2 7.13 / 7.22, D3 10.01 / 10.01, D4 10.05 / 10.04 (разницы в пределах шума 0.1); выселений VRAM за прогон: D1 709 / 828, D2 1289 / 1216, D4 1262 / 1025.

## 5. Этап 4: DEMO_003 у края зоны — «Out of memory allocating 663552 bytes» и его лечение (PS2-HW-445)
### 5.1 Находка
* Первый прогон итоговой ELF (`e8`: LTO, `PU_HWRCACHE_LRU`, проход верности) на D3 закончился `I_Error: Out of memory allocating 663552 bytes` (кадр 584, тег `PU_HWRBATCH`, `-ps2prof`: защиты `ps2_hwfb` нет). Сначала это выглядело как цена моих
  изменений (LRU + проход верности по отдельности D3 проходит: `-hwfid 1` 9.91, `-hwkeep 1 -hwfid 0` 9.73, оба вместе — ошибка). **Проверка показала, что это лотерея раскладки памяти, а не следствие моих изменений:** ELF `e8`, D3, разный
  `-zreserve` (размер арены), новые умолчания / прежнее правило (`-hwkeep 1 -hwfid 1`): 1408 — ошибка / ошибка; 1536 — ошибка / 9.72; 1664 — 9.94 / ошибка; 1792 — 9.77 / 11.60 (43 пропущенных рисования, 1429 realtics).
  Падают оба режима, на одном и том же кадре 584 и том же выделении.
* Что выделяется: **пул блоков коллекции полигонов** (`pb_pool`, `hw_pbatch.inc`: 12288 квадрослов, растёт ×1.5: 18432, 27648, 41472 · 16 B = 663 552 B). На кадре 584 (окно 6: 2297 полигонов на кадр, самый тяжёлый вид D3) пул растёт в четвёртый
  раз; в арене в этот момент 3.16 МБ свободно в 242 кусках, **самый большой 456 576 B** (фрагментация 86 %: между кусками долгоживущие `PU_LEVEL`/`PU_HWRPATCHINFO` и блоки спрайтов текущего кадра, которые вытеснять нельзя). Старый блок пула
  при росте жив до копирования, так что ему нужно место и под новый блок целиком.
### 5.2 Что сделано (`hw_pbatch.inc`, файл HWFRONT: точечная правка, см. раздел 11)
* **PS2-HW-445**: `HWR_PBGrow(need, soft)`: если в пуле ещё есть собранные полигоны, рост пула просится у зоны через `Z_TryReallocAlign` (старый блок цел при неудаче). Нет места — `pb_nogrow` (до конца уровня: каждая неудача обходит всю арену),
  `HWR_PBAdd` рисует собранное (`HWR_PBFlushEarly`, тот же путь, что у «слишком много состояний») и добавляет полигон в пустой пул заново. Порядок полигонов через разрез теряется (как при `HWR_PB_BMAX`); для непрозрачных пачек порядок решает Z-буфер.
  Строка `HWPROF50` получила `pool N quadwords, cut for room=K`. `-hwgo 16777216` — пул не растёт никогда (проверка разреза без нехватки памяти).
* Проверка (ELF `e9`, D3, новые умолчания): `-zreserve 1408` (там обе прежние ELF падали): **проходит, окно 6 — 21 разрез по нехватке места, пул остался 27648 квадрослов, wall 10.38 (макс 16.42)**; 1536 — проходит (пул вырос до 41472, 10.48); 1664 — 9.75; 1792 — 9.77; 1024 — 9.75.
  Итого D3, `-zreserve` 1024/1408/1536/1664/1792: **9.75 / 10.38 / 10.48 / 9.75 / 9.77, ни одной ошибки памяти** (до правки, прежнее правило, значения 1408/1536/1664/1792: ошибка / 9.72 / ошибка / 11.60; на 1024 не мерили).
### 5.3 Остаточный разброс D3 (не закрыто)
