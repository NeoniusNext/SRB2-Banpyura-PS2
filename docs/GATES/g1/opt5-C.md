Сессия 2026-10-05. Каталог `build/opt5-c/` (сборки `c0..`, прогоны `run-<сборка>-<демо>`, скрипты `bld.sh`, `prof.sh`, `phases.py`, `hostcheck2.sh`, `hostbatch.sh` — копии opt4-c).
Методика та же, что в `opt4-C.md`: PCSX2 2.6.3 (32 МБ), релиз, боевой путь, такты COP0 EE/кадр на `-timedemo` (окна 1..9, 945 кадров), FPS = 294.912 М / (такты/кадр).

## 0. Что нашёл на старте (недоделка OPT4)

Журнал `opt4-C.md` пуст, но в дереве лежат правки OPT4 (сравнение со снимком `pre-opt4-20261005.tar`): `PS2_OPT_SPR` (PS2-90: ускоряющая структура drawseg/спрайты, `r_things.c`),
`R_RenderSegLoopT(plain, tiers)` и прямое индексирование колонок (`r_segs.c`, `SEG_COLUMN`), `-G8` (PS2-92) и **LTO движка по умолчанию** (PS2-93) в `tools/ps2/build.py`,
`--memprof`, зонд `PS2SUB_*`. Сборка `build.py` (с LTO) и `SRB2_PS2_HW=1` собираются (проверено сегодня: 110/110 и HW-вариант, `build/opt5-c/c0`, `chw`).

Проблема инструмента: фазовый профайлер использует `-Wl,--wrap=...`, а при LTO все объекты движка сливаются в один (`-r`), внутренние вызовы wrap не видят — `--prof` сборка с LTO не печатает ни одной строки PROF
(мой первый прогон c0 висел до таймаута). Исправление PS2-94 (ниже): в LTO-профиль-сборке `-DPS2_PROF_DIRECT`, кадры считает `PS2Prof_FrameEnd()` из `I_FinishUpdate`; печатаются `total` и `SUB`-зонды; фазы — только с `SRB2_PS2_LTO=0`.

## 2. Этапы

### 2.1 PS2-94: профайлер в LTO-сборке (`tools/ps2/build.py`, `src/ps2/ps2_prof.c/.h`, `i_video.c`)
`--prof` при LTO определяет `PS2_PROF_DIRECT`, не ставит `--wrap`; кадры считает `PS2Prof_FrameEnd()` из `I_FinishUpdate`, в строке PROF — только `total` (все такты «other») и `tics` (дельта gametic);
`SUB`-зонды работают. Фазы — с `SRB2_PS2_LTO=0`. Без этого `--prof`+LTO вообще не печатал PROF (прогон c0 висел до таймаута).

### 2.2 PS2-96/97 (tic-ядро, общее для обоих рендереров; `PS2_OPT_PTICK`)
* PS2-96, `r_fps.c:R_UpdateMobjInterpolators`: пропускается, пока интерполяция кадров выключена (`!R_UsingFrameInterpolation()`): копии `old_*` читает только интерполированный рисунок
  (все читатели под этой проверкой), а копирование каждого интерполируемого mobj каждый тик стоило 0.13 М (DEMO_001) / 0.23 М (DEMO_002) тактов. При включении интерполяции (меню/HW 60) первый же тик
  обновит их; первый кадр после переключения может показать один устаревший шаг.
* PS2-97, `p_enemy.c:P_LookForShield` (вызывается из `A_AttractChase` каждым кольцом каждый тик, обходил до 31 пустого слота): прыжок по битовой маске игроков
  (`ps2_ingamemask`, обновляется в начале `P_Ticker`), `lastlook` оканчивается точно там же. Модель эквивалентности `build/opt5-c/lookshield_test.py`: 400000 случайных конфигураций
  (маска, `lastlook`, исходы) совпадают с оригиналом; негативный контроль (сдвиг `lastlook` на 1) расходится в 488 из 1000.

Замер (`c3` = c1 + PS2-96/97, LTO, `prof.sh`, DEMO_001/002, 945 кадров): **9.85 -> 9.40 М (31.4 FPS)** и **10.31 -> 9.62 М (30.7 FPS)**.
Хост (4 демо, `hostbatch.sh b`, позитив): tics identical, 0 кадров отличий, 0 px от golden.

### 2.3 PS2-95: интерполяция кадров для показа > 35 FPS (проверка на PCSX2, software, реальное время)

`I_GetRefreshRate()` (i_video.c): software -> 35 (как раньше: «Match refresh rate» = без интерполяции), аппаратный рендерер -> частота вывода (PAL 50, иначе 60); `-ps2refresh N` — любое значение (тесты).
Явный `fpscap 60` в конфиге включает интерполяцию и для software (механизм движка: `r_fps.c`, `D_RunFrame`: тики 35 Гц, кадры на реальном времени, `rendertimefrac`).
Прогон: `-playdemo DEMO_001` в реальном времени, сборка c3 (LTO --prof), конфиг `fpscap "60"` (`build/opt5-c/interp.py`, `interp-c3cap60.log`, `run-interp-c3cap60/boot.txt`).
Колонки: кадров/окно, тиков/окно, секунд (из тактов), кадров с 0 < rendertimefrac < 1 (`INTERP` в логе):

| окно | кадры | тики | сек | FPS показа | TPS | дробных кадров |
|---|---:|---:|---:|---:|---:|---:|
| 2 | 105 | 83 | 2.34 | 44.9 | 35.5 | 90 |
| 3 | 105 | 63 | 1.80 | 58.3 | 35.0 | 105 |
| 5 | 105 | 78 | 2.24 | 46.9 | 34.8 | 95 |
| 4 (тяжёлая сцена) | 105 | 147 | 4.20 | 25.0 | 35.0 | 3 |
| 7 | 105 | 124 | 3.54 | 29.7 | 35.0 | 6 |

Вывод: механизм работает на PS2: TPS остаётся 35 при любой нагрузке, FPS показа растёт до потолка 60 там, где кадр дешевле 4.9 М тактов (окно 3: 58 FPS, 5.1 М тактов на кадр вместе с простоем),
и падает до 25-30 в тяжёлых сценах (software 9.4 М/кадр > 4.9 М). Для стабильных 60 в любых сценах нужен рендерер дешевле 4.9 М/кадр (HW) — software без снижения качества достичь этого не может
(пол по профилю: стены 2.5 М, колонки/спаны 1.7 М, спрайты/маскированное 2.0 М, тик 1.2-3.5 М).

### 2.4 PS2-98 (`PS2_OPT_BSPC`) и PS2-99 (`PS2_OPT_ANIM`)
* PS2-98, `r_main.c:R_PointInSubsector` (0.40 М/тик в DEMO_002, по всем mobj: `P_CheckPosition`, `P_SetThingPosition`, ...): спуск по BSP стартует не с корня, а с узла, решающего целую клетку
  сетки (128..4096 ед., <= 16384 клеток, таблица UINT16 в статическом массиве 32 КБ). Клетка относится к стороне разделяющей линии, только если все четыре угла отстоят от неё минимум на 2 единицы карты
  (точное 64-битное векторное произведение; погрешность `R_PointOnSide` — доли 1/65536 единицы), оси x/y — точным сравнением. Ключ таблицы — указатель на массив узлов, их число и 6 слов корня.
  Если линии узлов не целые (формат с дробными), таблица не строится (полный спуск).
  * Первая версия брала память из зоны (`PU_LEVEL`) и печатала счётчик самопроверки через `CONS_Printf`: хост-сравнение показало 261 отличающийся кадр DEMO_003 и расхождение tics DEMO_004.
    Бисекция (`-DPS2_NOOPT_ANIM` / `-DPS2_NOOPT_BSPC`) указала на PS2-98; причиной оказалась **сама самопроверка**: строка консоли «BSPCHECK n calls verified» рисуется поверх кадров
    (9281 px в DEMO_003). Самопроверку перевели на `I_OutputMsg` (только лог), память — на статический массив (раскладка зоны не меняется).
  * Самопроверка `-DPS2_BSPCHECK` (каждый вызов сравнивает результат с полным спуском, при расхождении `I_Error`): 4 демо x 1049 кадров прошли, проверено 65536 + 655360 + 2293760 + 327680 =
    **3 342 336 вызовов**, 0 расхождений; кадры/тики: 0 отличий от base, 0 px от golden (`hostcheck-bsF.log`).
* PS2-99, `p_spec.c:P_UpdateSpecials` (анимация текстур: два деления на каждый кадр каждой анимации) -> одно деление на анимацию; `p_mobj.c:P_MobjThinker`: вызов `P_CheckMobjTrigger` только при `MSF_TRIGGERLINE_MOBJ` в секторе.
