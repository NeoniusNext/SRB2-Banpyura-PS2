# OPT11, агент AUDIO: «глюки звуков, когда музыка не играет» (отчёт, реестр PS2-300..329)

Ветка `worktree-agent-a1350918dd78df311`. Эмулятор PCSX2 2.6.3 (звук Null, но IOP и SPU2 исполняют настоящий `audsrv.irx` по эмулируемому времени; железо не проверялось).
Окружение: `export PS2DEV=/opt/ps2dev-x/ps2dev PATH=$PS2DEV/ee/bin:$PS2DEV/bin:$PS2DEV/dvp/bin:$PATH`, сборка `SRB2_PS2_OUT=$PWD/build/outN SRB2_PS2_NO= SRB2_PS2_HW=1 python3 tools/ps2/build.py --jobs 2`.

## 1. Причина (найдена чтением исходника audsrv и подтверждена запуском на настоящем `audsrv.irx` в PCSX2)

### 1.1 Источник: `play_thread` в `iop/sound/audsrv/src/audsrv.c` (ps2sdk, версия 0.93, кольцо 9400 Б, шаг 940 Б)

```c
if (playing && upsampler != NULL) {
    up.src = ringbuf + readpos;  step = upsampler(&up);   // 940 байт при 22050/16/стерео
    readpos += step; if (readpos >= ringbuf_size) readpos = 0;
}
```

Поток IOP **безусловно** двигает `readpos` каждые 512 выборок SPU2 (10.667 мс = 940 Б) после первого `audsrv_play_audio` (`playing = 1`) и **не смотрит на `writepos`**. Если EE перестаёт писать, `readpos` обгоняет `writepos` и IOP **бесконечно по кругу проигрывает старое содержимое кольца** (последние ≈106 мс), `audsrv_queued()` при этом рисует «пилу» (`ringbuf_size - (readpos - writepos)`), а не 0. Тишина (нули) там возможна только если кольцо перезаписано нулями.

Это проверено в эмуляторе, `-aprobe` (заполнить кольцо нулями, больше не писать, читать `audsrv_available/queued` каждые 25 мс; `build/runs/probe0/boot.txt`):
`queued: 6580, 4700, 1880, 0, 7520, 4700, 2820, 940, 7520, 5640, 2820, 940, 8460, ...` — период 9400 Б = 106.7 мс, то есть «очередь» не убывает до нуля и остаётся, а каждый круг IOP снова читает те же 9400 байт.

### 1.2 Почему это бьёт именно «звуки без музыки»

Движок (`i_sound.c: AudioPump`) при `!PS2E_Active()` (нет голосов SFX, нет музыкального блока, музыка на паузе / кончилась / остановлена / `digimusic Off`) **вообще не пишет в audsrv** (`return` до `audsrv_queued`). Пока играет музыка, поток пишется без перерыва и кольцо всегда свежее, поэтому дефект скрыт. Без музыки после каждого SFX (а также после конца трека, `stopmusic`, паузы, смены трека) кольцо остаётся с хвостом последнего звука, и IOP зацикливает его до следующего звука: слышен ритмичный повтор/дребезг последних ≈100 мс, а начало следующего SFX попадает в случайное место цикла.

### 1.3 Вторая причина (смертельная): схлопывание оценки ёмкости `queue_cap`

`AudioPump` после короткой записи делает `queue_cap = audsrv_available() + queued`. У `audsrv` указатели `readpos == writepos` означают одновременно «пусто» и «заполнено» (`audsrv_available()` и `audsrv_queued()` оба возвращают 0). Если запись упёрлась именно в это состояние, `queue_cap` становится 0 или 940, после чего `space = queue_cap - queued < 2048` и **ни одна запись больше не происходит** (повторная синхронизация ёмкости делается только внутри записи). Поток умирает навсегда, а IOP бесконечно зацикливает последнее содержимое кольца.
Свидетельство из прогонов других агентов (не моих, только чтение): 335 строк `ASTAT ... cap=0` и 9 строк `cap=940` в `.claude/worktrees/*/build/runs/*/boot.txt` (19 505 строк с `cap=9400`), например `agent-a401b66ae9f5c91a7/build/runs/rt-c/boot.txt`: после `blocks=941 sent=1927168` счётчики `blocks`/`sent` больше не растут, а `underruns` растёт (`13, 22, 32, ...`) — звук мёртв до конца прогона.

## 2. Инструменты воспроизведения (новые)
* `-atrace N` (ELF, `i_sound.c`): журнал каждой записи в audsrv (время, байты, номер блока) и каждого чтения кольца IOP (`audsrv_available/queued`), в простое — каждое 4-е пробуждение; пишется `atrace.bin` при выходе. `-adump F` (был) — все блоки, которые отрендерил микшер (`apcm.raw`).
* `tools/ps2/audio_ring_sim.py <run>`: модель кольца `audsrv.irx` (9400 Б, шаг 940 Б / 10.667 мс, безусловное движение `readpos`). Фаза шага подбирается по чтениям журнала: **в каждом прогоне совпали 100 % наблюдений** (`phase_matched == phase_total`, например 2066/2066), то есть модель описывает настоящий IOP в эмуляторе точно. Результат: что проиграл бы SPU2 (`heard.wav`), сколько байт прочитано из кольца, не записанных заново после прошлого чтения («старые»), из них не тишина, и самая длинная такая полоса.
* `tools/ps2/audio_scen.py --elf ELF --tag T сцена...`: прогон сцены (демо-таймдемо или карта, ключи `-adump/-atrace`, выход `-aquit`) + модель + строка ASTAT. Сцены: `d1_mus` (музыка), `d1_off` (`digimusic Off`, `midimusic Off`), `d1_track` (`-acmd 300 "tunes 5" -acmd 600 "tunes 8"`: смена трека), `d1_stop` (`tunes -none`), `d1_vol0`, `d4_off_hw`/`d4_mus_hw` (HW-рендерер), `m1_pause`, `m1_none` (карта без демо). `-acmd N "команда"` — консольные команды на кадре N уровня (диагностика).
* `tools/ps2/audio_hosttests.py` — запуск на Linux (gcc) хост-тестов звука, которые раньше собирались только MSVC: `core`, `thread`, `backend`, `ring`, `ring-neg`.

## 4. Исправление (PS2-300, PS2-301; `src/ps2/i_sound.c`, `ps2_athread.h` — поля статистики)
1. **PS2-300, заливка тишиной.** Каждый отрендеренный (слышимый) блок взводит `flush_left = ring_bytes`. Когда слышимого больше нет (нет голосов, нет блока музыки: конец трека, остановка, пауза, смена трека, `digimusic Off`), `AudioPump` продолжает писать нулевые блоки, пока не будет записано `ring_bytes` (9400) нулей подряд, затем снова простаивает. Кольцо целиком нули, и IOP может читать его сколько угодно раз. Нулевые блоки держат очередь не выше 2 блоков (46 мс), чтобы звук, начавшийся во время заливки, не ждал за 93 мс нулей. Стоимость: ≈5 нулевых блоков (10 КиБ, по одному RPC на блок) после каждой серии звуков, в простое — ноль.
2. **PS2-301, постоянная ёмкость и место.** `ring_bytes` измеряется один раз на старте (`available + queued0`) и не пересчитывается. Место берётся из `audsrv_available()` на каждом пробуждении (один RPC вместо `audsrv_queued()`; `queued = ring_bytes - avail`), пишется не больше `avail - 4` (кольцо никогда не заполняется целиком: `readpos == writepos` неотличимо от пустого), короткая запись прекращает пробуждение (`shortw`), ёмкость не трогается. Старый код при `available()==0` (указатели совпали) ставил `queue_cap = 0` или `940`, после чего не писал никогда.
3. Тесты: `tools/ps2/audio_ring_hosttest.c` (точная модель IOP из исходника audsrv; рабочий `i_sound.c` целиком): серии SFX без музыки (0 байт старого звука), 64 фазы старта, байты звука записаны = проиграны один раз и по порядку (111 944 из 111 944, 0 расхождений), музыка в 5 сценах (стоп, пауза, громкость 0, конец трека, зацикленный), остановки микшера 50 мс (без старого звука) и 300 мс (поток возобновляется), 235 пробуждений при `readpos == writepos` (поток всегда возобновляется, ёмкость остаётся 9400), ровно один блок свободного места (кольцо не заполняется целиком). Негативные контроли: без заливки (`flush_left = 0`) тест видит старый звук; без запаса 4 байт видит заполнение кольца (`python3 tools/ps2/audio_hosttests.py ring ring-neg`). `backend`, `core`, `thread` — PASS на gcc (тест backend правился под PS2-70/PS2-71/заливку: `W_LumpLength`, `LIMIT_NUMSFX`, короткая запись).

* Громкость музыки 0: музыка продолжает декодироваться и микшироваться с нулевым усилением, поток в audsrv не прерывается (flushblk 0), старого звука нет. Это же означает, что декодер тратит такты впустую при громкости 0 (идея пропуска, раздел оптимизации).
* Новое в модели: **задержка начала звука без музыки** (первый слышимый блок после тишины > 150 мс, до момента, когда читающая позиция IOP доходит до его первого байта). DEMO_001 без музыки (14 звуков): min 4.3 / медиана 48.4 / max 105.5 мс; до исправления 7.1 / 68.2 / 99.3 мс (там же 8 с зацикленного «старого» звука); HW DEMO_004 без музыки: 18.5 / 46.6 / 70.2. Причина разброса не в ошибке, а в устройстве audsrv: после простоя `readpos` продолжает идти по кругу, `writepos` стоит, и разность (то есть задержка нового звука) случайна в пределах кольца (9400 байт = 106.7 мс). С музыкой задержка постоянна (очередь 72..93 мс). Постоянную задержку дало бы вечное фоновое заполнение кольца нулями (≈43 RPC/с, ≈0.2 % EE) — не включено, потому что одиночный звук с неопределённостью ±50 мс неслышим, а постоянная стоимость в простое лишняя; решение записано здесь, чтобы его можно было включить (`SILENCE_TARGET` + не прекращать заливку).

## 6. Оптимизация аудио, этап 1: декодер Vorbis (PS2-310..316)
Измерение: `-abench` (декодирует N секунд лампы через `PS2_MusicRender`, считает такты COP0 и FNV-хэш PCM), сравнение ELF между собой и с самим собой при `-novu0a`: `tools/ps2/audio_exact.py`. **Важно про числа:** такты PCSX2 — это модель числа инструкций (`tools/ps2/ee_tests/cyc_calib.c`: `mul.s` = 4, load/store ≈ 1.76, остальное ≈ 1, VU0 макро-команда ≈ 1.14), а не время реальной PS2; кэш данных 8 КБ и задержки FPU не моделируются. Выигрыш на железе должен быть того же знака (меньше команд, меньше FPU `mul.s`, меньше обращений к памяти), но в процентах он не измерен.

|---|---:|---|
| исходная libvorbis.a + `ov_read` через double (до PS2-310) | 770..831 (среднее 790) | `build/runs/ab_old` |

| + PS2-315/316 (этот этап): VU0 для MDCT, перекрытия окон, перевода float->s16 | **381** (тот же ELF с `-novu0a`: 603) | `build/ax3` |

### 6.1 Что сделано в этом этапе
* **VU0 (COP2, макро-режим) в декодере.** Ядро EE **не сохраняет состояние COP2 при смене потока** (`tools/ps2/ee_tests/vu0ctx.c`: после первого переключения в главном потоке видны vf1, ACC, I, Q другого потока). Рендерер держит константы в vf1..vf13 и использует vf14..vf18, ACC, Q и флаг clip в главном потоке. Правило ядер (`src/ps2/vorbis/ps2_vu0a.h`): секция сохраняет vf1..vf18 на входе и восстанавливает на выходе, не использует ACC-формы, Q, clip, I; флаг занятости `ps2a_vu0_busy` исключает двух пользователей, второй идёт по C-пути (результат тот же). Поток декодера выше главного по приоритету и секция не блокируется, поэтому вытеснения внутри секции главным потоком нет; поток микшера VU0 не использует. Ядра: `ps2a_fft_pairs` (ступени БПФ MDCT), `ps2a_rot1_*` (предварительный поворот), `ps2a_bitrev` (разворот битов + поворот), `ps2a_rot2_a`/`ps2a_rev_neg`/`ps2a_rev` (конечный поворот и «развёртка»), `ps2a_lap`/`ps2a_copy` (наложение окон и копирование в `vorbis_synthesis_blockin`), `ps2a_conv` (float -> s16 стерео, ровно `PS2_FloatToS16_ref`).
* Каждое ядро выполняет те же одиночные операции (сложение, вычитание, умножение раздельно, без multiply-add и без другой ассоциативности), что и скалярный код; знаки констант вынесены в таблицы (умножение на -1 точное). Таблицы строит `mdct_init` в том же выделении, что `trig` (структура `mdct_lookup` не менялась: libvorbis.a выделяет и освобождает её).
* **Выравнивание.** Вектора спектра/PCM блока выделяет `synthesis.c` (скопирован из libvorbis 1.3.7, +12 байт и округление указателя до 16), накопитель `v->pcm` — `block.c` (скопирован, `memalign(16)`), буфер вывода `ps2_music.c` — выровнен. При невыровненных данных, занятом VU0 или `-novu0a` работает скалярный путь.
* Тесты: (1) `tools/ps2/vorbis_host_check.py` — на хосте весь декодер (скопированные единицы) в скалярном виде и в векторной структуре с C-близнецами ядер на 20 настоящих дорожках: **PCM побитно одинаково** (округление к ближайшему и к нулю); (2) `tools/ps2/ee_tests/vu0kern.c` — хэш каждого VU0-ядра на PCSX2 равен хэшу C-близнеца на хосте при округлении к нулю (6 ядер); (3) `ABENCH selftest`: векторный float->s16 против эталона на 3 721 030 значениях (все порядки, границы k+0.5, особые значения): **0 расхождений**; (4) `tools/ps2/ee_tests/mdct_ee.c`: MDCT n = 64..8192 на EE против оригинала.
* **Находка про арифметику PCSX2** (`tools/ps2/ee_tests/vu0arith.c`): `vadd/vsub/vmul` VU0 в PCSX2 равны точно усечённому (к нулю) результату в 100 % случаев; EE FPU PCSX2 `mul.s` — тоже усечённое, а `add.s/sub.s` отличаются от усечения в ≈23 % случаев (округляет иначе). Поэтому PCM версии с VU0 не равен PCM скалярной версии побитно **в эмуляторе**: **0.057 % отсчётов отличаются ровно на 1 LSB (максимум 1), отношение сигнал/ошибка 105.9 dB** (6 дорожек, 3.18 млн отсчётов; `build/ax3`). На железе обе арифметики усекающие (документация EE/VU), поэтому там результат должен совпасть, но это **не проверено на железе**.
* Находка: в `res0.c`/`codebook.c`/`mdct.c` тест на хосте показал, что системная libvorbis (x86, `-ffast-math`) сама расходится со скопированными единицами на ~100 отсчётов ±1 LSB — поэтому сравнение «скопированное против стокового» на x86 не критерий, критерий — скалярное против векторного, оба из этого репозитория.
