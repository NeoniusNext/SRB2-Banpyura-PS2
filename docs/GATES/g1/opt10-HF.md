## 2. Стадия 2: палитровый рендеринг на GS (PS2-HW-71) — главный разрыв паритета света

Находка (измерением): ПК-OpenGL по умолчанию рисует с `gr_paletterendering On` (цвет = `lighttable[индекс][строка]`, затем экранная палитра 565), то есть так же, как software. Движок на PS2 это отключал (PS2-HW-62 OPT9, `HWR_ShouldUsePaletteRendering() == false`)
и освещал формулой GLSL (`mix(цвет, fade, darkness)`), что на самом деле картинка ПК с `gr_paletterendering Off`. Проверка: DSZ1 (MAP07) ПК palette Off против HW — MAD 5.3, а против ПК по умолчанию — 14.1; признак палитровой картинки — 100 % пикселей на сетке RGB565 (`tools/ps2/hfgrid.py`).
(Побочное открытие: часть ПК-эталонов старта (карты 25/30/50/70) была снята llvmpipe без шейдеров — не на сетке 565; `pcshot.py` теперь проверяет сетку и повторяет снимок.)

Реализация (GS умеет таблицу цветов как CLUT):
* `src/ps2/hw/ps2_hw_pal.inc` — таблицы света движка (32 x 256 RGBA) хранятся как палитровые индексы (8 КБ на таблицу, `lt_store`), `out_pal()` = экранная палитра (flash / 565) вместо палитры текстур во всех CLUT палитровых текстур;
* полигон с `LightTableId` и PSMT8-текстурой режется по глубине там, где меняется строка таблицы (лестница `ps2_hw_light.inc`; классы 0 и 1 — одна строка: `lightp_t.pal`), каждый кусок рисуется с CLUT своей строки (`CK_LIGHT`, ключ = таблица + поколение + строка);
  fog GS для таких полигонов не используется; быстрые пути (`lit_fast_poly`) меняют CLUT при смене строки; путь VU1 для таких планов выключен (`P.vuok`);
* `hw_SetScreenPalette` — вспышки (урон, предметы, вода) применяются при построении CLUT, постобработка не нужна; финальный экран — сам кадр (`GENERIC2`), копия `GENERIC3` не делается; цветовой UI-fade (`SHADER_UI_COLORMAP_FADE`) на PS2 — полупрозрачный чёрный квад (путь без палитры);
* прямые цвета (CT32), плоские цвета, fog-блоки, спрайты с частичной прозрачностью остаются на уравнениях GLSL; текстуры карты остаются P_8 + chroma key (`textureformat` не переключается на AP_88), оптимизации HT (zero-copy, LOD, общий образ) работают;
* `clut_get`: прямое индексирование по хешу ключа перед линейным поиском по 124 слотам (PS2-HW-72) — запрос CLUT на каждую смену строки.

## 3. Стадия 3: валидатор потока GIF (PS2-HW-74) — ошибки «настоящего GS», которые PCSX2 прощает

Настоящего GS в контейнере нет, поэтому каждый буфер кольца GIF проверяется «после факта» на соответствие документированным правилам GS (`src/ps2/hw/ps2_hw_val.inc`, включается `-hwdbg 536870912`; разбор идёт в `pk_flush`, перед `SyncDCache` и постановкой буфера в DMA; состояние разбора переносится между буферами).
Что проверяется:
* цепочка DMA: тег CNT/REF/REFE/END, адрес REF выровнен по 16 Б (DMAC молча отбрасывает младшие биты — данные читаются «не оттуда»), QWC != 0, адрес внутри 32 МБ;
* теги GIF и регистры: PACKED/REGLIST/IMAGE, nreg/nloop, неизвестные адреса регистров, запись в регистры контекста 2 (драйвер рисует в контексте 1);
* поля регистров не вылезают за разрядность: TEX0 (TW,TH <= 10, формат, нечётный TBW для 8-битных форматов, CLD, CSA, CBP), CLAMP (биты выше MAXV, область региона вне текстуры, проверка при использовании пары TEX0+CLAMP), SCISSOR (<= 2047, зарезервированные биты, внутри кадра), FRAME/ZBUF (FBW <= 63, зарезервированные биты), ALPHA (селектор 3), TEST (ZTE = 0), BITBLTBUF/TRXPOS/TRXREG;
* передача IMAGE: число квадслов = ceil(RRW*RRH*бит/128), во время передачи не приходят другие пакеты, назначение внутри 4 МБ VRAM — по точной таблице блоков страниц GS (CT32/PSMT8/CT16/CT16S/PSMT4), а не по страницам;
* кэш текстур реального GS (в PCSX2 его нет): текстура, пересекающаяся с областью, в которую писали (передача, копия local->local, рисование в кадр) после последнего TEXFLUSH — ошибка `TEXFLUSH`;
* вершины: окно XY +-2000 px от XYOFFSET (охранная полоса драйвера 1900), Z не больше формата Z-буфера, поля XY/RGBA/UV не переполнены, Q > 0, S/T конечны, число вершин кратно примитиву при смене PRIM, размах текстурных координат одного примитива <= 4100 тексель (UV_EXTENT драйвера = 4096).

Проверка самого валидатора: `tools/ps2/hf_valtest.c` (хост, `gcc`): 4 чистых потока (состояние + загрузка текстуры + PACKED-веер + спрайт; REGLIST-веер как `emit_reglist_fan`; экранная текстура 320x200 вплотную к концу VRAM; загрузка 64x64 PSMT8 вплотную к концу VRAM) дают 0 ошибок, 27 внесённых ошибок (по классам, включая загрузку на блок дальше конца VRAM и REF с невыровненным адресом) все пойманы в своём классе.

Ложные срабатывания первых версий (оставлены в отчёте, потому что показывают, на что опирается драйвер): (i) экранная текстура 320x200 CT32 лежит по TBP0 = 15264, то есть ровно до конца VRAM (15264 + 35 страниц * 32 блока = 16384); (ii) загрузка 64x64 PSMT8 по DBP = 16368 занимает блоки 16368..16383, тоже вплотную. Оба случая верны с точностью до блока (проверено таблицей блоков GS), но запаса нет: любой сдвиг пула на блок даст заворот адреса VRAM на настоящем GS (охрана `vram_guard`, PS2-HW-73, этот случай ловит).

Статический аудит DMA и кэша (чтение кода, не измерение):
* источники DMA GIF — три: (a) кольцо `memalign(64)` (`pk_flush`: `SyncDCache(b, b + wr)` перед постановкой), (b) данные текстур движка по ссылке REF (`tex_upload_ref`: `SyncDCache(data, data + W2*H2)` на точный диапазон, адрес выровнен, хвост квадслова дописывается нулями в кольцо), (c) приём DMA из GS в буфер `memalign(64)` (`PS2HWD_ReadVram`: `SyncDCache` до и после передачи, как требует приём); путь VU1 по умолчанию выключен;
* PCSX2 не эмулирует кэш данных EE, поэтому пропущенный `SyncDCache` в нём не виден: перебор всех мест `pk_ref`/ссылок показал единственный вызов (текстуры), с `SyncDCache` в той же функции;
* TEXFLUSH стоит после каждой загрузки текстуры/CLUT и экранной копии (валидатор подтверждает на 15 картах: 0 нарушений на 44 тыс. – 1.2 млн записей TEX0 за прогон).

Чего валидатор не видит: путь VU1 (`-hwdbg 0x4000000`, пакеты строит микропрограмма), реальные такты GS, фактическую очистку кэша текстур железом.

## 4. Конформность текстур (PS2-HW-69): `-hwtextest`

Каждая текстура карты и каждый плоский пол (`levelflats`) рисуются 1:1 и с повтором, кадр читается из VRAM и сравнивается с текселями движка (с учётом экранной палитры в палитровом режиме). Прогон с финальным драйвером (`tools/ps2/hftt.py`, валидатор включён):

Карта 16 в этом режиме не вмещается в зону на 32 МБ (OOM, см. раздел 7). Децимированные текстуры (256x2048 RVZ, THZ) хранятся с шагом 2 по строкам (`TTDECIM`); потеря резкости по вертикали — известное отличие PS2-HW-20.
Итог кандидатов из задания (по измерению): ST/UV — ни одного выхода за предел 4096 тексель на примитив; точность Q — вершины Q > 0, S/T конечны во всех прогонах; повторы NPOT — 0 ошибок B; z-fighting/near-clip — на панелях карт 1..70 не видно (MAD <= 3.5); устаревшая текстура после вытеснения — 0 нарушений TEXFLUSH и 0 ошибок TT после `HWR_ClearAllTextures()` перед каждой текстурой; неверные TBW/CLUT — TBW всегда чётный для 8-бит (0 ошибок), 0 ошибок TT. Причина «глюков текстур на стенах и полах», найденная измерением, одна: освещение GLSL вместо палитрового (раздел 2); геометрически и по текселям текстуры в VRAM совпадают с движком.
