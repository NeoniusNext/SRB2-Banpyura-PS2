## 1. Рекуперируемая нехватка памяти вместо I_Error (PS2-170)

**Идея.** Кадр рисуется под «стражем» (`Z_GUARD_TRY`, `z_zone.h`): если `Z_Malloc` не нашёл места после всех вытеснений и хуков, он не вызывает `I_Error`, а прыгает (`longjmp`) обратно в страж. Дальше:
* **Hardware:** недорисованный кадр сбрасывается (`PS2HWD_Abort`: остановка DMA 1/2, `GIF_CTRL.RST`, сброс VIF1, очередь ring, состояние кадра), `currently_batching`/батчи/интерполяторы/wipe/`viewwindowy` приводятся в порядок, дальше обычное переключение рендерера как в Options → Video (`SCR_SetMode` → `HWR_ClearAllTextures`, `HWR_Shutdown`, драйвер выключается, GS берёт software), `PU_HWRPLANE` освобождается; карта запоминается как «не влезает в HW». **Обратно:** в конце загрузки следующего уровня, если пользователь выбрал Hardware (`-renderer Hardware` или cvar), карта не в списке и сбоев < 6, `setrenderneeded = render_opengl` — следующий `D_Display` (под тем же стражем) возвращает HW. Любой сбой при возврате снова даёт software.
* **Software:** кадр бросается, `Z_EmergencyFree` (весь кэш любого возраста, хуки звука/HW, соседние дыры сливаются), кадр рисуется заново; три провала за 12 кадров подряд — прежний отчёт `OOM:` и ошибка.
* Тот же страж ловит `hw_failure` драйвера («PS2 HW resource failure», тупик DMA): раньше `I_Error`.
* Во время вызова Lua (`lua_getstack(gL, 0, …)`, `PS2Lua_InCall`) прыжка нет (состояние Lua нельзя бросить на полпути) — как раньше.
* Уровень: `HWR_LoadLevel` вызывается из `PS2HWFB_BuildLevel` под стражем (то же падение → software с первого кадра уровня).

Файлы: `src/z_zone.c/.h` (`zguard_t`, `Z_OutOfMemory` → `longjmp`, `Z_AddReclaimHook`, `Z_EmergencyFree`, внедрение отказов `-zoomtest`), `src/ps2/ps2_hwfb.c/.h` (политика), `src/ps2/hw/ps2_hwd.c` (`PS2HWD_Abort`), точечно `d_main.c` (`PS2HWFB_Display(D_Display)`), `p_setup.c` (`PS2HWFB_BuildLevel`, `PS2HWFB_LevelLoaded`), `i_video.c` (`Impl_HWFailure`), `lua_script.c`/`lua_stub.c` (`PS2Lua_InCall`), `ps2_spill.c` (`PS2Spill_Reset`).

**Проверка запуском (ELF `build/elf-n1.ELF`, коммит 5965915):**
* `-hwfbtest 60 -zchain 02` (имитация сбоя внутри кадра 60 в HW): `HARDWARE -> SOFTWARE`, MAP01 дошла до 200 кадров, MAP02 — «trying the hardware renderer again», 200 кадров HW (`build/runs/fbt1`).
* `-zoomtest 60,90 -zchain 02,03` (настоящий отказ `Z_Malloc`: кадр 64 `12 B PU_HWRPATCHINFO` в MAP01; кадр 200 `52 B PU_HWRPLANE` при построении плоскостей MAP02 после возврата): оба раза возврат в software, MAP03 снова в HW (`build/runs/fbt2`).

## 2. Память: что дало место (PS2-171, PS2-172)

Измерено на ELF `build/elf-n2.ELF` (коммит 1aba2dc), `chain_sweep.py` по картам `01..10, 11, M3` (программный рендерер), 35 кадров на карту:

| карта | свободно до (`sw-base`) | свободно после (`sw-n2m11`) | комментарий |
|---|---:|---:|---|
| MAP10 | 1 633 952 | **2 471 312** | |
| **MAP11 (CEZ2) в цепочке** | **OOM `PU_RENDERWORK` 65 536 Б** | **280 672** (самый большой блок 170 КБ) | проходит; из чистой загрузки 175 520 → см. раздел 5 |
| MAPM3 | 422 496 | **5 161 712** | `frontscale` предыдущих карт освобождаются |

* **PS2-171: рабочие массивы HW-драйвера и `linkdrawlist` из `.bss` в зону.** `ovq` (64 КБ), `cutbuf` (93 КБ), `plan_info` (36 КБ), `blk_owner` (32 КБ) теперь блоки зоны, которые берутся в `PS2HWD_Init` (`hwbig_alloc`, 64-байтное выравнивание) и отдаются в `PS2HWD_Shutdown`; в объявлениях — указатель и `#define name (*name_p)`, код использования не менялся; `linkdrawlist` (172 КБ, `hw_main.c`) растёт по требованию (64 → 2048 записей, `Z_TryReallocAlign`) и освобождается в `HWR_Shutdown`; `band` (32 КБ) и `noup_data` (64 КБ, только измерительный режим) — `memalign` при первом использовании. **`.bss` 2 490 368 → 1 989 796 Б (−500 КБ), арена 23 801 856 → 24 293 376 Б.** Программному рендереру они не нужны вообще; HW берёт их при старте (нет места — драйвер не стартует и игра остаётся в software, как при любой другой ошибке старта).
* **PS2-172: `R_ReleaseDrawSegScales`** (`r_segs.c`, вызов из `P_LoadLevel` после `Z_FlushCache`): массивы `frontscale` в слотах drawseg растут до самого тяжёлого вида сессии (874 КБ после FOF-карт: 683 блока по 1.28 КБ) и никогда не отдавались; теперь новый уровень начинается без них (`maxdrawsegs` вынесен из `R_StoreWallRange` на уровень файла). Побитность software не нарушена (массив — рабочий, после выделения заново заполняется кадром).
* Не сработавшее/не сделанное (честно): `-Os` для холодных единиц — уже применён прежними агентами (`unit_flags`: `m_menu`, `deh_*`, Lua... дают 0 разницы), глобальный `-Os` экономит 377 КБ текста, но замедляет `p_user/p_mobj/r_draw/ps2_hwd` (горячий код, область CORE/VU); поля `pv1/pv2/flength` в `seg_t` при `HWRENDER` стоят software 12 Б на сегмент (595 КБ на MAP11), убрать их можно только правкой `hw_main.c/hw_bsp.c` (GEOM) — вынесено в раздел «не закрыто».

## 3. Нехватка памяти при загрузке уровня (PS2-170/173)

* `G_DoLoadLevel` → `PS2HWFB_LoadLevel`: загрузка уровня под стражем (не в сетевой игре). Нехватка памяти: сообщение `Not enough memory to load map MAPxx: N bytes (TAG). Back to the title screen.`, возврат на титул тем же путём, что и при любой невозможной карте (`Command_ExitGame_f`), HW при этом уходит в software.
* **Системный тест: инъекция отказа на N-м выделении под стражем** (`-zoomnth N -zoomafter 60`, `tools/ps2/oom_inject.py`: во время `map MAP02 -force` N-е выделение (любой тег) отказывает; затем через 400 кадров `map MAP01 -force` обязан загрузиться и пройти до `-zquitall`). 19 точек (1…6765): первый заход нашёл ровно одно место с висячим указателем — `R_ReInitColormaps`: `Z_Free(fadecolormap); R_CreateFadeColormaps();` (после отказа `fadecolormap` указывал на освобождённую память, следующая загрузка освобождала её дважды: `ZA_Free: bad or double-freed block`; исправлено `fadecolormap = NULL`, PS2-173); раньше был исправлен тот же шаблон в `LoadPalette` (`v_video.c`: новые таблицы выделяются до освобождения старых). Остальные 18 точек проходят. Причина класса: код вида `Z_Free(x); x = Z_Malloc(...)` без обнуления; прыжок из `Z_Malloc` оставляет `x` висячим.
* Страж не прыгает при работающем Lua-хуке и в сетевой игре для не-HW тегов (`Z_GuardMayJump`): `NetUpdate` живёт внутри кадра, сетевое состояние нельзя бросать на полпути.
