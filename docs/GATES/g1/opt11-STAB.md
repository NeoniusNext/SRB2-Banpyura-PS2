## 1. Рекуперируемая нехватка памяти вместо I_Error (PS2-170)

**Идея.** Кадр рисуется под «стражем» (`Z_GUARD_TRY`, `z_zone.h`): если `Z_Malloc` не нашёл места после всех вытеснений и хуков, он не вызывает `I_Error`, а прыгает (`longjmp`) обратно в страж. Дальше:
* **Hardware:** недорисованный кадр сбрасывается (`PS2HWD_Abort`: остановка DMA 1/2, `GIF_CTRL.RST`, сброс VIF1, очередь ring, состояние кадра), `currently_batching`/батчи/интерполяторы/wipe/`viewwindowy` приводятся в порядок, дальше обычное переключение рендерера как в Options → Video (`SCR_SetMode` → `HWR_ClearAllTextures`, `HWR_Shutdown`, драйвер выключается, GS берёт software), `PU_HWRPLANE` освобождается; карта запоминается как «не влезает в HW». **Обратно:** в конце загрузки следующего уровня, если пользователь выбрал Hardware (`-renderer Hardware` или cvar), карта не в списке и сбоев < 6, `setrenderneeded = render_opengl` — следующий `D_Display` (под тем же стражем) возвращает HW. Любой сбой при возврате снова даёт software.
* **Software:** кадр бросается, `Z_EmergencyFree` (весь кэш любого возраста, хуки звука/HW, соседние дыры сливаются), кадр рисуется заново; три провала за 12 кадров подряд — прежний отчёт `OOM:` и ошибка.
* Тот же страж ловит `hw_failure` драйвера («PS2 HW resource failure», тупик DMA): раньше `I_Error`.
* Во время вызова Lua (`lua_getstack(gL, 0, …)`, `PS2Lua_InCall`) прыжка нет (состояние Lua нельзя бросить на полпути) — как раньше.
* Уровень: `HWR_LoadLevel` вызывается из `PS2HWFB_BuildLevel` под стражем (то же падение → software с первого кадра уровня).

Файлы: `src/z_zone.c/.h` (`zguard_t`, `Z_OutOfMemory` → `longjmp`, `Z_AddReclaimHook`, `Z_EmergencyFree`, внедрение отказов `-zoomtest`), `src/ps2/ps2_hwfb.c/.h` (политика), `src/ps2/hw/ps2_hwd.c` (`PS2HWD_Abort`), точечно `d_main.c` (`PS2HWFB_Display(D_Display)`), `p_setup.c` (`PS2HWFB_BuildLevel`, `PS2HWFB_LevelLoaded`), `i_video.c` (`Impl_HWFailure`), `lua_script.c`/`lua_stub.c` (`PS2Lua_InCall`), `ps2_spill.c` (`PS2Spill_Reset`).

**Проверка запуском (ELF `build/elf-n1.ELF`, коммит 5965915):**
* `-hwfbtest 60 -zchain 02` (имитация сбоя внутри кадра 60 в HW): `HARDWARE -> SOFTWARE`, MAP01 дошла до 200 кадров, MAP02 — «trying the hardware renderer again», 200 кадров HW (`build/runs/fbt1`).
* `-zoomtest 60,90 -zchain 02,03` (настоящий отказ `Z_Malloc`: кадр 64 `12 B PU_HWRPATCHINFO` в MAP01; кадр 200 `52 B PU_HWRPLANE` при построении плоскостей MAP02 после возврата): оба раза возврат в software, MAP03 снова в HW (`build/runs/fbt2`).

## 2. Память: что дало место (PS2-171, PS2-172)

Измерено на ELF `build/elf-n2.ELF` (коммит 1aba2dc), `chain_sweep.py` по картам `01..10, 11, M3` (программный рендерер), 35 кадров на карту:

| карта | свободно до (`sw-base`) | свободно после (`sw-n2m11`) | комментарий |
|---|---:|---:|---|
| MAP10 | 1 633 952 | **2 471 312** | |
| **MAP11 (CEZ2) в цепочке** | **OOM `PU_RENDERWORK` 65 536 Б** | **280 672** (самый большой блок 170 КБ) | проходит; из чистой загрузки 175 520 → см. раздел 5 |
| MAPM3 | 422 496 | **5 161 712** | `frontscale` предыдущих карт освобождаются |

* **PS2-171: рабочие массивы HW-драйвера и `linkdrawlist` из `.bss` в зону.** `ovq` (64 КБ), `cutbuf` (93 КБ), `plan_info` (36 КБ), `blk_owner` (32 КБ) теперь блоки зоны, которые берутся в `PS2HWD_Init` (`hwbig_alloc`, 64-байтное выравнивание) и отдаются в `PS2HWD_Shutdown`; в объявлениях — указатель и `#define name (*name_p)`, код использования не менялся; `linkdrawlist` (172 КБ, `hw_main.c`) растёт по требованию (64 → 2048 записей, `Z_TryReallocAlign`) и освобождается в `HWR_Shutdown`; `band` (32 КБ) и `noup_data` (64 КБ, только измерительный режим) — `memalign` при первом использовании. **`.bss` 2 490 368 → 1 989 796 Б (−500 КБ), арена 23 801 856 → 24 293 376 Б.** Программному рендереру они не нужны вообще; HW берёт их при старте (нет места — драйвер не стартует и игра остаётся в software, как при любой другой ошибке старта).
* **PS2-172: `R_ReleaseDrawSegScales`** (`r_segs.c`, вызов из `P_LoadLevel` после `Z_FlushCache`): массивы `frontscale` в слотах drawseg растут до самого тяжёлого вида сессии (874 КБ после FOF-карт: 683 блока по 1.28 КБ) и никогда не отдавались; теперь новый уровень начинается без них (`maxdrawsegs` вынесен из `R_StoreWallRange` на уровень файла). Побитность software не нарушена (массив — рабочий, после выделения заново заполняется кадром).
* Не сработавшее/не сделанное (честно): `-Os` для холодных единиц — уже применён прежними агентами (`unit_flags`: `m_menu`, `deh_*`, Lua... дают 0 разницы), глобальный `-Os` экономит 377 КБ текста, но замедляет `p_user/p_mobj/r_draw/ps2_hwd` (горячий код, область CORE/VU); поля `pv1/pv2/flength` в `seg_t` при `HWRENDER` стоят software 12 Б на сегмент (595 КБ на MAP11), убрать их можно только правкой `hw_main.c/hw_bsp.c` (GEOM) — вынесено в раздел «не закрыто».

## 3. Нехватка памяти при загрузке уровня (PS2-170/173)

* `G_DoLoadLevel` → `PS2HWFB_LoadLevel`: загрузка уровня под стражем (не в сетевой игре). Нехватка памяти: сообщение `Not enough memory to load map MAPxx: N bytes (TAG). Back to the title screen.`, возврат на титул тем же путём, что и при любой невозможной карте (`Command_ExitGame_f`), HW при этом уходит в software.
* **Системный тест: инъекция отказа на N-м выделении под стражем** (`-zoomnth N -zoomafter 60`, `tools/ps2/oom_inject.py`: во время `map MAP02 -force` N-е выделение (любой тег) отказывает; затем через 400 кадров `map MAP01 -force` обязан загрузиться и пройти до `-zquitall`). 19 точек (1…6765): первый заход нашёл ровно одно место с висячим указателем — `R_ReInitColormaps`: `Z_Free(fadecolormap); R_CreateFadeColormaps();` (после отказа `fadecolormap` указывал на освобождённую память, следующая загрузка освобождала её дважды: `ZA_Free: bad or double-freed block`; исправлено `fadecolormap = NULL`, PS2-173); раньше был исправлен тот же шаблон в `LoadPalette` (`v_video.c`: новые таблицы выделяются до освобождения старых). Остальные 18 точек проходят. Причина класса: код вида `Z_Free(x); x = Z_Malloc(...)` без обнуления; прыжок из `Z_Malloc` оставляет `x` висячим.
* Страж не прыгает при работающем Lua-хуке и в сетевой игре для не-HW тегов (`Z_GuardMayJump`): `NetUpdate` живёт внутри кадра, сетевое состояние нельзя бросать на полпути.

Кадровая инъекция в software (9 точек) — 9/9; HW-уровень N=40, 300 — ok (остальные точки — в `stab_run.sh inject`).

### 6.1 Длинная сессия: утечка и ползучая статика (найдено цепочкой из 80 карт, ELF n12 → n16)

`chain_sweep.py` (одна сессия: 65–80 разных карт подряд, `-zck -zmap -zholes`) на n12 **не загружала MAPM3**: `OOM 2729194 B PU_LEVEL`, свободно 9.8 МБ, самый большой блок 2.72 МБ (не хватало 7 КБ); повтор загрузки с `Z_EmergencyFree` тоже не помогал. Разбор по шагам:

1. **Динамика.** `static` (PU_STATIC) на `level-free-after`: 4.0 МБ (первая карта) → 7.13 МБ к 60-й карте, самый большой блок после выгрузки уровня 19.5 → 9.0 МБ. Скачки привязаны к картам (MAP71 +0.50 МБ, MAPF1 +0.24, MAPF2 +0.84, MAPFB +0.26 …).
2. **Утечка (PS2-178).** После MAPFB в арене остаётся блок `PU_RENDERWORK` 541 728 Б (`[zblk]` — новый дамп больших выживших блоков при `-zmap`): воспроизводится без цепочки — `opt_run.py … --map MAPFB -- -zck -zmap -zquit 35 -zchain 01` (ELF n13: после `MAP01` блок на месте; n14: нет). Адреса вызовов (`-zcaller`, `addr_sym.py` по `nm`): два подряд `R_TryReadLump` одного и того же PNG-патча в `R_GenerateTexture`: проба «это PNG?» читает сырую лump в `pdata`, а ветка составной (non-FLAT) текстуры при незакешированном патче читала её второй раз и затирала указатель — первая копия (541 712 Б) оставалась навсегда (RENDERWORK не сбрасывается ни `Z_FlushCache`, ни `Z_FreeTags(PU_LEVEL)`). Исправление: второе чтение только если `pdata` пуст (`r_textures.c`). Блок стоял в середине арены и разрезал дыру 12 МБ → 9.0 + 0.54 + 2.7.
3. **Ползучая статика (PS2-179).** Остальное — рабочие массивы, растущие до самого тяжёлого вида сессии и никогда не отдаваемые: массив `drawsegs` (128 записей, рост ×1.5, ≈ 0.6 МБ после MAPF2; шесть перевыделений за карту) и плоскости `visplane` (по 2 КБ, сотни на FOF-картах, переработка по свободному списку). `R_ReleaseDrawSegScales` теперь отдаёт ещё и сам массив, `R_ReleaseVisplanes` (новая) — все плоскости; вызываются из `P_LoadLevel` после `Z_FlushCache` (кадр не рисуется), в начале следующего уровня массивы создаются так же, как при старте игры. **Результат (ELF n15, та же цепочка из 80 карт, `-zck`): `static` 4.0 → 4.66 МБ к 79-й карте (было 7.23), самый большой блок после выгрузки уровня 13.6 МБ (было 9.0/12.2), MAPM3 грузится; цепочка 83 из 84 за 573 с (было 1163 с).** Точность software: те же четыре демо побитно (см. раздел 7).
4. **MAPMG в software (ELF n12/n15/n16, и холодный старт): `OOM 4194304 B PU_RENDERWORK`.** Это не новая ошибка (так же на HEAD в начале сессии, `sw-base`; opt10-S: «83 из 84, не проходит MAPMG»). Причина: текстура 2048×2048 (`CLUDSSSS`), которую карта использует как пол, требует составной текстуры (4.2 МБ) и независимого плоского образа (4.2 МБ) одновременно; при уровне 6.5 МБ + статике 4.1 МБ + патчах 0.5 МБ на кэш остаётся 13 МБ и сплошного блока в 4 МБ на кадре 2 нет (`free 10 МБ, largest 3.65 МБ` после `Z_EmergencyFree`). HW эту текстуру читает полосами из лумпа и проходит. **Что сделано:** кадр software, который не удался три раза подряд, в локальной игре больше не заканчивает программу `I_Error`: `ERROR: Not enough memory to draw map MAPMG: 4194304 bytes (PU_RENDERWORK). Back to the title screen.`, `exitgame`, дальше титул и меню (проверено: `-warp MAPMG -zquitall 900` → `done=True`, титульная музыка; в сети — прежний `I_Error`). **Не сделано:** сама карта в software не открывается; нужен либо уменьшенный образ плоской копии (как «большие текстуры в HW», PS2-140), либо сборка плоской копии полосами без составной (≈150 строк в `r_textures.c`/`r_picformats.c`, область CORE/HT).

### 8.2 Зависание GS на MAPMD/MAPME: корень найден и устранён (PS2-HW-144, ELF `build/out-dbg`, коммиты 2c885d0, 5d48a52)
* **Метод.** Раздел 7.1 заканчивался «точное место обрыва не найдено». Сторож теперь печатает (`wd_chain_dump`, `ps2_hw_gs.inc`): `VIF1_CODE/NUM/ERR/MARK`, `VPU_STAT`, `D_STAT`, последние 16 ссылок `pk_ref` (буфер, смещение, адрес, qwc) и 32 слота цепочки DMA вокруг `D1_TADR` (две 64-битные половины тега: сам тег и два VIF-кода).
* **Что показал дамп (MAPMD, кадр 57):** `VIF1 CODE=11000000` (FLUSH), `NUM=0`, `VPU_STAT=0` (VU1 свободен), `GIF_STAT=0xa00` (APATH=2, FIFO пуст), `D1 TADR` указывает на тег `CNT qwc=1582, VIF-коды FLUSH + DIRECT(1582)`; перед ним `REF qwc=1806 (addr e1b480), DIRECT(1806)`, а заголовок загрузки: `GIF tag NLOOP=4 (A+D)`, `BITBLTBUF`, `TRXPOS`, `TRXREG = 170 x 170`, `TRXDIR`, **`GIF IMAGE tag NLOOP=0x70f = 1807, EOP=1`**. 170 × 170 = 28 900 Б = 1806 квадслов + **4 байта**: в `upload_ref` хвост («частичный последний квадслов», `bytes & 15`) отправлялся `pk_alloc(1)` — то есть **в следующий запуск цепочки, чей тег начинается с VIF-кода FLUSH**. FLUSH ждёт конца пакета GIF по PATH2, а пакет IMAGE не может закончиться, пока не придёт этот последний квадслов, лежащий за самим FLUSH: VIF1 и GIF ждут друг друга навсегда (раньше 2 с × 6 заморозок, потом 2 с + отключение zero copy).
* **Почему только MAPMD/MAPME и только zero copy:** хвост существует лишь у текстур, у которых `W2 × nr` не кратно 16 (здесь 170 × 170; обычные текстуры — степени двойки, ширина кратна 16); копирующий путь кладёт хвост в то же прогон-тело, что и заголовок (без FLUSH между ними).
* **Исправление (`ps2_hw_gs.inc`: `pk_ref_tail`, `ps2_hw_tex.inc`: `upload_ref`):** хвост — отдельный запуск с VIF-кодами `NOP + DIRECT(1)` (без FLUSH), следующий запуск обычный; перед заголовком `upload_ref` резервирует ещё два слота, чтобы заголовок, ссылка и хвост лежали в одном буфере. Проверка: `MAPMD` и `MAPME` на холодном старте, 120 / 75 кадров — **`WATCHDOG` 0 раз** (было: один таймаут 2 с + `zero-copy off`), снимок MAPMD правильный (`build/runs/tail-MAPMD/vidshot-320x200-l75.ppm`: Sonic, ступенчатый постамент, рамка HUD).
* **Страховка от повторения: «chain lint»** (`ps2_hw_val.inc`, `-hwdbg 536870912` при VU1, где прежний валидатор выключен): DIRECT-запуски цепочки разбираются как GIF, а тег с VIF-кодом FLUSH при открытом пакете (остаток данных или последний тег с EOP=0) — ошибка `HWVAL LINT`. Проверено: исправленная сборка на MAPMD — `direct runs=7425 flushes=16205 errors=0`; тест `-hwoldtail` (прежнее поведение хвоста) — **2 ошибки lint на индексе 124 (тот же, что в дампе) и тот же `WATCHDOG`**. Этап `lint` в `stab_run.sh` (MAPMD, MAPME, MAP01, MAP23, MAP11 с `-hwdbg 536870912`). Правка в чужом файле: `ps2_hw_gs.inc`, `ps2_hw_tex.inc`, `ps2_hw_val.inc`, `ps2_hwd.c` (VU-агент; все точечно, в начале файлов указаны комментарии OPT11-STAB).

### 8.4 MAPMG в software: карта открывается (PS2-180; коммит bb4bc1f)
* **Причина (разобрана по карте арены `-zmap` в момент отказа, ELF `build/elf-m10.ELF`).** Текстура `CLUDSSSS` 2048×2048 — это четыре сырых патча `CWLAD1..4` 1024×1024 (`TEXTURES.psz`), используемая как пол. Обычный путь строит составную текстуру (4.2 МБ с маской) и затем плоскую копию (ещё 4.2 МБ) — оба блока одновременно, и только что использованная составная защищена от вытеснения. Но и один блок в 4.2 МБ не находился: на кадре 4 свободно 9.9 МБ, самый большой блок 2.7 МБ — свободное место (0.96 / 2.73 / 2.62 / 1.0 / 2.5 МБ) разрезано пятью блоками `PU_CACHE` по 64 КБ (плоские текстуры 256×256, нужные кадру), стоящими посреди 10-МБ области между данными уровня (0..6.3 МБ) и статикой. Сброс всех кэшей (`Z_EmergencyFree`) и повтор кадра рисует те же 64-КБ плоскости раньше, чем доходит до большого пола, и разрез возвращается.
* **Исправление.** (1) `R_StreamTextureToFlat` (`r_textures.c`): плоская копия текстуры из сырых патчей **без составной**: колонки патчей читаются из пака окнами по 32 КБ (`W_ReadLumpHeaderPwad` с смещением), посты пишутся в плоскую копию «как есть», непокрытое — `TRANSPARENTPIXEL`; ничего, кроме самой копии (4.2 МБ) и окна, не нужно. Только для простых патчей (сырой Doom-патч, не PNG и не «приготовленный», стиль copy, без отражений); всё остальное идёт прежним путём. (2) Такая плоская копия (текстура ≥ 1 МиБ) получает тег `PU_LEVEL` на время уровня (блок кэша этого размера после фрагментации заново не построить) и строится **в начале уровня**, пока в арене ещё есть дыра: `R_LoadBigFlats` из `P_PrecacheLevelFlats` (только software, не демо).
* **Проверка запуском.** `--map MAPMG -vidshot l40 -zquit 60`: `FLATSTREAM texture 3859 PLHD5 (1024x1024)`, `FLATSTREAM texture 1751 CLUDSSSS (2048x2048)`, ни одного `OOM`/`no room`, карта рисуется (`build/runs/mg-sw5/vidshot-320x200-l40.ppm`: титул «Pristine Shores Zone», пол и шумящая облачная плоскость на месте). Раньше: `ERROR: Not enough memory to draw map MAPMG`, возврат на титул.
* **Самопроверка равенства маршрутов:** `-flatcheck` (для каждой текстуры, используемой как пол, считает оба маршрута и сравнивает побайтно, строка `FLATCHECK texture N NAME (WxH): equal` или `DIFFER`), `-flatstream` (все такие текстуры идут новым маршрутом). Этап `flats` в `stab_run.sh` (цепочка по всем картам с `-flatcheck`); результат — в 8.5.
* HW на MAPMG не затронут (плоскость ≥ 1 МиБ в HW по-прежнему пропускается, если места нет: `R_TryGetFlatForTexture` теперь пробует новый маршрут, но у HW на этой карте самый большой блок 0.7 МБ).
* Правки в чужих файлах: `p_setup.c` (`P_PrecacheLevelFlats`: вызов `R_LoadBigFlats`), `r_textures.c/.h` (CORE/GEOM; всё под `PS2 && PS2_PROFILE`, ПК-сборка не затронута), `z_zone.c` (`-zmap` при восстановимом отказе печатает карту арены).
