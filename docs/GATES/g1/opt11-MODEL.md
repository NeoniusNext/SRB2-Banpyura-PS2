# OPT11, агент MODEL: 3D-модели (MD3) и «трёхмерная» часть GS HW-рендерера (отчёт, дописывается по этапам)

Ветка worktree: `worktree-agent-a25646d85ed075ac1`. Реестр отличий: `PS2-HW-260..299`. Окружение — `docs/OPT11_BRIEF.md` (PCSX2 2.6.3, программный GS; ПК-эталон — OpenGL под Xvfb/llvmpipe).
Данные моделей: `/opt/dl-srb2/srb2full.zip` -> `/opt/srb2-assets-models/` (`models/`, `models.dat`; 165 MD3, 208 PNG; вне репозитория, в git не коммитятся).

## 0. Инструменты этапа (в репозитории)

* `tools/ps2/md3_stats.py` — статистика MD3 (поверхности, кадры, вершины, треугольники, байты в ОЗУ движка, размер текстуры, есть ли `_blend`).
* `tools/ps2/mdlscene.lua` — фикстура моделей: замороженные (`MF_NOTHINK`) объекты типов, чьи спрайты имеют модель в `models.dat`, сеткой перед игроком (одинаковая поза у ПК и PS2); печатает `MDLSCENE spr=.. mt=.. frame=..`.
* `SRB2_PCWADDIR` (`pcshot.py`) и `SRB2_PCEXE` (`fx_pair.py`): свой каталог ПК-движка (симлинки на pk3, свой `reference.cfg`, `models/`, `models.dat`) и свой ПК-exe. **Причина:** ПК-движок пишет все `CV_SAVE`-переменные в `<SRB2WADDIR>/reference.cfg` при выходе; опыт FX показал, что `gr_models On` в общем `/opt/srb2-assets/reference.cfg` портит эталоны остальных. Мой каталог — `/opt/srb2-assets-model-wad/`; общий файл не трогаю (проверено: `gr_models "Off"` после моих прогонов).
  Пример: `SRB2_PCWADDIR=/opt/srb2-assets-model-wad python3 tools/ps2/fx_pair.py mdl_g1 --map 1 --tick 300 --cfg 'chasecam "On"' --cmd 'gr_models~On;con_hudlines~0' --addon tools/ps2/mdlscene.lua --tree /opt/srb2-assets-models`.

## 1. Исходное состояние (проверено запуском, ELF `build/out` = HEAD `1ac175d`)

* PS2-сборка содержит libpng/zlib (`SRB2_PS2_NO=` пусто -> `-DHAVE_PNG`), поэтому `PNG_Load` из `hw_md2.c` работает на PS2 по обычным файлам рядом с ELF; бриф ошибался, что libpng нет (он не входит только в сборку «без zippng»).
* Один игрок (Sonic, MAP01, `chasecam On`, `gr_models On`, кадр k300): модель MD3 рисуется драйвером PS2 так же, как ПК-OpenGL (панель `build/fx/mdl_s1.png`; кроп спрайт/модель на ПК отличается явно, HW совпадает с моделью ПК). MAD всей картинки 2.62 (как без моделей: все отличия — привязка к палитре на ПК, 3.3 `opt11-FX.md`).
* **Сцена из 15 моделей врагов/объектов + игрок** (`mdl_g1`): MAD 3.18, **модель Sonic на PS2 пропала** (на картинке только тень), а прогон занял 8 мин 45 с вместо ~2.5 мин. В `boot.txt`: бесконечные повторы `HWD level N of F:GFS_CLD2/3/4 1024x1024 made in ~10M cycles` — **пул VRAM перегружен**: текстуры моделей приходят как `GL_TEXFMT_RGBA` и, не будучи цветами палитры (`rgba_to_indices` -> 0), идут в CT32 (256x256x4 = 256 КБ VRAM на модель); 15 моделей забирают ~3.8 МБ из 3.2 МБ пула, остальные текстуры (небо, облачные плоскости) вытесняются и пересоздаются каждый кадр.
  Вывод: без собственных 8-битных текстур моделей (P8 + CLUT, как у спрайтов, 64 КБ на 256x256) реальные модели непригодны. Это первая задача (раздел 2).
* Прочее, найденное чтением: загрузчик MD3 (`hw_md3load.c`) читает файл целиком `malloc(fileLen)` (1.0–1.6 МБ при C-куче 1.6 МБ), выделяет `indices` заново на каждом кадре цикла (утечка `numFrames-1` массивов индексов на поверхность), выделяет по 2 блока `Z_Malloc` на кадр поверхности (SONIC: 400 блоков), модели грузятся `PU_STATIC` и не освобождаются; `models.dat` при отсутствии даёт сообщение `Error while loading models.dat: I/O error`.

### 2.1 `MODELS.PAK` и загрузка (PS2-HW-260, 261)
* `tools/ps2/cook_models.py` (`--verify` читает пак назад независимым читателем): `models.dat`, `PLAYPAL` (палитра 0 из `srb2.pk3`), `<путь>.md3` в формате `SRMD`, `<путь>.png` в формате `SRMT` (8-битные индексы палитры, 255 = дыра при альфа < 128), `<путь>_blend.png` в формате `SRMB` (разреженные серии: альфа, яркость, среднее каналов). Формат пака — `docs/PACK_FORMAT.md` (имена лампов = пути из `models.dat`). Описание форматов — в заголовке скрипта.
  Результат: 352 лампа, 20.2 МБ -> **4.57 МБ** на диске (LZ4 по 64 КиБ), 153 модели из 165 (у 30 строк `models.dat` в раздаче нет файлов: мониторы, ящики), 143 текстуры, 54 карты цвета; готовится за 2.4 с.
  Индексы текстур — то, что делает с текселем шейдер палитрового рендера ПК (`gr_paletterendering On`): ячейка `floor(v/255*63+0.5)` на канал, цвет `4*ячейка`, ближайший цвет палитры по `NearestPaletteColor` (первый из равных; индекс 255 для непрозрачных не берётся).
* `src/ps2/ps2_models.c` (+ `.h`): модель — **один блок зоны** (структуры `model_t/mesh_t/tinyframe_t` + лампа пака, массивы используются на месте), загрузка `Z_TryMallocAlign` (никаких `I_Error`: нехватка памяти даёт `why = 1`, модель остаётся спрайтом, повтор через ~140 кадров), хук возврата памяти зоне `Z_AddReclaimHook` (освобождает не использованные в этом кадре модели, самую давнюю первой), бюджет живых моделей 5 МиБ (`-hwmodelbudget КиБ`), запас арены после загрузки 1.25 МиБ (`-hwmodelres КиБ`), проверка границ и индексов лампы (повреждённый пак -> `why = 2`, не падение). `md2_t` получил `ps2_retry`, `ps2_pal`.
  Движок (`hw_md2.c`, только `PS2_PROFILE`): `models.dat` из пака, иначе из файлов рядом с ELF; **нет `models.dat` — тихо** (`CONS_Debug`, раньше `Error while loading models.dat: I/O error`); модель из пака, иначе обычный файл (старый `LoadModel`); текстура из пака (8 бит, `TF_CHROMAKEYED` при дырах), иначе PNG/PCX с квантованием тем же правилом; смена палитры карты пересоздаёт текстуры (хеш палитры, перенумерация индексов пака); `HWR_GrowSpriteTables` и перераспределение `md2_playermodels` сначала возвращают все модели (указатели-владельцы).
* Найдено и исправлено (общий код, только PS2): `LoadModelSprite2` выделял **две таблицы по 1.05 МБ на модель игрока** (`NUMPLAYERSPRITES` = 1025 при динамических лимитах) — теперь `max(free_spr2, LIMIT_NUMPLAYERSPRITES)` (по умолчанию ~55 записей, 57 КБ); загрузчик MD3 из обычного файла терял по массиву индексов на каждый кадр (утечка `numFrames - 1` на поверхность) и падал при неудачном `malloc(fileLen)`.
* Цвет скина (`HWR_CreateBlendedTexture`, PS2-HW-262, `src/hardware/hw_md2_ps2.inc`): тот же алгоритм (построчно), но в индексах палитры: база — 8-битные индексы, карта цвета читается из пака на момент смешивания и тут же освобождается, результат — 8-битные индексы (64 КБ на цвет вместо трёх 256 КБ RGBA); неизменённый тексель сохраняет индекс. Отличие: где альфа карты цвета в (0, 255), смешивается цвет палитры, в который превратили тексель, а не цвет файла (в данных игры у 4 из 54 карт такие тексели).

### 2.2 Рисование моделей и освещение (PS2-HW-263, 264)
* `ps2_hw_model.inc` переписан: вершины поверхности (≤ 2048) интерполируются **один раз на вершину** (`(short)(a + lerp*(b-a))` как драйвер ПК), треугольники идут индексами в `emit_tris` (кэш преобразованных вершин, а не по 3 преобразования на треугольник); поверхности больше 2048 вершин (BRAK 6061) — прежний путь «по углам». Рабочая область (84 КБ) выделяется из зоны при первом рисовании модели. Переключатель `-hwmodel N`: 1 — путь по углам для всех (A/B), 2 — без освещения.
* **`gr_modellighting` (PS2-HW-264)**: коэффициент вершинного шейдера ПК `min(0.75 + max(n.y, 0), 1)` (`n.y` — нормаль MD3 `z`: `(char)(n.z*127)` в пак, на ПК `GL_BYTE` -> `(2c+1)/255`, интерполяция по компонентам как у драйвера ПК) считается на вершину, GS получает цвет прохода, умноженный на коэффициент (новый формат вершины 6 в `put_vertex`: ST + RGBAQ из коэффициента + XYZF; клип/нарезка по ступеням света несут один атрибут `a[2]`). Цвет не только у проходов с `CK_LIGHT`: работает и в режиме GS-fog (палитровый рендер выключен).
  Отличие от ПК: ПК умножает тексель на коэффициент **до** поиска цвета в палитре и таблице света, GS — после (цвет из CLUT-строки умножается на коэффициент).
* Сцена `mdl_g1` (15 типов врагов и объектов + Sonic, `chasecam On`, MAP01 k300; панель `build/fx/mdl_g1b.png`), `tools/ps2/md_cmp.py` (область модели = где картинка ПК с моделями отличается от ПК без них):

## 3. Матрица остальных 3D/HW-опций (ПК-OpenGL против PS2 HW; `tools/ps2/md_matrix.sh`)
