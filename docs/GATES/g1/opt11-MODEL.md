Данные моделей: `/opt/dl-srb2/srb2full.zip` -> `/opt/srb2-assets-models/` (`models/`, `models.dat`; 165 MD3, 208 PNG; вне репозитория, в git не коммитятся).

## 0. Инструменты этапа (в репозитории)

* `tools/ps2/md3_stats.py` — статистика MD3 (поверхности, кадры, вершины, треугольники, байты в ОЗУ движка, размер текстуры, есть ли `_blend`).
* `tools/ps2/mdlscene.lua` — фикстура моделей: замороженные (`MF_NOTHINK`) объекты типов, чьи спрайты имеют модель в `models.dat`, сеткой перед игроком (одинаковая поза у ПК и PS2); печатает `MDLSCENE spr=.. mt=.. frame=..`.
* `SRB2_PCWADDIR` (`pcshot.py`) и `SRB2_PCEXE` (`fx_pair.py`): свой каталог ПК-движка (симлинки на pk3, свой `reference.cfg`, `models/`, `models.dat`) и свой ПК-exe. **Причина:** ПК-движок пишет все `CV_SAVE`-переменные в `<SRB2WADDIR>/reference.cfg` при выходе; опыт FX показал, что `gr_models On` в общем `/opt/srb2-assets/reference.cfg` портит эталоны остальных. Мой каталог — `/opt/srb2-assets-model-wad/`; общий файл не трогаю (проверено: `gr_models "Off"` после моих прогонов).
  Пример: `SRB2_PCWADDIR=/opt/srb2-assets-model-wad python3 tools/ps2/fx_pair.py mdl_g1 --map 1 --tick 300 --cfg 'chasecam "On"' --cmd 'gr_models~On;con_hudlines~0' --addon tools/ps2/mdlscene.lua --tree /opt/srb2-assets-models`.

## 1. Исходное состояние (проверено запуском, ELF `build/out` = HEAD `1ac175d`)

* PS2-сборка содержит libpng/zlib (`SRB2_PS2_NO=` пусто -> `-DHAVE_PNG`), поэтому `PNG_Load` из `hw_md2.c` работает на PS2 по обычным файлам рядом с ELF; бриф ошибался, что libpng нет (он не входит только в сборку «без zippng»).
* Один игрок (Sonic, MAP01, `chasecam On`, `gr_models On`, кадр k300): модель MD3 рисуется драйвером PS2 так же, как ПК-OpenGL (панель `build/fx/mdl_s1.png`; кроп спрайт/модель на ПК отличается явно, HW совпадает с моделью ПК). MAD всей картинки 2.62 (как без моделей: все отличия — привязка к палитре на ПК, 3.3 `opt11-FX.md`).
* **Сцена из 15 моделей врагов/объектов + игрок** (`mdl_g1`): MAD 3.18, **модель Sonic на PS2 пропала** (на картинке только тень), а прогон занял 8 мин 45 с вместо ~2.5 мин. В `boot.txt`: бесконечные повторы `HWD level N of F:GFS_CLD2/3/4 1024x1024 made in ~10M cycles` — **пул VRAM перегружен**: текстуры моделей приходят как `GL_TEXFMT_RGBA` и, не будучи цветами палитры (`rgba_to_indices` -> 0), идут в CT32 (256x256x4 = 256 КБ VRAM на модель); 15 моделей забирают ~3.8 МБ из 3.2 МБ пула, остальные текстуры (небо, облачные плоскости) вытесняются и пересоздаются каждый кадр.
  Вывод: без собственных 8-битных текстур моделей (P8 + CLUT, как у спрайтов, 64 КБ на 256x256) реальные модели непригодны. Это первая задача (раздел 2).
* Прочее, найденное чтением: загрузчик MD3 (`hw_md3load.c`) читает файл целиком `malloc(fileLen)` (1.0–1.6 МБ при C-куче 1.6 МБ), выделяет `indices` заново на каждом кадре цикла (утечка `numFrames-1` массивов индексов на поверхность), выделяет по 2 блока `Z_Malloc` на кадр поверхности (SONIC: 400 блоков), модели грузятся `PU_STATIC` и не освобождаются; `models.dat` при отсутствии даёт сообщение `Error while loading models.dat: I/O error`.
