# OPT13-IO: ввод-вывод — читатель паков, предзагрузка, повторы чтения, безопасная запись, keepalive сети, сон без будильников

Роль IO волны реализации OPT13 (2026-10-09). Worktree `/home/user/wt/io`, ветка `opt13i-io`, база — HEAD основной ветки с OPT12 (`ea3d0fa`). PCSX2 2.8.2 в Linux-контейнере, 32 МБ,
`host:` (диск Linux). Основа — `docs/research/rsys/OPT13_RSYS.md` (RS-01…RS-16, S-00…S-16), прототипы в `docs/research/rsys/patches`.
Отчёт дописывается и коммитится после каждого пункта; ниже «Сделано» — только то, что запущено, «Не проверено» — всё остальное.

**Главное ограничение, повторённое в каждой цифре ниже:** эмулятор отдаёт `host:` со скоростью диска Linux, носителей консоли в нём нет. Число и размер команд устройству (`IO R …` в журнале) —
**измерены** (то, что движок реально просит у IOP); время DVD/USB/MX4SIO/HDD — **модель** `tools/ps2/io_log_summary.py` (допущения `OPT13_RSYS.md` раздел 1: DVD 4 МБ/с seek 100/25 мс;
USB 1.1 1 МБ/с и 3 мс на команду; MX4SIO 3 МБ/с, 1 мс; HDD 15 МБ/с, seek 12 мс). Консоль не использовалась: всё, что зависит от железа, помечено «не проверено на консоли».

## 0. Стенд и команды

```

python3 tools/ps2/opt_run.py --name N --elf ELF --pak build/pak2 --out build/runs --demo DEMO_002 --no-ref -- -renderer Hardware -zquit 700   # D2 (карта 4) HW, 700 кадров; D4 = DEMO_004 (карта 50)
python3 tools/ps2/io_log_summary.py build/runs/N/pcsx2.log          # команды устройству, байты, по файлам; модель носителей; фазы: «старт» и «после Entering main game loop»

python3 tools/ps2/verify_pack.py --src /opt/srb2-assets --pak build/pak2                                          # SHA-256 каждой лампы против pk3
```

Паки: `build/pak2` (SRP2 v2, без порядка хранения, `MODELS.PAK` собран), `build/pak` (SRP2 v1). Опции движка этой роли (все в `<datadir>/ps2args` тоже): `-pkmedium dvd|usb|sd|hdd|auto`,
`-pkwin cap,minreq,ahead,gap`, `-pkioerr at[,count]`, `-iostat`, `-pkprefetch [КБ]`, `-iobench`, `-amixhang N`.

## 2. RS-01: читатель паков с окнами по носителю (`src/w_pack.c`, `w_wad.c`)

**Что сделано.** Поток пака читается ниже stdio (`read()` на дескрипторе, целые сектора 2 КБ, буферы выровнены на 64 байта) через окно на поток; политика окна — функция носителя
(`-pkmedium dvd|usb|sd|hdd|auto`, по умолчанию `auto` = по имени устройства пути: `mass:`/`usb` → usb, `mx4sio` → sd, `hdd`/`pfs` → hdd, **всё остальное (`host:`, `cdfs:`, `mc0:`, без
устройства) → dvd = окно 64 КБ**, то есть не хуже прежнего буфера stdio):

| политика | окно (буфер) | минимум чтения при промахе | упреждение | считается последовательным, если промах не дальше … впереди конца прошлого чтения |
|---|---:|---:|---:|---:|
| dvd | 64 КБ | 64 КБ | 64 КБ | любое расстояние вперёд |
| usb, sd | 32 КБ | 4 КБ | 8→16→32 КБ (удваивается с каждым промахом, продолжающим последовательный пробег) | 4 КБ |
| hdd | 64 КБ | 16 КБ | 64 КБ | 64 КБ |

Прочее: заголовок и расширение пака разбираются один раз (`W_InitFile` больше не открывает пак второй раз через `W_VerifyNMUSlumps`, не делает `fseek(SEEK_END)`); индекс читается один раз,
а не 3–20 раз; блоки LZ4 разжимаются прямо из окна (без копии в `cbuf`); чтение сырых блоков/лумп — только нужные байты; буферы stdio паков (4 × 64 КБ) исчезли (поток `_IONBF`), окна
выделяются при первом промахе (пак, который не читают после индекса, окна не получает). Ошибка раздела 3 (RS-07) вшита в тот же слой. Поведение при `-pkmedium dvd` на `host:`/`cdfs:`
= прежние 64 КБ на промах.

**Числа (PCSX2 2.8.2, `build/pak2`, команды устройству из журнала `IO R`; время — модель):**

| сценарий / фаза | было (HEAD) | dvd (по умолчанию) | usb | usb + `-pkprefetch` |
|---|---|---|---|---|
| старт до «Entering main game loop» (титул) | 130 команд / 7.50 МБ | 168 / 6.25 МБ | 299 / 2.30 МБ | 299 / 2.30 МБ |
| MAP01 software: карта + 10 кадров | 113 / 7.24 МБ | 117 / 7.50 МБ | 284 / 2.98 МБ | **113 / 2.75 МБ** |
| **D2 (карта 4) Hardware, карта + 700 кадров** | 274 / **17.46 МБ** | 282 / 17.87 МБ | 478 / **4.66 МБ** | **243 / 4.71 МБ** |
| **D4 (карта 50) Hardware, карта + 700 кадров** | 268 / **17.18 МБ** | 277 / 17.72 МБ | 493 / **4.35 МБ** | **290 / 3.77 МБ** |
| модель USB 1.1 (с): MAP01 / D2 / D4 | 7.58 / 18.25 / 17.97 | 7.85 / 18.68 / 18.54 | 3.83 / **6.05 / 5.80** | 3.08 / **5.39 / 4.61** |
| модель DVD 4 МБ/с (с): MAP01 / D2 / D4 | 7.39 / 20.06 / 21.34 | 7.95 / 20.66 / 22.25 | (политика не для DVD) | — |

Вывод по цели «трафик чтения в HW-игре D2/D4 ×3–5 меньше»: **выполнена для носителей с дорогой командой** (политика usb/sd: 17.46 → 4.66 МБ = ×3.7, 17.18 → 4.35 МБ = ×3.9; с предзагрузкой
D4 ×4.6); **для DVD байты не уменьшаются** (+2…3 %, по модели +3 % времени) — на DVD время определяет seek, и прежние 64 КБ остаются (параметр носителя нужен именно для этого). Стартовая загрузка
на `dvd` уменьшилась на 17 % по байтам (−30 % по модели DVD4 из-за индексов: SRB2.PAK 1.44 → 0.95 МБ, ZONES 328 → 14 КБ, CHARS 524 → 143 КБ, MUSIC 393 → 12 КБ).
Число команд на usb **выросло** (2×): на USB 1.1 это 3 мс на команду в модели, и выигрыш по байтам (−73 %) её перекрывает (D2 18.25 → 6.05 с), но порог выбран по допущениям:
`-iobench` на консоли даст `c` и `b` (подсказка «-pkmedium …» печатается в конце).

**Память** (`ZSTAT` после MAP01, 10 кадров, база → dvd → usb): свободная арена 7.570 → 7.611 → **7.742 МБ** (+41 / +172 КБ), байты, ушедшие из кучи libc в арену (`spillnow`), 746 → 746 → **615 КБ**;
свободное место самой кучи libc (`libcfree`) меньше на 73 КБ (371 → 298 КБ: окна и буферы выделяются при открытии пака, а не по первому чтению; арену это не затрагивает). Статика ELF: text +22 КБ, bss +6 КБ
(читатель, `ps2_safefile`, `-iobench`, предзагрузка). Четыре буфера stdio по 64 КБ у паков исчезли; окна usb/sd — 4 × 32 КБ вместо 4 × 64 КБ.

Что не доказано: **времена носителей — модель**, не замер; **политика usb/sd/hdd на консоли не проверена**, `auto` выбирает её по префиксу пути (`mass:`, `mx4sio`, `hdd`); откат — `-pkmedium dvd`
в `ps2args`.

## 3. RS-07: повтор чтения вместо `I_Error`

**Что сделано.** Любое чтение устройства читателем паков (`DevRead` в `w_pack.c`) при ошибке `read`/`lseek` или коротком чтении внутри файла повторяется: **4 попытки** (первая и три повтора;
паузы 0 / 100 / 250 / 1000 мс через `PS2_SleepUs`; на 3-й и 4-й попытке поток открывается заново `freopen` по сохранённому пути, адрес `FILE *` у движка не меняется). Блок LZ4, который не
разжимается, читается с устройства ещё раз (окно сбрасывается). После 4-го сбоя `W_ReadLumpHeaderPwad_` заканчивает игру сообщением с именем пака, лампой, смещением и errno:
`I_Error(): host:/SRB2.PAK, lump 2359 (Graphics/Rings/CURWEAP): cannot read pack data (0 of 396 bytes at offset 0)` и строка `host:/SRB2.PAK: the read of 65536 bytes at offset 8980480 failed 4 times (I/O error) - check the disc, the cable or the stick`
(до этого было `wad 0, lump 2359: cannot read pack data` без пака и без причины). Каждая повторная попытка печатает предупреждение (`... failed (I/O error), trying again (2 of 4)`). Звуковые эффекты
(`I_GetSfx`, `W_SoftReads`) при окончательной неудаче пропускаются (эффект не звучит), музыка (`i_sound.c`, частный читатель декодера): 3 попытки (100/200 мс, поток открывается заново),
после чего декодер сообщает об ошибке музыки и игра идёт дальше.

**Проверка.** Внедрение ошибок (`-pkioerr at[,count]`: попытки с номера `at` подряд `count` штук возвращают ошибку; тот же код в хост-тесте `PACK_TEST_INJECT`):
* хост-тест (`test_pack_reader.py`, CHARS.PAK): 1 ошибка на 3-й попытке и на 1-й — 0 отказов, 1 повтор, таблица лумп та же; 3 подряд — 0 отказов, 3 повтора (с `freopen`), таблица та же; 4 подряд — ровно один отказ с именем пака в сообщении;
* PCSX2, MAP01 software, `-pkioerr 150,1`: `WARNING: host:/SRB2.PAK: read of 65536 bytes at 8980480 failed (I/O error), trying again (2 of 4)`, дальше `LHASH map.all eab10543da06fc16` (тот же, что у базы) и `ZQUIT DONE`, без `I_Error`;
* PCSX2, `-pkioerr 150,4`: `I_Error` с сообщением выше после трёх предупреждений;
* остальные прогоны с `-pkioerr` — см. раздел 9 (после правки номера попытки: в первом прогоне номер 300 лежал за концом чтений).

Не проверено на консоли: реакция настоящего USB/DVD на повтор (допущение RSYS: часто помогает через 50–200 мс).

## 4. RS-08: атомарная запись сейвов и конфига, накопитель загрузки файлов

**Сохранения (`src/ps2/ps2_safefile.c`, вызовы в `m_misc.c`, `g_game.c`).** `FIL_WriteFile` (gamedata.dat, сейвы, реплеи, `gamedata.bad`, снимки) и основной `config.cfg` (`M_SaveConfig(NULL)`, при выходе)
пишутся в `NAME.tmp`; результат `fwrite`, `fflush`, `fclose` проверяется. Только целый временный файл заменяет `NAME`: старый файл → `NAME.bak`, временный → `NAME`, `NAME.bak` удаляется. При
отключении питания в любой момент `NAME` или `NAME.bak` целы; `PS2Safe_Recover` (в `FIL_ReadFileTag`, когда `NAME` не открылся) возвращает `NAME.bak`. Полная карта/вынутая флешка при записи
временного файла: старый файл не тронут, `FIL_WriteFile` возвращает `false`; `G_SaveGameData` и `M_SaveConfig` теперь говорят игроку («Could not save the game data … full?») — раньше молчали (S-06).
Носитель, который не умеет `rename` (по факту: `host:` в PCSX2; драйвер карты памяти — по коду libcglue неизвестно), даёт один неудачный `rename`, модуль запоминает это («навсегда») и пишет
дальше поверх файла как раньше (запись проверяется); при потоковой записи конфига временный файл читается обратно и пишется поверх.

Хост-тест `tools/ps2/safefile_hosttest.c` (настоящие файлы, подменяемые операции): обычная запись, нет старого файла, полная карта, нет `rename`, нет `rename` старого файла, нет `remove`,
потоковая запись конфига, **отключение питания (longjmp) на каждом шаге записи — 10 точек прерывания: после `Recover` в файле целиком старое или целиком новое содержимое, во всех**; мутация модуля
(старый файл не уходит в `.bak`) ловится тестом. В PCSX2 на `host:`: `reference.cfg.tmp` создаётся, `rename` не работает, содержимое читается обратно и пишется поверх `reference.cfg`
(в журнале `IO O … reference.cfg.tmp` ×2 и чтение 9195 байт) — то есть **путь отката проверен в эмуляторе, путь атомарной замены — только хост-тестом**; на `mc0:` в этом слоте эмулятора карта не
отформатирована (`-iobench -home mc0:` → «cannot create mc0:/iobench.tmp»), а форматировать общий слот не стал.

**Накопитель загрузки файла (`d_netfil.c`).** Фрагменты по 1 КБ раньше писались `fseek`+`fwrite` на каждый. Теперь поток получает буфер 32 КБ (`setvbuf` сразу после `fopen`), `fseek` пропускается,
если фрагмент идёт сразу за предыдущим (сервер шлёт по порядку), фрагмент не по порядку ищет как раньше; `fclose` проверяется (последний кусок мог не дойти до носителя). Включено по умолчанию для
`mc*`, `mass`, `mx4sio`, `hdd`, `usb` (в `downloaddir`); `-dlbuf 0|1` принуждает. Проверка эквивалентности: сценарии `dl-buf0`/`dl-buf1` (раздел 8). Время записи на носителе консоли — не
измерялось (модель RSYS: 2000 фрагментов × 3–10 мс на USB 1.1 → 31 запись по 32 КБ).

## 6. RS-02: предзагрузка рабочего набора уровня одним проходом (`-pkprefetch [КБ]`, **по умолчанию ВЫКЛ**)

**Что сделано.** `R_PrefetchLevel` (в `P_LoadLevel` перед `R_PrecacheLevel`) собирает список ламп: заплатки всех текстур на сторонах, флатов уровня и неба, все кадры спрайтов, которыми пользуются mobj
уровня, и спрайты скинов игроков; `WPack_PrefetchRun` сортирует их по `(пак, смещение)`, читает проход (дыры до `merge` носителя: 128 КБ dvd / 8 КБ usb,sd / 64 КБ hdd читаются «насквозь», чтение —
кусками по 64 КБ, между кусками `NetKeepAlive` для сетевой игры) и кладёт **сжатые** байты (до 98 КБ на лампу, бюджет 2 МБ) в один блок `PU_CACHE` с владельцем `pf.blob`. Зона забирает блок под
давлением (`Z_Evict…` освобождает кеш-блоки раньше любых reclaim-хуков, поэтому отдельный `Z_AddReclaimHook` не нужен и не заведён), указатель обнуляется, и чтения идут через окно как без предзагрузки.
Любое чтение (`ReadAt`/`PeekAt`) сначала смотрит блок: попадание — `memcpy`/декод прямо из блока. Список ключуется адресом `FILE *` и сбрасывается при открытии любого нового потока.

**Числа** (журнал устройства, `build/pak2`, одна ELF `out-io5`, A/B флагом; «после» = карта + игра):

| сценарий | политика | без предзагрузки | с предзагрузкой | блок |
|---|---|---|---|---|
| MAP01 software, 10 кадров | usb | 285 команд / 2.99 МБ | **113 / 2.75 МБ** | 720 КБ, 21 чтение |
| MAP01 software | dvd | 117 / 7.50 МБ | **89 / 4.58 МБ** | 720 КБ |
| D2 HW, 700 кадров | usb | 478 / 4.66 МБ | **243 / 4.71 МБ** (ELF `out-io3`) | 1226 КБ, 51 чтение |
| D2 HW | dvd | 283 / 17.88 МБ | **195 / 11.24 МБ** | 1226 КБ, 24 чтения |
| D4 HW, 700 кадров | usb | 426 / 3.88 МБ | **290 / 3.77 МБ** (`out-io3`) | 692 КБ |
| D4 HW | dvd | 277 / 17.66 МБ | **217 / 12.89 МБ** | 692 КБ, 18 чтений |

Цена в памяти и в тактах эмулятора (то, из-за чего флаг выключен): блок занимает 0.7–1.2 МБ арены, пока зона его не отберёт. На MAP01 (7 МБ свободно) свободное падает 7.57 → 6.87 МБ (блок цел), `cycles`
не меняются (98.9 → 98.1 М). **На D2 (свободно ≈ 330 КБ) блок вытесняется сразу и мешает HW-кешу текстур: `failed` (промахи списка свободных блоков зоны) 39 → 861, время прогона 700 кадров
`t_ms` 28.1 → 30.6 с (+8.7 %)**; на D4 `cycles` 2151 → 2159 М (+0.4 %, в пределах разброса), `failed` 87 → 77. То есть предзагрузка помогает носителю там, где в арене есть запас, и вредна там, где его нет
(D2, «лотерея арены» IZ). Включать её имеет смысл после того, как IZ уберёт зависимость от ёмкости арены, или по списку карт с запасом ≥ 1.5 МБ; пока — только флаг.
Числа для DVD (11–20 с против 20 с в модели) показывают порядок эффекта сортировки, а не обещание: допущения раздела 1 RSYS.

## 7. RS-06: сон без будильников на игровой нити, наблюдатель нитей звука

**Что сделано.** Игровая нить больше не спит `DelayThread` в звуке (`YieldSleep` очереди команд, `SleepMs` в `StopThreads`/`WaitConsumed`/`WaitClosed`), в ожидании пада (`i_joy.c`, старт и экран ошибки)
и в ожидании USB (`ps2_addons.c`, до 10 с): всё через `PS2_SleepUs` (нить опускается до приоритета 120 и читает часы; образец — PS2-NET-3). Нити микшера (приоритет 5) и декодера (7) `PS2_SleepUs`
использовать не могут (после сна они остались бы ниже игровой нити), поэтому они **под наблюдением**: каждый круг нити увеличивает счётчик и пишет, внутри ли она `DelayThread`; `AudioWatch`
(игровая нить, раз за кадр) смотрит счётчики. Если счётчик стоит 300 мс — строка `AUDWD <нить> thread stalled …` (состояние, `waitType`, `waitId`); если нить при этом внутри своего `DelayThread` и ждёт на
семафоре, наблюдатель делает `SignalSema(waitId)` — сигнал заканчивает сон так, как это сделал бы потерянный будильник. Нить, которая не в своём сне (читает носитель или ждёт IOP), только
отмечается: чужой семафор сигналить нельзя. `-amixhang N` заставляет микшер после N кругов бесконечно ждать семафор, который никто не сигналит (имитация потерянного пробуждения).

**Проверка (PCSX2).** MAP01, `-amixhang 300`: `AUDWD mixer thread stalled for 300 ms: status=4 waitType=2 waitId=35 prio=5 beat=300 - signalling its semaphore`, звук продолжился (счётчики
`blocks`/`pumps` растут после события: 902 → 1154 блоков), в итоговой строке `underruns=1 gapmax_ms=232` (один разрыв на время ожидания наблюдателя; без наблюдателя нить ждала бы вечно). Версия без
флага «нить внутри сна» (первый вариант) сигналила любому ожидающему на семафоре; в итоговой версии условие уточнено (чтобы не «разбудить» ожидание ответа IOP) — прогон итоговой версии (ELF `out-io7`): `AUDWD mixer thread stalled for 300 ms: status=4 waitType=2 waitId=35 prio=5 beat=300 sleeping=1 - signalling its semaphore`, звук продолжился, итог `underruns=1 gapmax_ms=226`.

**Не проверено.** Что потерянное пробуждение на железе вообще случается в звуковых нитях (NET видела его только у игровой нити в HW); `DelayThread(25000)` в `ProbeQueue` (диагностика `-aprobe`) и сторож
сети `WdThread` оставлены. Вариант (в) исследования (семафор по прерыванию таймера) не делался.

## 8. RS-09: keepalive сети при долгой загрузке

**Что сделано.** Нить приёма (`ps2_netsvc.c`): когда от сервера пришёл пакет тиков, а игровая нить не опрашивала сокет дольше 500 мс (идёт загрузка уровня или аддона) и клиент подключён
(`cl_mode == CL_CONNECTED`, любое состояние игры — включая промежуточный экран перед загрузкой), нить отвечает пакетом, который оригинальный клиент шлёт во время затухания (`CL_SendClientKeepAlive`:
`PT_BASICKEEPALIVE`, голый заголовок 8 байт, контрольная сумма как у `EarlyAck`), не чаще раза в секунду. Тики не подтверждаются, протокол и типы пакетов — оригинальные, `NET-протокол не менялся`.
Нашёл тест: первая версия пропускала пакеты, когда кольцо приёма (64 слота) переполнено, а за долгой загрузкой оно переполняется за ≈ 2 с (`dropped 840`) — keepalive отправлялся до переполнения
и не после; теперь он вызывается и для отбрасываемых пакетов. Прочее: `prefetch` между чтениями вызывает `NetKeepAlive` (для сетевой игры); тестовые крючки `ps2stall MS` (консольная команда:
игровая нить стоит MS мс) и `-loadstall MS` (задержка после чтения карты у подключённого клиента), `-netnokeepalive` (A/B).

**Проверка** (`tools/ps2/net_specs13.py`, ПК-сервер с таймаутом по умолчанию 350 тиков = 10 с, PS2-клиент software, игровая нить клиента стоит 14 с; сервер ПК из `build/pc-net`):

| сценарий | что | результат |
|---|---|---|
| `ka-stall` (ELF `out-io7`) | стоим 14 с, keepalive включён | **rc 0**, клиент остался в игре, 63 общих отсчёта `NETSYNC` (тики 35…2205), 0 отличий; `load-keepalives 14` к кадру 770 (по одному в секунду), `dropped 840` (кольцо переполнено) |
| `ka-stall-off` (`out-io6`, `-netnokeepalive`) | то же без keepalive | rc 5: сервер: `*Sonic left the game (Connection timeout)` ровно через 10 с после начала паузы |
| `ka-stall` (`out-io6`, до исправления кольца) | keepalive включён, кольцо переполнилось | rc 5, тот же таймаут (так нашлась ошибка) |
| `ka-stall-short` (`out-io6`) | пауза 7 с (контроль) | rc 0, 49 отсчётов, 0 отличий |

Не сделано: сторона PS2-**сервера** (его загрузка карты; ПК-клиенты ждут те же 10 с) — нужны вызовы `NetKeepAlive()` из главной нити внутри `P_LoadLevel` либо знание адресов узлов в нити приёма;
`PS2NetSvc_Stop` по-прежнему `TerminateThread` (S-07). Совместимость с ПК-сервером и игра: раздел 9.

## 10. Не проверено / не закрыто (честно)

* **Консоль не использовалась.** Все времена носителей — модель RSYS (раздел 1); политики usb/sd/hdd (и их выбор по префиксу `mass:`/`mx4sio`/`hdd`), повтор чтения на настоящем сбое, `rename` на карте памяти и USB, запись на карту
  (`mc0:` в слоте эмулятора не отформатирован), загрузка с DVD/USB/MX4SIO/HDD (S-01: **не исправлено**, нужны IRX в ELF; S-02: драйвер карты поднимается, запись на карту не проверена) — на железе не видел. `-iobench` готов (на `host:` запускается:
  `window command 85 us x 209.73 MB/s: T = 17.4 KB -> -pkmedium hdd`, `rename … FAILS`), числа носителя даст только консоль.
* **RS-02 (предзагрузка) — флаг ВЫКЛ**: помогает, где в арене есть запас (MAP01, D4, число команд −40…−60 %), вредит в D2 (+8.7 % времени, `failed` 39 → 861); без решения IZ по арене не включать.
* **RS-04 (подъём носителей)** сделан только для дома при загрузке с DVD; USB/MX4SIO/HDD как корень данных — нет.
* **RS-09**: клиент — да; PS2 как сервер (его загрузка карты), остановка нити приёма без `TerminateThread` (S-07), игра вчетвером/сплитскрин по сети — не делались.
* **Не взято из списка RSYS** (вне этого задания): RS-11 (постоянный дескриптор музыки), RS-12 (MD5 add-on блоками по 64 КБ — одна строка, но требует отдельной перепроверки и пересборки), RS-13 (кеш разжатой лампы для вложенного MAP.wad),
  RS-10 (`netcmds`), S-10, S-12, S-14, S-15, S-16 (CRC при чтении).
* Число команд устройству на usb **выросло** (2×): выигрыш по модели есть только потому, что команда USB дешевле байт; если `-iobench` на консоли покажет другое `T`, `-pkmedium hdd|dvd` возвращает крупные окна без пересборки.
* Разбор `ReadHeader` для не-пакетных файлов (add-on pk3/wad) прежний, но они теперь читают сигнатуру ниже stdio перед `setvbuf` (+1 команда на файл).
