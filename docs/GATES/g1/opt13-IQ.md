## 6. Маска Lua-хуков (RTICK L-1)

`src/lua_hook.h`, `src/lua_hooklib.c`, `src/p_mobj.c`. Вместо глобального `lua_mobjhooks_any` (после первой регистрации любого хука мобжа любого вида на любой тип все `LUA_HookMobj / Hook2Mobj / HookMobjLineCollide` каждого объекта шли в `*Slow`: `prepare_mobj_hook` → `init_hook_type` → `mobj_hook_available`, всегда с ответом «нет») — `UINT32 lua_mobjhookmask[тип]`: бит k = на этот тип зарегистрирован хук вида `MOBJ_HOOK(k)`, строка `MT_NULL` = хуки на все типы. `LUA_MobjHookWanted(mo, вид)` даёт тот же ответ, что `mobj_hook_available` (то же условие, `mo == NULL` — только строка `MT_NULL`), и вызывается встроенно; без хука `*Slow` не вызывается. Маска растёт в `LUA_GrowMobjHooks` вместе с таблицей типов, бит ставится после `add_hook`. `P_SceneryQuick` (быстрый путь неподвижной декорации, PS2-203) теперь отказывается только для типов с хуком `MobjThinker` (единственный хук, который быстрый путь пропустил бы: у него `fuse == 0`, движения нет), а не для всех типов после любой регистрации.
Условия и порядок вызова хуков не меняются: проверка эквивалентна проверке внутри `prepare_mobj_hook` (при недоступном хуке `init_hook_type` не трогает стек Lua и возвращает умолчание: 0).
**Числа** (`--prof` LTO, D3 software, `-file lq_fang.lua`: `addHook("MobjThinker", function(mo) end, MT_FANG)` — тип, которого в демо нет; тик на тик, М тактов):

| | без скрипта | со скриптом | разница |
|---|---:|---:|---:|
| до (`lua_mobjhooks_any`, ELF после пунктов 1–4) | 5.247 | 5.684 | **+0.437** (+8.3 %) |
| после (маска) | 5.267 | 5.351 | **+0.084** (+1.6 %) |

(остаток 0.08 М = встроенная проверка маски в ≈8000 вызовах на тик; исследование мерило +0.44 М на EE при том же скрипте.)
**Проверка:** `tools/ps2/luatests/lt_hooks3.lua` (новый, в `lua_suite.sh`): хуки на ОДИН вид для ОДНОГО типа (`lt_hooks.lua` вешает каждый вид на все типы, там путь «хука этого вида для этого типа нет» не берётся никогда), счётчики и свёртка аргументов по (хук, тип) на демо D1; PC-эталон против EE. `src/console.c/h`, `src/d_main.c`. Патч исследования `rs05a_startup_console.patch` взят и дополнен тем, чего в нём не было:

* две печати с интервалом < 40 мс делят одну перерисовку (`rsys_pending`); **`CON_FlushStartup()`** рисует задержанную печать и вызывается сразу после печати перед долгой работой: `HU_LoadGraphics`, `M_FirstLoadConfig`, `R_Init` (R_LoadTextures ≈ 130 М тактов), `S_InitSfxChannels`/`I_StartupSound`, `ST_Init`, `D_CheckNetGame`; `CON_EndStartup()` в начале `D_SRB2Loop` освобождает кеш картинки (в патче исследования он нигде не освобождался) и с `-loadprof` печатает строку `CONRD redraws= cycles=`;
* `-rsys_nostart` — как до правки (A/B на одной ELF).
**Числа** (`--prof` LTO, одна ELF, `-skipintro -zquitall 120 -loadprof`, сумма кругов `B_*` старта, М тактов; `CONRD` — число перерисовок и их такты):

| | `-rsys_nostart` | по умолчанию | разница |
|---|---:|---:|---:|
| software, сумма `B_*` | 386.5 | **317.2** | **−69.3 (−17.9 %)** |
| software, перерисовок / тактов в них | 28 / 90.9 | 7 / 9.2 | −81.7 |
| Hardware, сумма `B_*` (в ней 1845.8 М — `B_GFX2`, инициализация GS) | 2230.2 | **2162.9** | **−67.3** |
| Hardware, перерисовок / тактов в них | 29 / 86.0 | 8 / 11.6 | −74.4 |

(В исследовании HW оценивалось «≈ −65 М, не измерено» — измерено −67 М.) Что не проверено: вид экрана старта глазами на консоли (экран отстаёт от лога не более чем на 40 мс и сразу перед долгими шагами дорисовывается; `-vidshot` консоль старта не снимает).
