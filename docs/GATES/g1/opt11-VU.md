## 0. Как мерить (скрипты в `build/vu/`, не в git)

## 2. Этап 1 — VU1 по умолчанию, палитровый свет с резкой по рядам на VU1 (PS2-HW-100)

### 2.1 Что сделано
* `src/ps2/hw/vu1/ps2_hw_vu1.vsm` написана заново (600 инструкций): трансформ, классификация по 6 плоскостям (guard band), отсечение Сазерленда–Ходжмана в общем цикле по таблице плоскостей
  (таблица загружается при старте VU1 и лежит в памяти VU1 всё время; код стал вдвое короче — 12 вариантов макроса не помещались в диапазон ветвления ±1024 инструкций),
  перспективные ST/Q, деление, Z, упаковка пакета GIF (ST, RGBAQ, XYZF2 или одни XYZF2 для плоских), XGKICK, двойная буферизация выхода.
* **Палитровый свет на VU1 без резки на EE:** программа сама считает ряд colormap по формуле SRB2 (`row = clamp(floor(max(base − K80/(lightz+1), cap)), 0, 31)`, `lightz = clamp((w − near)·kz/16, 0, 127)`)
  для минимальной и максимальной глубины полигона после отсечения; если ряды разные, режет полигон плоскостями `w = T_m` (T_m — глубина, где ряд становится m: одно деление на ступень) и каждый
  кусок выводит с A+D-пакетом `TEX0` (CBP ряда, CLD = 1) перед пакетом веера. Таблица TEX0 рядов (по QW на ряд) приходит с константами плана; драйвер гарантирует, что CLUT рядов `[rlo, rhi]` этой
  таблицы света есть в VRAM (`prow_blk`: слот проверяется по ключу, обычный `clut_get` при промахе).
* EE: `ps2_hw_vu1.inc` переписан: `vu_plan_setup` (ряды, состояние GS `pass_setup`, константы), `vu_poly` (проверка размаха UV, заголовок и вершины в чанк), чанки через UNPACK/MSCAL как раньше.
  VU1 теперь по умолчанию (`-hwdbg 268435456` = `HWDBG_NOVU1` выключает: путь EE как раньше, для A/B); `-hwvu1` ничего не делает.
* Пригодность к железу: константы плана идут за `FLUSHE`; `MSCAL` идёт за `FLUSH` (пакеты состояния PATH2 исполнены GS до пакетов PATH1 программы); каждый `DIRECT` за `FLUSH` (было);
  индекс выходного буфера и ряд, который держит GS, лежат в памяти данных VU1, а не в регистрах (между запусками ничего не предполагается о регистрах);
  следующий `XGKICK` ждёт предыдущую передачу, буфер переписывается только после него.

## 2.3 Этап 2 — свет на полигон, один открытый чанк для одиночных рисований, единые ряды CLUT (PS2-HW-101..106)
* `PS2HWD_PalLit` (PS2-HW-106): для палитровых полигонов уровень света больше не часть ключа батча. Заголовок полигона VU1 (QW0.y) несёт `light_level` сектора; программа считает `cap`/`base` ряда
  из него (константы `K_LIGHTB`). Партии больше не режутся по сектору: DEMO_001 248 → 76..95 батчей на кадр. `PS2HWD_DrawFans` получил тройки (first, count, light) (`hw_batching.c`, файл роли GEOM, правка только `#ifdef PS2`).
* PS2-HW-101: `H.clut_epoch` (+1 при каждой сборке CLUT-образа) — по нему проверяется, что таблица TEX2 рядов (`VU.rt`) по-прежнему указывает на нужные блоки VRAM; без пересчёта на каждый батч.
* PS2-HW-102: после записи CLUT-образа в VRAM идёт `TEXFLUSH` (на железе кэш текстур GS иначе может держать старую палитру; PCSX2 этого не показывает).
* PS2-HW-103: одиночные рисования (`hw_DrawPolygon`: HUD, тени, спрайты вне батча) идут на ту же программу VU1. Чанк остаётся открытым между вызовами; кто пишет в кольцо иначе (`pk_alloc/pk_ref/pk_flush`) — закрывает его сам.
  Рисование с тем же ключом плана (`vukey_t`, 28 слов) присоединяется к открытому чанку без `begin_draw` и без констант.
* PS2-HW-104: VU0 (макро-программа планировщика/трансформации) грузится лениво при первом использовании.
* PS2-HW-105: ряды CLUT «keyed» и «plain» различаются только записью 255. Текстура карты/плоскость без индекса 255 использует keyed-ряды в обоих вариантах → вдвое меньше CLUT-слотов; на DEMO_001 была
  «пробуксовка» кэша CLUT (84 сборки CLUT на кадр, `prow_ensure` 1.2 М) — пропала (rows=0..2).

## 2.4 Этап 3 — смена плана вместо нового плана, один проход копирования, цикл по партии (PS2-HW-107, 108)
* PS2-HW-107 (retarget). Одиночное рисование (HUD: глифы шрифта, спрайты, тени) и партия, чей план отличается от плана предыдущего рисования VU1 только текстурой того же рода (psm, вид палитры, wrap, npot, region,
  фильтр) и, при свете по рядам, уровнем света, больше не вызывают `begin_draw_inner` и пересылку констант: `vu_retarget` меняет `P.r/tsx/tsy/clamp` и LRU текстуры, `vu_retex` пишет только TEX0/TEX1/CLAMP (остальные регистры
  те же: `H.serial` не менялся), константы остаются в памяти VU1 (для рядов отправляется одно QW K_INT: ряд, который держит GS). Масштаб текстуры (`tsx, tsy`) теперь едет в заголовке полигона (QW1.z, w): программа
  читает его на каждый полигон, поэтому один чанк может нести полигоны разных текстур одного плана. Ключ плана — 32 слова, сравнение по двойным словам (`vu_key_cmp`: 2 = то же, 1 = смена текстуры/света, 0 = другой план).
  `-hwnoretarget` / `-hwnobretarget` / `-hwbretmask N` — выключатели для A/B (одиночные+партии / только партии / по видам).
* PS2-HW-108. `vu_poly` — один проход по вершинам (размах s, t для UV_EXTENT считается при копировании; слова w и нулевые слова вершин не пишутся: программа берёт w = 1.0 из VF00); `vu_fans` — цикл по
  всей партии с локальными значениями плана (запасной путь `vu_poly` для первого полигона плана, полного чанка, необычного размера); `vu_plan_setup` вынесен из горячего пути (`noinline`: меньше сохранений регистров).
  Чанк остаётся открытым и после партии (PS2-HW-103); `begin_draw` закрывает его первым делом: открытый чанк меняет состояние GS (ряды CLUT, RGBAQ), а кэш состояния должен быть таким, каким он станет, до того как новый
  план решает, что писать.
* Из-за этого же правила `P.serial = H.serial - 1` ставится после рисования полигона общим путём внутри плана VU1 (общий путь мог загрузить другой ряд CLUT).

### Как сравнивать картинки (важно)
A/B путь EE против VU1 по кадрам таймдемо корректен только при одинаковой «форме» командной строки обоих прогонов: добавление или отсутствие любого последнего аргумента (даже `-hwfbh 200` второй раз) сдвигает
соответствие кадр → такт игры, картинки расходятся на 800..5000 пикселей без всякой причины в драйвере. Поэтому `abd.sh` теперь даёт обоим прогонам по одному последнему аргументу (`-hwdbg 268435456` для EE, `-hwdbg 0` для VU1).
Результат (сборка этапа 3, EE против VU1, пикселей из 64000 на кадрах f150 / f450 / f750): DEMO_001 4 / 54 / 10; DEMO_002 27 / 20 / 8; DEMO_003 48 / 6 / 12; DEMO_004 33 / 39 / 130 — одиночные пиксели
на ступенях ряда света и на краях текстур (арифметика VU1, PS2-HW-100). Смена плана включена и выключена: MAP01 k100 (`-hwnoretarget`) и DEMO_004 f750 (`-hwbretmask 7/0/4/3`) — 0 пикселей разницы (на других кадрах не проверялось).
`--prof`-сборки считают ещё и `PS2HWD_QuadHidden` в режиме проверки (`PS2_PROFILE`, PS2-HW-72): по сэмплеру это 0.3 М (DEMO_001) – 0.8 М (DEMO_004) на кадр, которых в релизной сборке нет; числа всех этапов и базы сняты в одной
и той же конфигурации.

## 2.5 Этап 4 — запись состояния в чанке, небо с NPOT-текстурой, сортировка, слияние с основной веткой (PS2-HW-109, 110, 111)
* PS2-HW-111 (записи состояния). Смена текстуры внутри открытого чанка больше не закрывает чанк: драйвер кладёт в поток чанка «запись состояния» (заголовок `n = 0, y = m` и GIF-пакет A+D с регистрами
  CLAMP / TEX1 / TEX0 новой текстуры), программа VU1 (`StateRec`) отправляет её через XGKICK между полигонами. Нет `MSCAL`, нет `FLUSH`, нет `DIRECT` на каждый глиф HUD / смену текстуры партии.
  Только планы без света по рядам (`!P.pal`: там ряд CLUT ведёт программа); при нехватке места в чанке или если для CLUT пришлось строить образ (загрузка закрывает чанк) — прежний путь `vu_plan_setup`.
  `-hwnorecord` выключает. A/B запись включена / выключена: DEMO_001 f449, f450, f451, f750 и DEMO_004 f301, f303, f305, f601, f603, f605, f751, f753 — 0 пикселей разницы. * PS2-HW-110 (небо). `sky_dome_fast` отказывался от текстуры, у которой высота или ширина не степень двойки (небо 512×768 в DEMO_002: `P.cuty`): купол шёл старым путём (1.45 М тактов на кадр, 15 % кадра).

  разрезы и `sb/tb` старого пути для такого треугольника. Сетка с полосой, пересекающей повтор, по-прежнему идёт старым путём. A/B против старого пути (`-hwdbg 4096`), DEMO_002 f150 / f450 / f750: 7 / 0 / 0 пикселей.
  DEMO_002: wall 9.54 → 8.47 М.

### Формат блока VU1 (интерфейс для кэша геометрии, PS2-HW-80)
Чанк = один `UNPACK V4-32` в буфер VU1 (до 255 QW), первое QW: `x = число элементов`. Элемент — полигон или запись состояния:
* полигон: QW0 `(u32 n = 3..12, float уровень света сектора, 0, 0)`; QW1 `(float sb, tb, tsx, tsy)` (целые повторы s, t, вычтенные из координат; масштаб текстуры плана — абсолютный, зависит от уровня текстуры в данный момент);
  затем по 2 QW на вершину: `(x, y, z, не читается)` в пространстве движка и `(s, t, не читаются)`. Размер: `2 + 2n` QW.
* запись состояния: QW0 `(u32 0, u32 m, 0, 0)`, затем m QW готового GIF-пакета (A+D, EOP = 1).
`PS2HWD_DrawFans(surf, base, nfans, flags, desc)` принимает тройки `(первая вершина, число вершин, уровень света)`; `vu_fans` копирует вершины в чанк (≈220 тактов на четырёхугольник), блок можно было бы подать по REF-DMA тем же
форматом (`CNT`-тег с заголовком + `REF`-тег на вершины внутри одного UNPACK: VIF читает данные UNPACK через границы DMA-тегов). Не сделано: (а) `tsx, tsy` в заголовке зависят от текущего уровня текстуры, а статический блок
обязан их не хранить (VU должна брать масштаб из констант плана, заголовок давать поправку), (б) производителя блоков (кэш GEOM выключен), (в) память: блок 32 байта на вершину против 20 у `FOutVector`. Оценка выигрыша на стороне драйвера:
≈160 тактов на полигон (D1 ≈0.2 М, D4 ≈0.36 М); остальное из «−1 М» роли GEOM — работа движка (`HWR_ProcessPolygon`, отпечаток, копирование), не драйвера.

### 6.1 Этап 1 — QuadHidden на VU0, ключ палитры раз в кадр, branchless outcode, локальные переменные в vu_fans (PS2-HW-220..223)
* PS2-HW-220: `PS2HWD_QuadHidden` (проверка 4 углов спрайта/тени, 1100..1300 вызовов на кадр в D4, 2/3 «скрыты») считается на VU0 в макрорежиме: четыре цепочки умножения матрицы (`vmulaw/vmaddax/vmadday/vmaddz`),
  четыре `vclipw.xyz`, сборка флагов `vi18`; матрица в vf21..24 (регистры планов vf1..18 не трогаются). Близко к глазу (w < 2 near) — ответ «не скрыт» (решает клиппер).
  Ответ «скрыт» только для квада без центра пикселя (бокс расширен на 0.1 px). `-hwqh 1` — прежний скалярный тест, `-hwqh 2` — оба и счёт расхождений (HWSPRCULL: differ). Расхождений ~0-2 на ~150 К проверок
  (арифметика VU0 усекает: угол на самой плоскости клипа может сменить сторону; рисует такой квад ни одного центра пикселя).
* PS2-HW-221: `PS2HWD_PalLit` вызывается на каждый полигон кадра (2250 раз в D4); основная цена — `palette_mode()` (проверки шейдера/эпохи) на каждый вызов. Теперь `palette_mode_fr()` — то же значение, но
  вычислено один раз за кадр (сбрасывается по `frame_no`/смене палитры); тот же кэшированный режим идёт в ключ плана `vu_key_make` (`w[30]`). Первая версия (мемо на (текстура, флаги, шейдер) с версией текстур) давала мало
  (низкий процент попаданий: загрузки текстур увеличивали версию) и убрана. Ответ PalLit тот же: счётчики партий совпали с прежним (D1).
* PS2-HW-222: `outcode()` (план: 6 сравнений на вершину) без ветвей: знаковые биты разностей. Тот же результат (биты порядка 0..5 прежние).
* PS2-HW-223: `vu_fans` держит позицию в чанке в локальных переменных, публикует в `H`/`VU` только на медленном пути; цикл по полигонам короче.
Числа тыла (сэмплер, К тактов/кадр, D1 / D4): база 2983 / 5201; после 220+221 (первая версия) 2776 / 4653; после 222+223 2707 / 4505.

### 6.2 Этап 2 — как считает машина (-hwbench), планировщик на VU0, партия без индексов, мелочи тыла (PS2-HW-224..229)
**Что стоит инструкция на машине, на которой сделан профиль** (`-hwbench`, строки HWBENCH, `ps2_hw_bench.inc`; PCSX2 2.6.3, такты COP0 Count). Это меняет, как писать горячий код:
умножение `mul.s` = 4 такта и ничего не перекрывается, сложение / `cvt` = 1, `div.s` / `sqrt.s` = 6, целое `mult` = 2, **сравнение float с ветвлением (`c.lt.s` + `bc1t`) = 5**, `lw`/`sw` = 1
(копия пяти слов вершины ≈ 12), `lq`/`sq` и `lwc1`/`swc1` в паре с зависимостью ≈ 2.4, память не моделируется (промахи кэша бесплатны), `memcpy` 80 байт с невыровненным
приёмником = 90. Матрица на вектор на VU0 в макрорежиме: 11 тактов на вектор при четырёх независимых (45 на четыре), один вектор сам по себе ≈ 40 (цепочка, `vclipw`, `sqc2`, `cfc2`
ждут друг друга). Отсюда: меньше умножений, сравнения float по битам (положительные float упорядочены как целые), `min.s`/`max.s`, VU0 для векторной арифметики пачками по четыре.
* PS2-HW-224: `HWR_ProcessPolygon` копировал вершины полигона (3..16 по 20 байт) через `memcpy`: newlib идёт побайтово при приёмнике, не выровненном на 8 (пул вершин по 20 байт), 70..150 тактов
  на четырёхугольник, 224 К тактов на кадр D1 (memcpy + wrap). Теперь `HWR_CopyVerts`: пять слов на вершину без вызова (холостой `asm` не даёт GCC вернуть цикл в `memcpy`). Сумма с `memcpy`
  в сэмплере: D1 613 → 559 К, D4 1140 → 1046 К.
* PS2-HW-225: `HWR_GroupSort32` (старый путь партии): цепочка полигонов с одним ключом (стены одной текстуры подряд) не ходит в хэш-таблицу; цифры радикса, одинаковые у всех различных ключей, пропускаются
  без очистки 256 слов и прохода; циклы «индексы» и «ключи» слиты в один проход. Тот же порядок (хост-тест `tools/ps2/hw_sort_hosttest.c`, gcc: 1200 случаев + отрицательный контроль).
* PS2-HW-226: **партия без отсортированного массива индексов** (`HWR_RenderBatchesV2`, `HWR_GroupPlan` в `hw_sort.h`). Было пять проходов по полигонам (индексы, ключи, группировка, разброс индексов,
  обход с проверкой границ партий соседних полигонов), ≈ 150 тактов на полигон. Стало: группировка по ключу (ведро = полигоны с одним ключом: порядок текстур и хэш состояния), сортируются только ведра
  (сотни), один проход кладёт тройку (первая вершина, число вершин, свет) каждого полигона на своё место и проверяет, что полигон в том же состоянии, что первый в ведре (ключ 30 бит: два состояния
  могут совпасть, тогда функция уступает старому обходу); смены состояния ищутся между первыми полигонами соседних вёдер теми же проверками, что в старом обходе. Те же партии в том же порядке:
  `-hwgo 128` сравнивает порядок полигонов и список партий (первый полигон, число полигонов, хэш состояния, с которым партия рисуется) со старым обходом (сухой прогон) на каждом кадре (HWBATCH2; на 4 демо
  расхождений 0 при ≈ 3000 списков на демо); `-hwgo 64` — старый обход; `-hwgo 256` — по строке на партию для тиков уровня 372..376 (то, что получает драйвер: так сравниваются два прогона).
  Сэмплер: RenderBatches + GroupSort 369 → 220 К на D1, 585 → 316 К на D4. Реальные такты D1 (HWPROF21, non-LTO): sort+walk 262 → 190 К на кадр.
  Что показал поиск разницы картинок: у `-hwgo 64` против умолчания на D4 f449/f451 отличается 15 / 7 пикселей на ±1 в тёмно-красном (тени спрайтов: полупрозрачные квады на полу). Причина не в партии:
  вызовы драйвера совпадают (кроме слова `surf.PolyFlags`, которое вызывающие не инициализируют и драйвер не читает), но порядок вёдер с одной текстурой и разными состояниями задаёт 16-битный

### 6.3 Этап 3 — слияние с FX2, детерминированный порядок вёдер, лёгкий HWR_ProcessPolygon, ответы FX2 (PS2-HW-230..232)

  текстур: порядок состояний одной текстуры и порядок двух патчей зависели от раскладки кучи, и два копланарных полигона (тень и пол, два спрайта на одной глубине) рисовались в порядке, который менялся с любой
  правкой выделений памяти. Нашёл так: картинка D4 f751 у разных сборок одного и того же кода различалась (35, 1077, 1151 пикселей против сборки раунда 1), а вызовы драйвера (`-hwgo 256`: строка на партию) одинаковы
