# OPT11, агент VU: GS Hardware Renderer — драйвер: VU1 / VIF1 / GIF (отчёт, дописывается по этапам)

Ветка worktree `worktree-agent-af8eb538583cafe96`. Единицы: такты COP0 EE на кадр (`HWPROF wall`), PCSX2 2.6.3 (32 МБ, программный GS), `-ps2prof`, релиз с LTO,
`-renderer Hardware -zreserve 1536`, окна по 105 кадров (окно 0 = загрузка карты, среднее и максимум по окнам 1..9), FPS = 294.912 М / такты. Реестр отличий: PS2-HW-100..119.

## 0. Как мерить (скрипты в `build/vu/`, не в git)
* `build/vu/mk.sh TAG [--prof]` — сборка полной конфигурации (`SRB2_PS2_NO= SRB2_PS2_HW=1`, `--jobs 2`) в `build/out-TAG` (`SRB2_PS2_LTO=0` для быстрых функциональных проверок:
  там два файла (`ps2_curl.c`, `d_netfil.c`) просят `-Wno-format-truncation`, mk.sh это делает).
* `build/vu/run.sh NAME TAG DEMO_00n [арг. движка]` — таймдемо в PCSX2, `python3 tools/ps2/hwsum.py --skip 1 NAME` — среднее / максимум окон 1..9.
* `build/vu/snap.sh NAME TAG MAPxx k100 [арг.]` — снимок карты (`-hwfbh 200`, 1:1), `build/vu/ab.sh TAG "карты"` — снимок с путём EE (`-hwdbg 268435456`) и с VU1, число различных пикселей.

## 2. Этап 1 — VU1 по умолчанию, палитровый свет с резкой по рядам на VU1 (PS2-HW-100)

### 2.1 Что сделано
* `src/ps2/hw/vu1/ps2_hw_vu1.vsm` написана заново (600 инструкций): трансформ, классификация по 6 плоскостям (guard band), отсечение Сазерленда–Ходжмана в общем цикле по таблице плоскостей
  (таблица загружается при старте VU1 и лежит в памяти VU1 всё время; код стал вдвое короче — 12 вариантов макроса не помещались в диапазон ветвления ±1024 инструкций),
  перспективные ST/Q, деление, Z, упаковка пакета GIF (ST, RGBAQ, XYZF2 или одни XYZF2 для плоских), XGKICK, двойная буферизация выхода.
* **Палитровый свет на VU1 без резки на EE:** программа сама считает ряд colormap по формуле SRB2 (`row = clamp(floor(max(base − K80/(lightz+1), cap)), 0, 31)`, `lightz = clamp((w − near)·kz/16, 0, 127)`)
  для минимальной и максимальной глубины полигона после отсечения; если ряды разные, режет полигон плоскостями `w = T_m` (T_m — глубина, где ряд становится m: одно деление на ступень) и каждый
  кусок выводит с A+D-пакетом `TEX0` (CBP ряда, CLD = 1) перед пакетом веера. Таблица TEX0 рядов (по QW на ряд) приходит с константами плана; драйвер гарантирует, что CLUT рядов `[rlo, rhi]` этой
  таблицы света есть в VRAM (`prow_blk`: слот проверяется по ключу, обычный `clut_get` при промахе).
* EE: `ps2_hw_vu1.inc` переписан: `vu_plan_setup` (ряды, состояние GS `pass_setup`, константы), `vu_poly` (проверка размаха UV, заголовок и вершины в чанк), чанки через UNPACK/MSCAL как раньше.
  VU1 теперь по умолчанию (`-hwdbg 268435456` = `HWDBG_NOVU1` выключает: путь EE как раньше, для A/B); `-hwvu1` ничего не делает.
* Пригодность к железу: константы плана идут за `FLUSHE`; `MSCAL` идёт за `FLUSH` (пакеты состояния PATH2 исполнены GS до пакетов PATH1 программы); каждый `DIRECT` за `FLUSH` (было);
  индекс выходного буфера и ряд, который держит GS, лежат в памяти данных VU1, а не в регистрах (между запусками ничего не предполагается о регистрах);
  следующий `XGKICK` ждёт предыдущую передачу, буфер переписывается только после него.

## 2.3 Этап 2 — свет на полигон, один открытый чанк для одиночных рисований, единые ряды CLUT (PS2-HW-101..106)
* `PS2HWD_PalLit` (PS2-HW-106): для палитровых полигонов уровень света больше не часть ключа батча. Заголовок полигона VU1 (QW0.y) несёт `light_level` сектора; программа считает `cap`/`base` ряда
  из него (константы `K_LIGHTB`). Партии больше не режутся по сектору: DEMO_001 248 → 76..95 батчей на кадр. `PS2HWD_DrawFans` получил тройки (first, count, light) (`hw_batching.c`, файл роли GEOM, правка только `#ifdef PS2`).
* PS2-HW-101: `H.clut_epoch` (+1 при каждой сборке CLUT-образа) — по нему проверяется, что таблица TEX2 рядов (`VU.rt`) по-прежнему указывает на нужные блоки VRAM; без пересчёта на каждый батч.
* PS2-HW-102: после записи CLUT-образа в VRAM идёт `TEXFLUSH` (на железе кэш текстур GS иначе может держать старую палитру; PCSX2 этого не показывает).
* PS2-HW-103: одиночные рисования (`hw_DrawPolygon`: HUD, тени, спрайты вне батча) идут на ту же программу VU1. Чанк остаётся открытым между вызовами; кто пишет в кольцо иначе (`pk_alloc/pk_ref/pk_flush`) — закрывает его сам.
  Рисование с тем же ключом плана (`vukey_t`, 28 слов) присоединяется к открытому чанку без `begin_draw` и без констант.
* PS2-HW-104: VU0 (макро-программа планировщика/трансформации) грузится лениво при первом использовании.
* PS2-HW-105: ряды CLUT «keyed» и «plain» различаются только записью 255. Текстура карты/плоскость без индекса 255 использует keyed-ряды в обоих вариантах → вдвое меньше CLUT-слотов; на DEMO_001 была
  «пробуксовка» кэша CLUT (84 сборки CLUT на кадр, `prow_ensure` 1.2 М) — пропала (rows=0..2).

## 2.4 Этап 3 — смена плана вместо нового плана, один проход копирования, цикл по партии (PS2-HW-107, 108)
* PS2-HW-107 (retarget). Одиночное рисование (HUD: глифы шрифта, спрайты, тени) и партия, чей план отличается от плана предыдущего рисования VU1 только текстурой того же рода (psm, вид палитры, wrap, npot, region,
  фильтр) и, при свете по рядам, уровнем света, больше не вызывают `begin_draw_inner` и пересылку констант: `vu_retarget` меняет `P.r/tsx/tsy/clamp` и LRU текстуры, `vu_retex` пишет только TEX0/TEX1/CLAMP (остальные регистры
  те же: `H.serial` не менялся), константы остаются в памяти VU1 (для рядов отправляется одно QW K_INT: ряд, который держит GS). Масштаб текстуры (`tsx, tsy`) теперь едет в заголовке полигона (QW1.z, w): программа
  читает его на каждый полигон, поэтому один чанк может нести полигоны разных текстур одного плана. Ключ плана — 32 слова, сравнение по двойным словам (`vu_key_cmp`: 2 = то же, 1 = смена текстуры/света, 0 = другой план).
  `-hwnoretarget` / `-hwnobretarget` / `-hwbretmask N` — выключатели для A/B (одиночные+партии / только партии / по видам).
* PS2-HW-108. `vu_poly` — один проход по вершинам (размах s, t для UV_EXTENT считается при копировании; слова w и нулевые слова вершин не пишутся: программа берёт w = 1.0 из VF00); `vu_fans` — цикл по
  всей партии с локальными значениями плана (запасной путь `vu_poly` для первого полигона плана, полного чанка, необычного размера); `vu_plan_setup` вынесен из горячего пути (`noinline`: меньше сохранений регистров).
  Чанк остаётся открытым и после партии (PS2-HW-103); `begin_draw` закрывает его первым делом: открытый чанк меняет состояние GS (ряды CLUT, RGBAQ), а кэш состояния должен быть таким, каким он станет, до того как новый
  план решает, что писать.
* Из-за этого же правила `P.serial = H.serial - 1` ставится после рисования полигона общим путём внутри плана VU1 (общий путь мог загрузить другой ряд CLUT).

### Как сравнивать картинки (важно)
A/B путь EE против VU1 по кадрам таймдемо корректен только при одинаковой «форме» командной строки обоих прогонов: добавление или отсутствие любого последнего аргумента (даже `-hwfbh 200` второй раз) сдвигает
соответствие кадр → такт игры, картинки расходятся на 800..5000 пикселей без всякой причины в драйвере. Поэтому `abd.sh` теперь даёт обоим прогонам по одному последнему аргументу (`-hwdbg 268435456` для EE, `-hwdbg 0` для VU1).
Результат (сборка этапа 3, EE против VU1, пикселей из 64000 на кадрах f150 / f450 / f750): DEMO_001 4 / 54 / 10; DEMO_002 27 / 20 / 8; DEMO_003 48 / 6 / 12; DEMO_004 33 / 39 / 130 — одиночные пиксели
на ступенях ряда света и на краях текстур (арифметика VU1, PS2-HW-100). Смена плана включена и выключена: MAP01 k100 (`-hwnoretarget`) и DEMO_004 f750 (`-hwbretmask 7/0/4/3`) — 0 пикселей разницы (на других кадрах не проверялось).
`--prof`-сборки считают ещё и `PS2HWD_QuadHidden` в режиме проверки (`PS2_PROFILE`, PS2-HW-72): по сэмплеру это 0.3 М (DEMO_001) – 0.8 М (DEMO_004) на кадр, которых в релизной сборке нет; числа всех этапов и базы сняты в одной
и той же конфигурации.

## 3. Не проверено / упёрлось
* Цель «драйвер ≤ 1.5 М на кадр» на DEMO_001/002 не достигнута: 2.20 / 1.79 М. Остаток — то, что не принадлежит роли VU: вода на пути EE (`emit_water_poly`, роль FX: 45..100 полигонов, 0.15–0.42 М), `imm_prepare` крупных
  текстур вне партий и `settex_now` (роль HT, 0.2–0.5 М), планировщик уровней текстур (`plan_measure`, 0.46–0.84 М), небо (`hw_RenderSkyDome` + `clip_poly`, 0.14 М), сортировка (`HWR_RadixSort32` + `HWR_GroupSort32`
  0.3 М, файл `hw_sort.h` / `hw_batching.c`: зона GEOM, не трогалась). Часть VU: копирование полигона в чанк (~220 тактов на полигон, 0.3–0.5 М), смена плана HUD (≈1.9 К на глиф), `begin_draw` партий.
* HW всё ещё не «заметно быстрее» софта на всех четырёх демо: DEMO_001 8.71 против 8.66, DEMO_002 9.54 против 8.90, DEMO_003/004 — на 1.4–1.6 М хуже (движок, а не драйвер: bsp 2.3–3.0 М и пр.).
* Не сделано: нулевое копирование статических блоков (REF блоков VU из кэша геометрии GEOM): формат блока описан в разделе 5, производителя блоков нет; UNPACK сырых 20-байтных вершин движка (программа с фазой
  `(адрес & 15) >> 2`) — спроектирован, не реализован; единый чанк для глифов разных текстур через «записи состояния» (A+D, пересылаемые программой) — оценка выигрыша ≈0.1 М на кадр, не делалось.
* Резка света «по расстоянию» без CPU: сделана на VU1 (ряды colormap, точный палитровый путь). Проход «рампа глубины» (S/Q = глубина, сравнение с палитровым эталоном по MAD) не делался: измерения роли HF (MAD 3..12
  против ≤ 3.4 на 6 из 8 карт) показали, что рампа хуже эталона.
* На железе ничего не проверялось (только PCSX2 2.6.3, программный GS): порядок FLUSHE/FLUSH/MSCAL/TEXFLUSH сделан по документации; `UCAB`-кольцо (запись без SyncDCache) не делалось — в PCSX2 кэш не моделируется,
  выигрыш нельзя измерить.

## 5. Правки в чужих файлах
* `ps2_hw_draw.inc`, `ps2_hw_gs.inc`, `ps2_hw_vif.inc` — файлы роли VU (по брифу).
* `src/hardware/hw_batching.c` (роль GEOM): только `#ifdef PS2` — `HWR_DrawBatch` передаёт `count/3` и тройки (first, numVerts, light_level); хэш пересчёта батча не учитывает `light_level`, когда
  `PS2HWD_PalLit(...)` истинно. Интерфейс к кэшу геометрии GEOM: блок VU1 = заголовок (QW0: n, light; QW1: sb, tb, tsx, tsy), по 2 QW на вершину (x, y, z, не читается / s, t, не читаются).
* `ps2_hw_tex.inc` (роль HT): `clut_build_into` (эпоха), `clut_write` (TEXFLUSH).
* `src/hardware/hw_sort.h` (общий чистый код, им пользуются hw_main.c — сортировка спрайтов — и hw_batching.c — запасной путь сортировки батчей): `HWR_RadixSort32` (PS2-HW-109).
