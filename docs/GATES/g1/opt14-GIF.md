# OPT14, агент GIF: «при подключении к серверам включается запись GIF»

Сессия 2026-10-10, ветка `opt14-gif`, worktree `/home/user/wt/gif`, PCSX2 2.8.2. Стенд: `build/out` (PS2 ELF, без LTO для функциональных проверок),
`build/pc-net` (ПК-сборка с `-DNETSYNC_DIAG`: dedicated-сервер), `build/opt14-gif/{specs,run}`; сценарии — `tools/ps2/net_specs14_gif.py`
(`python3 tools/ps2/net_specs14_gif.py --base build/opt14-gif [имя ...]`, запуск `python3 tools/ps2/net_session.py build/opt14-gif/specs/ИМЯ.json`).

## 0. Происшествие со стендом (честно, до остального)

Сценарий `gif-mash1-sw` (мой, через `pcsrv(ms=True)` из `net_specs9.py`: ПК-сервер регистрируется на MOCK мастер-сервере контейнера) запустил ПК-сервер,
который **попытался зарегистрироваться на настоящем мастер-сервере**: в `srv/out.txt` строки `HMS: connecting 'https://ds.ms.srb2.org/MS/0/rooms/1/register'...`,
`ERROR: ... Could not resolve host: ds.ms.srb2.org` (аудит `net_session.py` пометил `real_master_server_contact`).
Запрос **не ушёл из контейнера**: имя не разрешилось (у процесса движка `net_session.py` вырезает переменные прокси, DNS наружу нет); ничего на `ds.ms.srb2.org`
не отправлено. Тем не менее это нарушение правила «регистрировать там запрещено» по намерению, и стенд надо чинить:

* причина — гонка в самом движке: `masterserver "<mock>"` из `config.cfg` вызывает `MasterServer_OnChange` -> `Set_api()` (`src/netcode/mserv.c`), а тот
  в многопоточной сборке ставит `hms_api` **из отдельной нити** (`change-masterserver`); следующая строка конфига `masterserver_room_id "1"` вызывает
  `RoomId_OnChange` -> `RegisterServer()` сразу же, и `HMS_connect` берёт ещё прежний (настоящий, по умолчанию) адрес. Результат зависит от нагрузки машины
  (раньше у NET/OPT12 это не сработало, сегодня нагрузка 4..11 — сработало);
* что сделано: сценарии этого агента **не** используют `pcsrv(ms=True)`: сервер читает из конфига только `masterserver "<mock>"`, а `masterserver_room_id 1` ему
  подаётся через stdin через 12 с (нить давно отработала); все остальные сценарии (`-connect`, OSK) идут с `masterserver "http://127.0.0.1:9/MS/0"` (мёртвый порт);
* `tools/ps2/net_specs9.py: pcsrv(ms=True)` (чужой файл) остаётся с этой гонкой — записано в раздел «правки в чужих файлах / замечания»: опасность реальна
  для любого, кто запустит `menu-browse`/`ps2host-menu` в среде с DNS наружу.

## 1. Причина (воспроизведено в Software и в Hardware)

**Симптом воспроизведён** сценарием `gif-browse-oldcfg-sw` (Multiplayer > Server browser > комната > список с mock-мастер-сервера > ПК-сервер > Join; таблица
управления «старого» конфига/ПК-`reference.cfg`: `setcontrol "screenshot" "f8" "joy7"`, второй ключ у `recordgif` свободен): в логе клиента
`PS2: record key 0 ... / Movie mode enabled (GIF).` / `Movie mode disabled; wrote 0 frames` 119 раз подряд сразу после первого блокирующего запроса к мастер-серверу
(`HMS: connecting '.../rooms'`), последнее включение остаётся: `Movie mode disabled; wrote 1465 frames (19.90 mb)` — запись шла ~42 с игры, пока не упёрлась в предел
`gif_maxsize` (20 МБ); файл `.srb2/movies/srb20000.gif` 20.9 МБ. Это и есть «при подключении к серверам включается запись GIF».
(С управлением по умолчанию PS2 то же самое событие вызывает **снимок экрана** 119 раз: `PS2: screenshot key 0`, т.к. на консоли второй ключ `screenshot` = 0 после PS2-137.)

**Что именно происходит (по шагам, подтверждено печатью `tail/head` очереди событий):**

1. В `D_ProcessEvents` (`src/d_main.c`) цикл `for (; eventtail != eventhead; eventtail = (eventtail+1) & (MAXEVENTS-1))` берёт событие в `ev = &events[eventtail]` и
   двигает `eventtail` **после** тела цикла.
2. В теле цикла меню выполняет блокирующий сетевой запрос (PS2-332: окно «Please wait» рисуется и запрос идёт сразу, не отложенной командой): `HMS_...` -> `PS2NetUI_Waiting` ->
   `Tick` -> `Poll()` (`src/ps2/ps2_netui.c`), а тот сам вычерпывает очередь событий (`for (; eventtail != eventhead; ...)`) — **начиная с события, которое внешний цикл ещё обрабатывает**
   (поэтому нажатие Cross, выбравшее пункт меню, ещё раз видно экрану «Please wait» как `confirm`), и оставляет `eventtail == eventhead`.
3. Внешний цикл возвращается и делает свой `eventtail = (eventtail+1) & 127`: теперь `eventtail == eventhead + 1` (в логе `queue tail 9 head 8`, затем 10, 11, ...), условие `eventtail != eventhead`
   истинно, и цикл **проигрывает заново всё кольцо из 127 слотов**: старые события и ещё ни разу не записанные слоты. Нулевой слот — это `ev_keydown` (значение 0 в `evtype_t`) с `key == 0`.
4. `M_ScreenshotResponder` (`src/m_misc.c`, вызывается первым, «над всем») сравнивает `ev->key` с `gamecontrol[GC_SCREENSHOT][1]` и `gamecontrol[GC_RECORDGIF][1]`; у управления без второго ключа этот слот = `KEY_NULL` = 0,
   так что каждое такое событие совпадает: либо снимок (если `screenshot[1]` = 0, как у PS2 по умолчанию), либо, если у `screenshot` второй ключ есть (старый сохранённый конфиг PS2 до PS2-137, `reference.cfg` с ПК:
   `"screenshot" "f8" "joy7"`) — **переключение записи GIF** (`((moviemode) ? M_StopMovie : M_StartMovie)()`), 119 раз подряд; нечётное число = запись остаётся включённой.
   В длинной сессии кольцо заполнено, и вместо нулей проигрываются **старые настоящие нажатия** (случайные «повторные» действия в меню) — тот же дефект.

Кроме пути с мастер-сервером тот же вложенный разбор очереди есть у экранов сети (`PS2NetUI_Begin/Step/Ready/Failed` вызываются из обработчиков меню Connect / Specify address / Host), так что дефект общий для всех
блокирующих сетевых окон; на ПК такого вложения нет (запросы там идут из главного цикла, не из обработчика события), поэтому у ПК-клиента этого нет.

Из-за чего это не замечали: сценарии стенда (`-connect`, `-padscript`) идут без меню-запросов в обработчике событий; логи 918 прежних прогонов не содержат «Movie mode», потому что у них управление по умолчанию PS2
(реакция — снимок экрана, а не запись; снимок молча пишет PCX и в логе не виден).

**Hardware, до исправления** (`build/elf-before.ELF`, `gif-browse-oldcfg-hw`): то же — `enabled 60 / disabled 59, record-key lines 119, key-0 events 119`, к моменту игры запись **включена** (последнее
переключение нечётное), клиент дошёл до `NETSYNC` с идущей записью GIF. Software, до исправления: `enabled 60 / disabled 60`, запись шла 1465 кадров, 19.90 МБ (остановил предел 20 МБ).
Число 119 — не случайность: после 8 записанных событий кольцо из 128 слотов даёт 128 − 8 − 1 = 119 ни разу не записанных слотов, их и проигрывает цикл (хост-тест `tools/ps2/evqueue_hosttest.c` даёт те же
`119 of them keydown/key 0` для старого цикла и 0 для нового).

Уточнение к шагу 2: вложенный разбор очереди в сценарии браузера — это **подъём сети** (`PS2NetUI_Begin/Step/Ready/End`: «Loading the network modules», «Waiting for the link», DHCP, «Network ready»), который
выполняется внутри обработчика нажатия (первый же запрос к мастер-серверу или `connect` из меню при первом обращении к сети после загрузки), т.е. «когда подключаешься к серверам» — первое подключение после включения консоли.
Экран «Network ready» тоже вызывает `Tick -> Poll` (опрос очереди) по 700 мс; потом внешний цикл `D_ProcessEvents` продолжает по уже проигранной очереди. Лог до исправления: `NETUI ready at frame 143` ->
`HMS: connecting '.../rooms'` -> `PS2 net: receive thread started` -> `PS2: record key 0 ... queue tail 9 head 8`.

## 2. Исправление (только PS2: `#ifdef PS2`; ПК-поведение не менялось)

1. `src/d_main.c`, `D_ProcessEvents`: событие **берётся из очереди до** вызова ответчиков (копия события, `eventtail` двигается сразу), цикл `while (eventtail != eventhead)`; вложенный разбор очереди внутри
   обработчика больше не может «перескочить» `eventhead`, а нажатие, которое запустило блокирующую работу, не видится вложенным циклом второй раз. Без вложения порядок и набор событий те же
   (хост-тест: 100 событий — по 100 в старом и новом цикле).
2. `src/m_misc.c`, `M_ScreenshotResponder` (два защитных условия, тоже PS2): `KEY_NULL` (0) — «нет клавиши» — не снимает экран и не переключает запись (пустой второй слот управления больше не совпадает с событием
   без клавиши); повтор клавиши при удержании (`ev->repeated`, USB-клавиатура) — не переключает запись туда-обратно (событие поглощается). Первое нажатие F8/F9/привязанной клавиши работает как раньше.
3. `src/m_misc.c`: две строки журнала (`PS2: record key N`, `PS2: screenshot key N`) — какая клавиша включила запись/сняла кадр (раньше не было видно, кто включил запись).
4. Стенд: `tools/ps2/net_specs14_gif.py` (сценарии), `gif_scan.py` (разбор логов), `gif_repeat.py` (N прогонов подряд), `evqueue_hosttest.c` (хост-тест цикла очереди).

## 4. Не проверено / ограничения (честно)

* **Реальная консоль (DualShock, USB-клавиатура, сетевой адаптер, настоящий мастер-сервер) не проверена**: всё — PCSX2 2.8.2 + `-padscript`/`-kbdscript` + mock-мастер-сервер контейнера. Условие воспроизведения «на железе» то же (вложенный
  разбор очереди в окне подъёма сети), но события там идут от настоящего пада; поведение исправленного цикла от пада не зависит.
* **Конфиг пользователя неизвестен.** Запись GIF (а не снимок) включается, только если у `Screenshot` есть второй ключ (`setcontrol "screenshot" "f8" "joy7"`: старый сохранённый конфиг PS2 до PS2-137, `reference.cfg`/`config.cfg` с ПК).
  С конфигом PS2 по умолчанию то же событие снимает экран (`PS2: screenshot key 0`, один `.pcx`). Исправление закрывает обе ветки (и случай, когда у пользователя вообще другая привязка), но «именно такой конфиг у жалующегося» — предположение.
* Золотые кадры (`golden_full.sh`) сняты на ELF без LTO (`--ps2ref`, `SRB2_PS2_LTO=0`); на релизной LTO-сборке golden не гонялся (код правок не участвует в демо; сборка LTO проверена только линковкой и сетевыми прогонами).
* ПК-поведение не менялось (правки под `#ifdef PS2`); у ПК-клиента той же проблемы нет: вложенного разбора очереди внутри обработчика события там нет. Скрытый дефект «ключ 0 совпадает со свободным вторым слотом»
  в `M_ScreenshotResponder` общий для ПК (при `screenshot[1] = joy7` по умолчанию любое событие key 0 переключает запись) — на ПК его не трогали, событий key 0 там нет.
* Запись, начатая сервером через Lua (`COM_BufInsertText(p, "startmovie")`, команды `startmovie`/`stopmovie` помечены `COM_LUA`), не меняется: это тот же путь, что и явная команда игрока в консоли.
  `gif_rolling` только продолжает уже начатую запись после предела `gif_maxsize` (по умолчанию Off).
* Заглушённый эффект исправления: нажатие, запустившее подъём сети, больше не «подтверждает» экран «Network ready» (раньше то же событие повторялось вложенным циклом и пропускало 0.7 с показа) — экран теперь показывается свои 0.7 с.
