# Exact AP_88 byte gathering, iteration 5, 2026-11-14

This component changes only the byte-gather operation in `fill_ap88` in
`src/ps2/hw/ps2_hw_tex.inc`. The reference is the immediately preceding
cumulative source at `build/nov14-next5/baseline-src/src`, verified by
`tools/ps2/prepare_next5_baseline.py`. Git HEAD is older and is not the
comparison baseline. The preceding REGLIST, compact free-list, direct CLUT,
alpha conversion and footprint changes remain intact.

## Exact operation and bounded source audit

The existing fast loop loads four AP_88 index/alpha pairs in one aligned
64-bit load. It gathers every second byte with shifts, masks and ORs, once
for the indices and again for alpha when alpha matters. The EE's `PPACB`
instruction directly gathers the low byte of each halfword. The new inline
`ap88_gather` returns only its low 32 bits, so output byte `j` is exactly
`(v >> (16*j)) & 255`, for `j = 0..3`. Input register bits above bit 63
cannot affect these four output bytes. The portable branch retains the
original C expression.

The same helper gathers alpha from the existing `v >> 8`. It does not change
the old zero-alpha detection, byte order, index-255 handling, chroma-key mode,
rounding or palette interpretation. Every nonzero mode continues to ignore
alpha. No floating-point operation is changed.

`gs_next5_hosttest.py` mechanically verifies that removing the helper and
restoring its two call expressions reconstructs the **entire frozen texture
source byte-for-byte**. It checks the caller counts as well. Consequently,
the existing `dx == 0`, 8-byte source alignment, width and debug predicates
remain unchanged. `x4 = W2 & ~3u` still bounds the same four-texel loads;
the same scalar loop handles the final 1..3 texels. Both aligned stores and
the existing unaligned copy remain unchanged. The helper adds no memory
accesses and requires no additional source padding.

The sole selection of `fill_ap88` is the AP_88 case of `tex_upload`.
`upload_bands` invokes the chosen callback for each uploaded row. Both of
these functions, the source row/column calculations, source classification,
formats, dimensions, planner, allocator, packet construction and DMA ordering
are unchanged. The bounded audit is retained as `caller-audit.json` in both
fixture output directories.

## Production-source verification

```sh
source /workspace/.onboarding/environment.sh
python3 -B tools/ps2/prepare_next5_baseline.py
python3 -B tools/ps2/gs_next5_hosttest.py \
  --out build/nov14-next5/gs-next5-host \
  --base-src build/nov14-next5/baseline-src/src \
  --sanitize --negative-controls
```

The script extracts the actual frozen/current functions without editing their
implementations, places them in separate non-LTO translation units and calls
both with identical live source/context contents. A third translation unit
also checks an independent per-texel oracle, all destination canaries and
unchanged source bytes. Every possible 16-bit index/alpha pair occurs in each
of the four packed lanes, in both modes. Other cases cover all widths 1..1024,
seven source alignments, all eight destination alignments, short tails,
arbitrary alpha, zero/opaque/mixed alpha, decimation, cropped-width source
strides and the existing `FX3_NOFILL` and compose-debug branches.

Ordinary and ASan/UBSan host runs each pass **259,092 row cases and
63,569,830 output pixels**. All four negative controls are detected: a changed
index bit, a wrong alpha-byte shift, a corrupted source alpha and an oversized
four-texel tail. The host executes the portable gather branch; the EE proof
below executes the actual `PPACB` branch.

  --out build/nov14-next5/gs-next5-ee \

  --summarize build/nov14-next5/gs-next5-ee/run.log

EE GCC 15.2 uses the normal `-O2 -G8 -mno-abicalls` integer ABI. The two
production versions and the fixture remain in three separate non-LTO
translation units, with no cross-version folding or constant propagation.
Builds pass `-Werror`; linking retains the existing SDK abicalls warning.
Disassembly confirms two native `PPACB` sites in the current row loop.

The standard 32 MiB PCSX2 profile reaches `GS NEXT5 DONE`, exit code 0.
Before timing, the native branch passes **140,944 exact/oracle row cases and
1,733,071 output pixels**, including the complete index/alpha byte-pair set
in every packed lane. Source bytes and all destination canaries match. The
EE matrix reduces the exhaustive width sweep to 1..65 plus the same large
edge widths; the host matrix retains all 1..1024 widths.

4/16/64/256/1024 and tail widths 5/7/31/127, with aligned and unaligned

These measurements concern the complete row-filling helper, not whole

No DMA/GIF byte count or GPU work is reduced.

## Code and memory

In the separate-TU EE fixture, the complete generic row function shrinks
**1124 to 980 bytes**, a reduction of 144 bytes. Each text section includes
the same additional four bytes of alignment padding. The conditional fast
branch's stack frame shrinks **64 to 16 bytes**; branches that previously
returned without a frame continue to do so. The two existing debug counters
remain eight BSS bytes in both versions.

There are no new persistent buffers, data/BSS, allocations, scratch capacity
or VRAM requirements. The helper is inlined and introduces no call frame.
`code-size-report.json`, EE disassembly, object sections and all source/build
hashes are retained in the EE output directory. Full-engine LTO section sizes
are integration results measured separately by the coordinator.

Read-only inspection of the **final linked Hardware ELF** confirms the
change in its actual `fill_ap88`, independently of the isolated fixture:

| Actual linked function | Frozen Hardware | Final Hardware | Change |
| --- | ---: | ---: | ---: |
| Function text | 1380 B | 1220 B | −160 B |
| Conditional stack frame | 48 B | 16 B | −32 B |
| Native `PPACB` sites | 0 | 3 | +3 |

LTO separates the keyed loop, which has one gather, from the alpha-aware
loop, which has two. The helper remains inlined, with no standalone
`ap88_gather` symbol. The initial decimation/source-alignment rejection still
branches before frame allocation. These are actual linked function and
static-frame measurements; the isolated timing percentages are not assigned
to the full engine.
