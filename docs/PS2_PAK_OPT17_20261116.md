# Lossless PAK layout candidate, optimization 17

The fresh `build/pak-opt17` game packs occupy **188,952,576 bytes**, down
**1,150,976 bytes (0.605%)** from the immutable `build/pak` reference. The
decoded data, stored compressed data, entry names/order, name pool, head table
and CRC table are unchanged. Directory payload positions change. Runtime RAM and VRAM consumption change by **0
bytes**. This is a disk/ISO footprint optimization.

The candidate also exposes a locality tradeoff: an exhaustive directory-order
reader scan performs more device reads. Gap filling therefore remains an
explicit `--fill-gaps` option; the previous append-only layout remains the
default. Native gameplay acceptance remains necessary before changing that
default. The pack bytes are proven
lossless; a general loading-speed improvement is not claimed.

## Existing compression and the selected change

The preceding cooker already uses LZ4HC level 12, 64 KiB decoded blocks,
whole-payload deduplication, a 90% acceptance threshold, raw tiny/Ogg entries,
and a first-use storage-order list. Searching HC levels 9–12 improves the
existing compressed payloads by only **122 bytes total**. Exhaustive suffix
sharing of the name pool saves only **100 bytes total**. Neither adds enough
value to justify a new production path. The 88.32-second host compression
survey and per-pack results are in the JSON evidence.

The selected candidate reuses otherwise empty padding before sector-aligned
large lumps. In one directory-order pass, a later small lump can occupy a
previous gap if its existing payload fits at a 64-byte-aligned offset. The
best-fitting available gap is selected deterministically; the unused tail
remains available. Lumps in `tools/ps2/lump_order.txt` never occupy gaps.
Their original positions and stored bytes remain exactly identical, including
aliases to their payloads. New gaps are created only by the existing alignment
rules.

This changes no format version, codec, block size, decompressor, alignment
requirement, entry numbering, file type, physics data or rendering data.
Version 1 retains monotonic placement. The optional TEXC cooker is unchanged.
The default and `--no-gap-fill` reproduce the previous game-pack layout byte
for byte.

## Executed correctness checks

`tools/ps2/pak_layout_verify.py` performs independent Python decoding and then
compiles the actual `w_pack.c` with system liblz4. Its host fixture extends the
existing reader test only to emit the literal full decoded output. It does not
substitute a model of the production reader.

* **15,052 entries and 401,801,745 decoded bytes** compare literally against
  the original packs. Every stored payload also compares literally. Ordinary
  archive entries compare literally with the source pk3; the 15 cooked PNGs
  additionally pass the existing independent pixel/transparency/offset model.
* All **1,370 first-use entries**, including **1,313 distinct nonempty
  payloads**, retain their exact offsets. Entry names, order, sizes, codecs,
  long names, head bytes and per-lump CRCs remain identical.
* Real C reader output matches the original pack output byte for byte, with
  **300,940 partial reads per corpus run**, unaligned destinations and red
  zones. The candidate is repeated under ASan/UBSan after dropping all head
  tables, so every read takes the file path.
* A focused nine-entry gap fixture verifies protected ordering, raw and LZ4
  payloads, empty entries, aliases and byte-identical idempotent recooking.
* **26 malformed/version/checksum rejection controls** pass through the real C
  reader under ASan/UBSan. The existing v1/v2, dedup/order and headless fixtures
  also pass.
* A payload is deliberately changed and its CRC/checksum updated to make a
  structurally valid pack. The real C reader accepts that consistent pack,
  while the literal comparator correctly detects the changed decoded bytes.
  A separate valid-content startup-order regression is also detected.
* Source archives, reference packs, candidate packs and sidecars retain their
  before/after SHA-256 hashes. No assets are committed or published.

## I/O tradeoff and deployment boundary

The C test intentionally visits the directory in order and performs 20
full/partial range checks per nonempty lump plus `WPack_Verify`. It is not a
gameplay trace. On its default DVD policy, SRB2 device traffic changes from
**341,475,328 to 542,670,848 bytes**, and commands from **5,458 to 8,528**.
MUSIC traffic changes from **412,299,264 to 415,379,456 bytes**. ZONES and CHARS
are identical. Packing late small lumps into distant earlier gaps explains the
additional window misses; compressed bytes and decompression work are unchanged.

A measured 32 KiB locality limit reduces the total saving to 145,408 bytes
while SRB2 scan traffic remains 1.6% higher. A 64 KiB limit saves 239,616 bytes
with 5.4% higher SRB2 traffic. Choosing the nearest unrestricted gap does not
resolve the tradeoff. These are isolated measured variants, not extra cooker
options. The unrestricted candidate is available for a native gameplay A/B
decision; the preceding layout remains available without changing assets.

SRP2 v1/v2 has **no embedded source MD5 field**. Its reserved header bytes are
preserved, and the verification JSON records the unchanged original archive
MD5s. Existing cooked-pack zero-digest handling and add-on hashing are
unchanged. No loader edits belong to this cooker change.

Moving payloads changes the entry-table checksum. That checksum participates
in existing TEXC texture keys, so an optional external `TEXC.PAK` must be
rebuilt for the selected game packs. An old TEXC has valid cache misses and
the Hardware renderer composes the same pixels; it does not select the
Software renderer. The canonical `build/pak` used here contains no TEXC pack.

## Measured next-format direction

The measured next-format experiment is a block-local modulo-256 delta
predictor for existing native DMX sound bytes. `pak_predictor_audit.py` keeps
the eight-byte header and a first-byte anchor in every 64 KiB block, compresses
the transformed bytes with the same LZ4HC 12, decodes them and reverses the
predictor. All **9,058,466 source bytes across 150 unique DMX payloads** compare
literally after inversion. Applying the existing 90% ratio rule and keeping
the old representation unless smaller admits 97 entries: unique sound payloads
would shrink from **5,673,452 to 5,115,557 bytes**, a **557,895-byte** opportunity.
This is not added to the candidate's saving. It requires a new codec/format
and a prediction pass on the EE; the current reader correctly rejects such a
codec. Its modest additional disk benefit does not justify changing the
compatible format in this pass. The model writes no game pack or decoded asset.

The separate
`docs/research/opt17/SPRITE_TEXTURE_COMPRESSION_AUDIT_20261116.md` identifies a
larger opportunity in resident canonical pixels and indexed/coverage source
buffers. That is a different storage layer from the already compressed PAK
payloads. Its measured corpus byte totals are not additional disk savings or
measured simultaneous live RAM savings; safe consumer access and ownership
adapters remain necessary.

## Reproduction and evidence

Use the existing host assets venv, with python-lz4 4.4.5 / bundled LZ4 1.9.4:

```sh
/workspace/.onboarding/assets-venv/bin/python -B tools/ps2/cook.py \
  --from-pak build/pak --out build/pak-opt17 --jobs 4 --fill-gaps \
  --log build/nov17-pak/cook-candidate.log --report build/nov17-pak/cook-candidate.json
/workspace/.onboarding/assets-venv/bin/python -B tools/ps2/cook.py \
  --from-pak build/pak --out build/pak-ref17 --jobs 4 --no-gap-fill \
  --log build/nov17-pak/cook-reference.log --report build/nov17-pak/cook-reference.json
/workspace/.onboarding/assets-venv/bin/python -B tools/ps2/pak_layout_verify.py \
  --reference build/pak --candidate build/pak-opt17 \
  --src /workspace/.onboarding/srb2-assets --rebuilt-reference build/pak-ref17 \
  --out build/nov17-pak/verify-final-optin
/workspace/.onboarding/assets-venv/bin/python -B tools/ps2/pak_predictor_audit.py \
  --pak build/pak --out build/nov17-pak/predictor.json --jobs 4
```

The committed evidence is
`docs/research/opt17/PAK_LAYOUT_RESULTS_20261116.json`. Full build logs, literal
reader output, disposable malformed controls, source snapshots, compression
survey and locality experiment remain under `build/nov17-pak`. No emulator,
console, BIOS, renderer or hardware-driver execution was used for these checks.
