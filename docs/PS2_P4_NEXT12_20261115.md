The PSMT4 prototype is **not adopted**. It preserves the tested packed texels, but its smaller residency changes inputs of the existing texture quality controller. An executed counterexample shows why a larger budget does not establish universal preservation of visible texture quality. Shipping source stays unchanged by this prototype.

The baseline is the complete 602-file source snapshot `85bd9716b1ed114d46f95831c64a87623038eeaa`, pinned by [next12_baseline.json](../tools/ps2/next12_baseline.json). [Candidate hashes](../tools/ps2/next12_p4_candidate.json), the [zero-context patch](../tools/ps2/next12_p4_candidate.patch), and [strict replay](../tools/ps2/next12_p4_replay.py) retain the investigation without editing production.

## Storage opportunity and bounded implementation

The raw stock flat census finds 409 of 1,386 square indexed flats whose every index lies in one aligned sixteen-entry band. Their source payload totals 8,796,160 bytes; halving that payload is a **corpus opportunity**, not simultaneous residency or a shipping saving. `Flats/Greenflower/Skybox/GFS_CLD3` is 1024×1024, uses band 8, and has SHA-256 `1fa8745023519eed052a0e3bea2a63b042d25d191d5ef2bfca49b07e0f5efad0`. At its existing full-size upload, its exact T8 footprint is 1,048,576 bytes and the proposed T4 footprint is 524,288 bytes.

The prototype keeps the existing P8 engine/cache source and packs low nibbles directly into the existing DMA ring. It adds no persistent packed copy, staging allocation, texture-record bytes, or VU state bytes. Packet payload is half the P8 size; this is not a measured CPU or whole-frame claim. It preserves the preceding T8 level-planning input and retries the original T8 allocation path if its P4 allocation fails.

Eligibility is deliberately narrow: regenerable P8 map/flat data, both wrap flags, known palette, at least 2,048 source texels, legal multiple-of-eight transfer width, dimensions at most 1024, one complete palette band, no index 255, and no active cap, configured texture budget, adaptive cap, or debug flags. Other data keeps the full existing path. Plain/keyed twins retain their original image sharing and CLUT policy. A P4 record stores its band in a previously unused byte.

## CLUT protocol and limits of this proof

CSA selects a bank in the **internal** GS CLUT. P4/CLD1 at the same CBP always loads the first sixteen source entries; CSA is not a source palette offset. The proposed protocol loads all 256 entries with T8/CLD1/CSA0, then selects T4/CLD0/CSA=band. Scalar setup does that before TEX0. Each VU light-row packet retains the full T8 row load and appends a T4 selector from VU data quadword 28; the correction above records that this placement overwrites a clipping mask. The existing VU row/sprite exits invalidate the tracked global CLUT identity. P4 does not enter the separate fast sprite stream because eligibility requires wrapping and that stream rejects wrapped records.

The manual evidence is Sony GS Users Manual v6.0, sections 2.6, 2.7, 3.4.7, 4.1.5, 4.3 and 8.3.4. It also requires an even indexed TBW, transfer start X multiple of four and P4 transfer width multiple of eight. The source uses the documented 128×128 page / 32×16 block geometry and retains logical texture dimensions and filtering inputs.

**No EE compiler, VU assembler, emulator, or actual GS fixture was run for this candidate.** Its VU scheduling, complete register ownership, native filtering and CLUT execution therefore remain unvalidated. The host model of CLUT selection is not a native GPU proof. There is no full LTO, linked ABI, stack, performance or peak-runtime-memory acceptance claim.

## Executed policy counterexample

Residency reaches more than the allocator. `plan_tex_touch` charges `H.unplanned_cur`; frame end computes a reserve from `U + U/7`. `tex_drop` charges `H.thrash_blk`, changing `plan_pct`. Cap restamping, upgrade budgets and emergency failure behavior are additional consumers. Preserving only the T8 comparison in `plan_too_fine` is insufficient. Reduced eviction/reupload histories can also change when an image is counted again.

The host fixture executes the literal unchanged baseline `PS2HWD_PlanEnd`, constants, histogram reduction and footprint helpers. At a 12,032-block PAL pool and `plan_pct=69`, the raw budget is 8,280 blocks. Three new map images have dimensions 1024², 1024² and 512×256; visible areas 2,000, 8,000 and 100; histogram upper edges 1/4, 1 and 1/2. Their initial exact levels are 2, 0 and 1.

| Reserve | Remaining budget | Final levels A/B/C |
|---:|---:|---|
| 3,980 | 4,300 | 1 / 1 / 0 |
| 3,468 | 4,812 | 2 / 0 / 1 |

The larger budget leaves A and C coarser. At the lower budget, the coarsening pass first reduces B, after which the existing fidelity pass has room to improve A and C. These reserves can result from fourteen unplanned 128² P8 images changing from 64 to 32 resident blocks, plus an unchanged 2,587-block unplanned contribution: `3483 + floor(3483/7) = 3980`; `3035 + floor(3035/7) = 3468`. A preceding thrashing frame can produce 69% from the existing 75% maximum. The three new map images can themselves use multiple palette bands and retain T8, so the issue does not depend on their P4 eligibility.

This proves that “less residency gives more budget, therefore no quality loss” is false for this controller. It does not claim an observed stock-game regression. Exact policy accounting must also retain the old eviction/reupload history. Duplicating the full block-owner map and maximum free-range representation would cost 32,768 + 32,772 = 65,540 additional bytes before records and CPU work, but **that duplication is not necessary**. It is only one costly representation considered during the initial investigation. The followup below reuses the existing canonical metadata instead.

## Deferred logical/physical split

A separate design keeps the existing T8 allocator, owner map, LRU, record IDs and logical `blk/nblk/psm/tbw` as the canonical reference. Physical P4 addresses and sizes would be resolved only when emitting actual GS work. The old logical admission, eviction and quality-controller quantities would keep their original meaning. There is no second logical allocator.

For image groups sorted by canonical address, let each physical span be no larger than its logical span and require no stronger alignment. Packing physical groups in that order gives each physical start an address at or below its canonical start, so every canonically admitted live set has a fitting physical layout. Existing groups can move left in ascending order, then right in descending order; with matching image order and memmove block order, each existing block need move at most once. Pending uploads, views, split groups and screen captures still require explicit handling. These are abstract layout arguments, not native GS validation.

A simple sidecar would cost `12 * rec_cap` bytes, including capacity consumed by views: 6 KiB at 512 records, 48 KiB at 4,096, and 768 KiB at 65,536. A lower-RAM representation may fit entirely in existing record padding: a hardware-bounded physical TBP in the two alignment bytes predicted at offsets 126–127 of the 148-byte EE record, P4/CSA in existing `pad2`, and target-layout alignment padding in existing `pad3`. Physical size and reverse targets can then be derived without a sidecar or target array. This requires actual target ABI assertions for every old field offset and record size; no such candidate was compiled. Record IDs must remain full width, including a safe fallback when the existing 16-bit owner-map label cannot represent one.

The costs remain substantial. One PAL-pool compaction can move up to 3,080,192 bytes, causing 6,160,384 bytes of local read/write traffic and roughly 962,560 bytes of five-qword-per-block GIF commands, before synchronization, transfer barriers and state rebuilds. Repeated insertions can repeat this work. Eagerly packing an early big image would also make later low-address small images shift it again, so a physical gap policy would need to avoid unnecessary compaction. These are bounds, not measured timings.

More fundamentally, preserving logical VRAM history alone does not preserve CPU source-cache history. Added completion fences and copied P4 ring payloads change `dc` busy/lock/release timing. `plan_too_fine` reads `dc_find` of the full-size source, and `dc_find_finer` can select a different source for the non-associative `dec_level` filter. Every cached physical address, CLUT/VU transition, overlapping raw transfer and partial-relocation recovery also needs proof.

The coordinator therefore **deferred this design for the current pass**. It is a plausible research direction, not a claim that lossless packing is impossible. The old logical quota would remain unchanged: lower physical image occupancy or upload payload would not admit extra logical images or avoid the old evictions. Leaving P4 inside its original logical slot would avoid compaction, but its unused tail must not be called reclaimed usable quota. No shipping RAM, VRAM or FPS saving is attributed to either P4 design. The separate design record is `build/nov15-next12/p4/logical-physical-design.json`; the immutable `corpus-v1` stage retains the earlier document bytes and provenance history.

## Reproduction

Replay also verifies the retained canonical `build/nov15-next12/baseline/{software,hardware}/gen/config.h` bytes. Those canonical build inputs must be present; the source exporter does not generate them.

```sh
python3 tools/ps2/prepare_next12_baseline.py
python3 tools/ps2/next12_p4_replay.py
python3 tools/ps2/next12_p4_corpus.py
python3 tools/ps2/next12_p4_hosttest.py --src build/nov15-next12/p4-replay/src --corpus build/nov15-next12/p4/corpus/full-texels.bin --negative-controls
```

The host test compiles complete texture/palette source and real source headers from the isolated snapshot, plus literal texture-register and policy functions. It decodes every upload texel, checks exact footprints, transfer alignment, initialized qword tails and TEXFLUSH ordering, and exercises fallback policies. Synthetic cases cover all sixteen bands and 32 CLUT rows across three palette values. The complete stock raw corpus is tested, with no sampling of pixels.

The retained run passes normal GCC and ASan/UBSan: **2,229 uploads, 101,357,032 texels, 101,422,023 checks per run**. Six executed mutations fail for lost index bits, wrong block geometry, wrong image length, a partial P4 CLUT preload, lost CSA and a scan that misses the final mismatching texel. The immutable report is `build/nov15-next12/p4/stages/corpus-v1/host/report.json`; the stage also retains full source/header/tool bytes, executed binaries, build/run logs, mutation inputs/results, corpus data and a 602-file source manifest. The broader resource audit is `build/nov15-next12/vram-residency-audit.json`. The actual controller counterexample passes as a rejection check in both host runs.

An earlier 843-upload development report used `p4/host` and was overwritten during corpus expansion without being archived. Its independent review remains a historical execution record, with an explicit supersession correction; it must not be read as a pin of the expanded files. The new stage manifest maps the expanded run's original paths to its preserved bytes and records this provenance limitation. No reconstruction is represented as the original early execution.
