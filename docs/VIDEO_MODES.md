# Видеорежимы PS2-порта: внутреннее разрешение и формат вывода

> Статус: контракт агента видео (агент №2). Версия 1, написана ДО реализации; числа помечены:
> **[расчёт]** — выведено из спецификации GS/gsKit/ps2sdk и арифметики, **[измерено]** — получено запуском
> (будет заполнено в `docs/GATES/g1/final-video.md`), **[не проверено]** — запуска нет. Менять номера режимов нельзя:
> на них ссылаются конфиг и командная строка.

Две НЕЗАВИСИМЫЕ настройки (обе в Options -> Video Options и в командной строке):

1. **Внутреннее разрешение** — `vid.width x vid.height`: размер индексного кадра `screens[0]` (software, PSMT8 + CLUT) и
   координатного пространства HW-рендерера. Меняется без перезапуска (`vid_mode`, меню «Set Resolution...»).
2. **Формат вывода** — как GS отдаёт картинку на телевизор/монитор: NTSC/PAL, field/frame, 480p/576p/720p/1080i,
   VESA. Определяет размер кадрового буфера GS (`fbw x fbh`, CT32, двойная буферизация) и магнификацию CRTC.
   Меняется в меню (`Output Format`) и параметром; при смене GS переинициализируется (как при переключении software/HW).

Внутренний кадр -> кадровый буфер GS: один текстурный спрайт (PSMT8 + CLUT CT32, nearest или bilinear) в прямоугольник
`dest` внутри `fbw x fbh`; затем CRTC растягивает буфер на экран целочисленной магнификацией (`MAGH`/`MAGV`).
Режим по умолчанию (**320x200 + NTSC/PAL по региону, спрайт на весь буфер, nearest**) обязан давать тот же кадр,
что и до этого документа: индексный кадр побайтно, GS-вывод — те же команды.

## 1. Внутренние разрешения (таблица A)

`modenum` — индекс для `vid_mode N`, `-vidmode N`, `VID_SetMode()`. Порядок и индексы фиксированы.
Все `W*H` кратны 64 (каждый `screens[i]` выровнен на 64 Б для DMA), `W` кратно 8.
`dup = min(W/320, H/200)` (целое, `V_Recalc`) — множитель HUD/меню; в режимах с `dup=1` и большим `W` HUD остаётся 1:1 по
пикселям (так же ведёт себя ПК-версия на нецелых разрешениях). Память: 1 экран = `W*H` Б; в `vid.buffer` лежит
`NUMSCREENS(5)` экранов подряд (`screens[i] = buffer + i*W*H`).

**Максимум для структур движка (`MAXVIDWIDTH` x `MAXVIDHEIGHT`) под `PS2`: 640 x 512** — минимально достаточное
значение для режима 10; режимов крупнее нет (800x600 и выше как ВНУТРЕННИЕ разрешения не делаются: см. §4, «стоимость»).
Сейчас в `src/screen.h` под `PS2` стоит 320 x 240; агент видео заменяет на 640 x 512. Что это делает с размерами структур
(агент №3, `r_*.c` не правит агент видео):

| структура / массив | поля, зависящие от `MAXVIDWIDTH/HEIGHT` | при 320x240 | при 640x512 |
|---|---|---:|---:|
| `visplane_t` (`r_plane.h`) | `top[W]` + `bottom[W]` UINT16 + 4 pad | 1 292 Б (+ прочее) | 2 572 Б (+ прочее) |
| `visffloor_t` (`r_plane.h`) | `f_clip[W]` + `c_clip[W]` INT16 | 1 280 Б | 2 560 Б |
| `vissprite_t` (`r_things.h`) | `clipbot[W]`, `cliptop[W]` INT16 | 1 280 Б | 2 560 Б |
| `drawseg_t` (`r_defs.h`) | `frontscale[W]` fixed_t | 1 280 Б | 2 560 Б |
| глобальные массивы | `floorclip/ceilingclip` (2xW INT16), `frontscale` (W x4), `yslopetab[H*16]` x4, `xtoviewangle[W+1]` x4, `negonearray/screenheightarray`, `spanstart[H]`, `rastertab[H]`, `tiltlighting[W]`, `ffloortexturecolumn[W]` | см. `size` ELF | +≈ 30 КБ к 320x240 [расчёт] |
| `MAXSEGS` (`r_bsp.c`) | `W/2+1` | 161 | 321 |

Итог для агента №3: разрешение 640x512 увеличивает КАЖДУЮ из четырёх «экранных» структур ровно вдвое относительно
320x(240) (в 2x по ширине); при `MAXVISPLANES`/`MAXVISSPRITES`/`MAXDRAWSEGS` из `r_plane.c`/`r_things.c`/`r_segs.c` это
прямой множитель на их пул. Если пулам нужен предел памяти, они обязаны выделять структуры по ТЕКУЩЕЙ `vid.width`, а не по
`MAXVIDWIDTH` (агент видео этого не делает; точные размеры — `sizeof` на хосте: `tools/ps2/video_hosttest.py` печатает их).
Нужно гарантировать, что при `vid.width <= MAXVIDWIDTH` и `vid.height <= MAXVIDHEIGHT` никакой код не выходит за массивы
(проверяет `tools/ps2/video_hosttest.py` с redzone на хост-профиле).

**Память `vid.buffer` (EE, не зона):** выделяется `memalign(64)` под текущий режим; при смене режима старый блок
освобождается, затем выделяется новый (если не хватило — возвращается прежний режим). Для агента №3: вне арены зоны надо
оставить запас **не менее 1 638 400 Б** (максимальный режим 640x512) + 64 Б выравнивания, помимо резерва libc. При 320x200
(по умолчанию) расход прежний: 320 000 Б.

## 2. Форматы вывода (таблица B)

Номер формата (`outid`) фиксирован; 0..2 совпадают с прежними `PS2GS_MODE_NTSC/PAL/480P` и с `PS2HWD_VIDEO_*`
у HW-драйвера. `AUTO` (-1) = 0 для NTSC-консоли, 1 для PAL (по `rom0:ROMVER`).

Параметры CRTC берутся так же, как в gsKit 1.5.1 (`gsKit_set_buffer_attributes`) — таблица `DX,DY,DW,DH` по режиму
`SetGsCrt`; `MAGH = DW/fbw - 1`, `MAGV = DH/fbh - 1` (для interlaced + frame дополнительно `MAGV--`), дальше окно центрируется.
Кадровый буфер всегда **CT32**, **двойной**; шаг строки (`fbw` для DISPFB/FRAME) = ширина, округлённая вверх до 64.
Страница CT32 = 64x32 px = 8 КБ; всего в VRAM 512 страниц (4 МБ).

Что НЕ делается и почему:
* Нативные буферы 720p (1280x720) и 1080i field (1920x1080) в CT32 не помещаются в 4 МБ (3,6 МБ и 8 МБ на ОДИН буфер);
  CT16 (потеря цвета) и один буфер (разрывы) не берём. Вместо них — уменьшенный FB с магнификацией (см. таблицу).
* VESA 800x600/1024x768/1280x1024 с нативным CT32-буфером x2 не помещаются (494 / 768 / 1280 страниц); берётся FB в
  1/2 по каждой оси, пиксель удваивается CRTC (чёткие квадраты, фильтра нет).
* Все VESA-режимы требуют VGA-выхода (RGBS/sync-on-green) и монитора; проверить их без железа нельзя, PCSX2 их
  отдельно не показывает — они помечены «не проверено» и включаются только явным выбором.
* Режимы, у которых после смены не прошла проверка VRAM или BIOS, в списке показаны как недоступные с причиной; выбор
  такого режима отклоняется сообщением, текущий вывод остаётся.

**VRAM-проверка** для пары (формат вывода, внутренний режим): `2*pages(CT32, stride, fbh) + pages(PSMT8, W, H) + 1 <= 512`.
Для ВСЕХ формул таблицы B и ВСЕХ внутренних режимов 0..10 она выполняется с запасом (максимум 437+... см. столбец
«+ текстура 640x512»: 576p 704 — 437 из 512). Остаток VRAM под нужды HW-рендерера см. §5.

## 3. Размещение кадра на экране (`vid_fit`)

`dest` — прямоугольник в пикселях FB, куда рисуется внутренний кадр. `vid_fit`:

| значение | поведение |
|---|---|
| `Fit 4:3` (по умолчанию) | на 4:3-выходе — весь FB (ровно прежнее поведение 320x200 -> весь буфер); на 16:9 (720p, 1080i и 4:3-выход при ТВ 16:9 в OSD консоли) — центрированный столбец с отношением 4:3 по отображаемому экрану |
| `Stretch` | весь FB на любом выходе |
| `Square` | пропорции внутреннего кадра как есть (квадратные пиксели: 320x200 = 16:10), вписано в экран с полосами |
| `Integer` | наибольший целый множитель внутреннего кадра, помещающийся в FB (в пикселях FB), по центру; если целого нет — как `Fit 4:3` |

`vid_filter`: `Off` = nearest (по умолчанию, как ПК), `On` = билинейный (GS `TEX1.MMAG/MMIN = LINEAR`, регион зажат
`CLAMP` по границам кадра). Параметр `-linear` оставлен.

## 4. Тракт вывода кадра и ожидаемая стоимость

Тракт: `ps2gs_present(frame, w, h)`: (1) CLUT 1 КБ только если палитра изменилась, (2) загрузка PSMT8 `w*h` байт по GIF path 3
своей цепочкой DMA с REF-тегом прямо из `screens[0]` (без копии, 64 Б выравнивание гарантировано), (3) состояние, TEXFLUSH,
спрайт `dest` из текстуры в задний буфер, FINISH. Флип в прерывании vblank (как сейчас). Текстура PSMT8 хранится
постранично (128x64 px на страницу), `TBW = 2*ceil(W/128)`, `TW/TH` — степень двойки не меньше `W/H`, область зажата `CLAMP`.

Время EE на `present` ≈ `FlushCache` + сборка цепочки + ожидание конца DMA чтения (≈ `W*H` байт по шине GIF).
**[расчёт]**: 64 000 Б — единицы–десятки мкс; 327 680 Б — в ≈ 5,1 раза больше; относительно тика (28,6 мс) < 1 %.
**[измерено]** — в `final-video.md` (COP0 Count, `ps2gs_stats_t.present_max`, PCSX2).

Стоимость software-рендера на EE (294,9 МГц; бюджет тика 8,43 М тактов) растёт примерно как число пикселей (колонки/спаны) с
добавкой на BSP/сегменты, пропорциональной ширине: оценка **[расчёт]** — множитель из столбца «отн. к 320x200» таблицы A
для заливочной части (колонки/плоскости/спрайты) и до ~1,5-2x для остального. То есть 640x400 = «в ≈ 4 раза дороже» по
пикселям. Реальные числа по фазам — **[измерено]** в `final-video.md` и сюда будут перенесены. Режимы крупнее 640x512
как ВНУТРЕННИЕ не делаются: 640x512 уже ≈ 5x стоимости эталона, а ПК-логика не рассчитана на `vid.height > 512` в массивах.

## 5. Контракт для HW-рендерера (агент №1)

* Координатное пространство `GClipRect/DrawPolygon` — `vid.width x vid.height` (внутренний режим); оно меняется при
  `vid_mode`, ТЕМ ЖЕ вызовом, что и для software: `VID_SetMode` -> `PS2HWD_SetScreenSize(vid.width, vid.height)`,
  если драйвер активен (вызов добавляется в `VID_SetMode` под `#ifdef HWRENDER`; он уже существует в драйвере).
* Размер и формат буфера GS HW-драйвер выбирает САМ (`ps2hwd_config_t.fbw/fbh/fb32`, сейчас формат вывода 0..2). Единая
  таблица форматов вывода (таблица B) будет доступна в `src/ps2/ps2_gs.h` как `ps2gs_output_t ps2gs_output(int outid)`
  (поля: `gsmode, interlace, ffmd, fbw, fbh, magh, magv, aspect, pages_fb`); HW-драйвер может брать из неё CRTC и FB.
  До тех пор HW поддерживает ТОЛЬКО outid 0..2; при активном HW выбор других форматов вывода отклоняется сообщением
  (`vid_output` применяется при возврате в software). Режим 576p/720p/1080i/VESA для HW — отдельная задача агента №1.
* Бюджет VRAM HW (CT16S x2 + Z24 + текстуры): остаток после буферов берёт сам драйвер; формулы страниц — §2.
  Для 720p (FB 640x360): CT16S x2 = 2x60 страниц, Z24 = 120 страниц [расчёт].

## 7. Поведение при смене режима

Смена внутреннего режима идёт тем же путём, что в оригинале: `setmodeneeded` -> `D_Display` (не во время вайпа) ->
`SCR_SetMode` -> `VID_SetMode` -> `SCR_Recalc` (`V_Recalc`, `V_Init`, `R_SetViewSize`, `con_recalc`, `am_recalc`) ->
`R_ExecuteSetViewSize`. На паузе, в меню, на титуле, в игре, в демо и в интермиссии поведение одинаково; кэшированные
экраны (`screens[1..4]`, `usebuffer` интермиссии) обнуляются при смене режима. Игровая логика, демо и сейвы не
затрагиваются: `vid.*` на них не влияет, кроме экранных размеров в рендере.
