## Precise GS sections for the P4 candidate

These are additional locators in the original SCE **GS User's Manual v6.0,
April 2002**, [archival mirror](https://raw.githubusercontent.com/ninjadynamics/PS2Docs/main/GS_Users_Manual.pdf).
The mirror is not a current Sony support endpoint. The web reader rejected its
content type; direct HTTPS GET and local PDF text inspection succeeded.

| Locator | Checked constraint |
| --- | --- |
| §§2.7.3–2.7.4, pp30–31; TEX0 p126 | CSM2 is documented for **PSMCT16 only**, with CSA zero. TEXCLUT placement is therefore not a documented CT32 palette-packing shortcut. |
| §3.4.7, pp55–57 | CSA selects the internal CLUT destination. A full T8 load at CSA0 followed by T4/CLD0 selects an existing bank; a T4/CLD1 load does not offset the source by that bank. TEXFLUSH is required after new CLUT storage. |
| §4.1.5, p76; §4.3, p79 | P4 start X is a multiple of four and transfer width a multiple of eight. Texel zero occupies the low nibble, followed by texel one in the high nibble. |
| §§8.2–8.3.4, pp163–168; §8.5, p171 | T4 uses 128×128 pages, 32×16 blocks and the CT16 block-number pattern. A block-relative base retains that pattern. |
| §8.6.1, pp172–173 | A separate, exact P4-to-CT32 transfer permutation is documented. It is distinct from packing adjacent source indices into nibbles. |

**Application/inference:** retaining the existing full CT32 palette rows and
selecting an aligned sixteen-entry band requires **zero additional VRAM CLUT
storage**. It also avoids adding texture-specific palettes for every light row.
This supports the narrow aligned-band proposal; it does not prove its state
tracking, VU packets or native filtering.

**Address calculation, not a runtime measurement:** for positive dimensions and
legal even `tbw`, the contiguous T4 span in blocks is

```text
w0 = w - 1; h0 = h - 1
last_page = (h0 >> 7) * (tbw >> 1) + (w0 >> 7)
span = last_page * 32 + blk_16[(h0 >> 4) & 7][(w0 >> 5) & 3] + 1
```

Here `blk_16` denotes the already present CT16 block-number table. Enumerating
the same address pattern gives these examples; payload and reserved span are
different quantities:

| Image | P8 payload / span | P4 payload / span |
| --- | ---: | ---: |
| 16×16 | 256 B / 256 B | 128 B / 256 B |
| 64×16 | 1,024 B / 1,536 B | 512 B / 768 B |
| 128×16 | 2,048 B / 5,632 B | 1,024 B / 2,816 B |
| 64×32 | 2,048 B / 2,048 B | 1,024 B / 1,024 B |
| 1024×1024 | 1,048,576 B / 1,048,576 B | 524,288 B / 524,288 B |

For example, 64×16 P4 touches blocks **0 and 2**. Reserving two consecutive
blocks would overlap another allocation. Using internal holes would require a
different allocator that tracks touched block sets and every transfer/sample
footprint; merely shortening the current range is insufficient.

## Original visibility work: one new paper and useful slide locators

**New to the existing catalog:** Tomas Akenine-Möller and Timo Aila,
[Conservative and Tiled Rasterization Using a Modified Triangle Setup](https://users.aalto.fi/~ailat1/publications/am2005jgt_paper.pdf),
author-hosted draft of JGT 10(3), 2005, seven PDF pages. The
[author's publication index](https://users.aalto.fi/~ailat1/) links this draft.
Sections 2–3, pp3–5, derive edge-function tests and select one extremal tile
corner from each edge normal. Section 3.1 and Figure 4 explain why applying
underestimation only to a mesh silhouette can admit partially uncovered pixels.
This is an original algorithm paper, not a GS capability claim.

**Application/inference:** a future software coverage buffer must overestimate
the candidate object's coverage and underestimate proven opaque occluder
coverage. A coarse bounding rectangle around a wall with a hole, a translucent
FOF, or a union of partially covered triangles cannot serve as a solid blocker.
Increasing coverage-buffer resolution alone does not prove conservative
occlusion. No such buffer is implemented here.

The already catalogued Colin Hughes/SCEE
[PlayStation 2 Clipping](https://lukasz.dk/files/final-gdc2002-clippingps2.pdf)
has these more useful exact slide locators:

| PDF slide | Practical constraint |
| --- | --- |
| 22; 27 | Negative homogeneous `w` creates misleading X/Y regions; near/Z handling precedes full side-plane clipping. |
| 26 | The guard-band shortcut relies on valid small primitives and GS scissoring. It does not establish rejection of an intersecting large primitive. |
| 34 | A bounding volume wholly inside the clip volume permits a path without per-triangle clipping. |
| 35 | Different transform arithmetic on clipped and unclipped paths can create boundary cracks. |

For this renderer, the safe immediate use is conservative earlier rejection or
acceptance of a bound derived from its actual transform. Sprite frame offsets,
rolling/paper transforms, attachments and alternate views still belong in the
bound. The paper does not supply SRB2-specific bounds.

## Read-only policy audit and bounded conclusion

The GS evidence supports exact index storage; it does not remove the existing
resource-policy counterexamples. In this baseline:

* `plan_tex_touch` in `ps2_hw_draw.inc` classifies planned palette images using
  **`psm == PSM_T8`**, and charges `nblk` to unplanned reserve otherwise.
  Changing the storage enum alone changes that classification.
* `tex_drop` in `ps2_hw_tex.inc` charges current-frame eviction footprints to
  `H.thrash_blk`; `plan_frame_end` changes the next planner percentage from it.
  Reserving fewer blocks can change which evictions occur even if an individual
  level comparison retains its P8 footprint.
* `dc_find_finer`, `dc_slot`, `rel_poll`, and `dec_level` connect packet/source
  lifetime to the selected cached level and its bytes. Eligibility restricted
  to full-size P4 uploads does not isolate unrelated textures from that history.

Thus no new source found here justifies claiming a general P4 residency saving
with unchanged texture choices solely from narrower eligibility. A shipping
candidate needs the actual level/source-history comparison and native CLUT
fixture being investigated separately. Smaller IMAGE payloads establish a
transfer-size opportunity, not smaller total RAM, higher FPS, or a safe return
of the saved blocks to the current quality controller.

A separate future bitplane lead preserves the current CT32 framebuffer alpha:
the driver already requests **Z24** in `ps2_hw_gs.inc`. The original-author
[Fobes article](https://fobes.dev/ps2/fragmenting-memory-with-the-ct24-format)
explicitly includes Z24 alongside high indexed formats. The GS manual's
§8.3.1 p164 distinguishes Z24 and CT32 block permutations; high indexed formats
follow CT32. **Inference:** only after proving absolute block/bit ownership,
all Z clears/transfers, cache invalidation and sampling can a Z24 high-byte
overlay be considered. This does not require reducing the existing depth
precision or allocating another palette, but is not an accepted change or a
new physical-memory measurement.
