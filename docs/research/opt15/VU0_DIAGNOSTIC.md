# VU0: известные outcode differences и остаточная точность

Дата: 2026-11-15. База: `e10593b0d`, EE GCC 15.2.0, PCSX2 slot0,
обычная конфигурация 32 MiB. Это проверка EE/VU0 в эмуляторе; отдельного
подтверждения на физической PS2 нет.

**Причина сигнатуры `outcode_diff=24625/49152` установлена: диагностический
hook пропускал ленивую загрузку констант VU0.** Исправлен только
`PS2HWD_TestVU0`: после `begin_draw` он загружает те же константы, что
`vu0_need` в производственном пути `emit_poly`, с прежним negative control `256`.
Инструкции `vu0_xform` / `vu0_xform2`, скалярный oracle и допуски не изменены.

После исправления outcodes совпадают на всех 49 152 вершинах. Однако старый
строгий тест **по-прежнему FAIL**: впервые осмысленно измеренные максимумы
`dZ=86` и относительная ошибка `1/w=3.61343e-05` превышают прежние границы
`8` и `2e-6`. Эти расхождения оставлены видимыми. Утверждения о полном
совпадении VU0 со скалярным преобразованием или об исправлении производственной
арифметики здесь нет.

## Воспроизводимая проверка

[`tools/ps2/vu0_diagnostic.c`](../../../tools/ps2/vu0_diagnostic.c) включает
настоящий `ps2_hwd.c`, чтобы использовать его статические функции.
`hw_test.c` в отдельном объекте предоставляет обычные engine stand-ins.
Дополнительные stand-ins в diagnostic имеют weak linkage для совместимости
со старыми версиями fixture. Код не меняет производственные функции при сборке.

Проверяются одни и те же 12 seeds и 4096 вершин на seed:

1. Настоящий `PS2HWD_TestVU0` без и с неправильным масштабом X (`256`).
2. Точное воспроизведение пропущенного preload: константные регистры VU0
   обнуляются, затем вызывается `begin_draw`, после него — `vu0_xform` напрямую.
3. Те же вершины с `vu0_need` после `begin_draw`.
4. Побитовое совпадение single/pair, snapshots `vf1..vf4`, `vf8`, `vf11..vf13`,
   число видимых в обоих путях вершин, и независимый outcode через шесть прямых
   сравнений. Последний проверяется отдельно на scalar и VU clip coordinates.
5. Ввод и промежуточные значения двух наиболее расходящихся видимых вершин.

Текущий код запускается так:

```bash
source /workspace/.onboarding/environment.sh
source /workspace/.onboarding/emulator-env.sh
SRB2_PS2_OUT=build/opt15-vu0/config python tools/ps2/vu0_diagnostic.py \
  --out build/opt15-vu0/fixed
```

**Ожидается exit 1**, поскольку численные границы не ослаблялись. В
`report.json` поле `diagnosis_passed=true` означает, что объяснение missing-load,
константы, outcode oracle и negative control проверены; `passed=false`,
`standard_strict_gate=false` и `loaded_strict_gate=false` сохраняют остаточный
сбой точности. Это разные результаты, а не переклассификация FAIL в PASS.
`--expect-baseline` применялся к исходному hook до исправления и разрешает только
его точную известную сигнатуру, сохраняя loaded projection FAIL.

Повторный анализ сохранённых логов без занятия emulator slot:

```bash
python tools/ps2/vu0_diagnostic.py --out build/opt15-vu0/baseline \
  --expect-baseline --analyze-only
python tools/ps2/vu0_diagnostic.py --out build/opt15-vu0/fixed --analyze-only
```

Compile/link output проверяется на diagnostics, кроме известного
`abicalls/non-abicalls` предупреждения для VU1 assembler objects.
`commands.json` сохраняет команды компилятора, `report.json` — SHA256 исходников
на момент сборки, ELF, parsed metrics и статус wrapper. Emulator использует
исходное окружение вызывающего shell: `build.ENV` намеренно сужает PATH для SDK
и исключает локальный `xvfb-run` из onboarding runtime.

## Что показал EE

| Метрика | Без `vu0_need` | После `vu0_need` |
|---|---:|---:|
| Вершины | 49 152 | 49 152 |
| Разные outcodes | 24 625 | 0 |
| Scalar visible | 23 005 | 23 005 |
| VU visible | 0 | 23 005 |
| **Common visible, реально сравнены X/Y/Z/q** | **0** | **23 005** |
| VU clip `w == 0` | 49 152 | 0 |
| Seeds с неверными constant snapshots | 12 из 12 | 0 из 12 |
| Direct-comparison oracle differences, scalar / VU | 0 / 0 | 0 / 0 |
| Single/pair differences | 0 | 0 |
| max dX / dY / dZ | 0 / 0 / 0, сравнений нет | 1 / 1 / 86 |
| max relative `1/w` error | 0, сравнений нет | 3.61343e-05 |
| max absolute clip-coordinate delta, все вершины | 5114.49 | 0.000976562 |

При нулевой матрице VU0 получает `w=0`; ветка `d->w <= 0` возвращает `63`.
В наборе ровно 24 625 scalar outcodes отличаются от `63`, что даёт опубликованную
сигнатуру. Single и pair используют одни и те же неверные константы и потому
совпадают. Условие `oc == 0 && oc2 == 0` ни разу не выполнено: прежние нулевые
максимумы координат не измеряли точность.

Настоящий hook до исправления даёт ту же сигнатуру. Исправленный hook даёт
`outcode_diff=0`, `pair_diff=0`, `max_dx=1`, `max_dy=1`, `max_dz=86`,
`max_q_rel=3.61343e-05`, как независимая loaded-фаза. Negative control до и после
исправления ловится: `max_dx=278`. Он и раньше явно загружал константы, что
объясняет, почему испорченный масштаб мог измеряться при пустом обычном сравнении.

## Остаточные worst cases

Максимальная относительная ошибка q: seed **9**, index **3573** (с нуля).

| Значение | Scalar | VU0 |
|---|---:|---:|
| clip x | -80.6672363 | -80.6672363 |
| clip y | 32.2160645 | 32.2161255 |
| clip z | 11.7475586 | 11.7480469 |
| clip w | 13.5471191 | 13.5476074 |
| q | 0.0738164335 | 0.0738137662 |
| Packed X/Y/Z | 20076 / 30290 / 1114319 | 20077 / 30291 / 1114280 |

Вход: `(118.061279, 1425.05408, 3356.89844)`.
Члены scalar суммы w:
`75.1296844 + 76.4734268 + 2583.20679 - 2721.2627`.
Разница w около `0.0004883` становится относительной разницей q около `3.6e-5`
после взаимного вычитания членов порядка нескольких тысяч.

Максимальное dZ: seed **6**, index **3516**. Вход
`(2088.21118, 267.891357, 1522.95068)`; scalar/VU clip z равны
`11.5773926 / 11.5776367`, w — `13.3769531 / 13.3770752`, packed Z —
`1128494 / 1128408`. X/Y совпадают. Члены суммы w:
`1575.98157 + 132.579132 + 655.924744 - 2351.1084`.

Скалярная функция прибавляет translation последней; VU0 начинает с translation
и затем накапливает x/y/z. Округление FPU и VU также отличается. Наблюдения
согласуются с чувствительностью к порядку суммирования и округлению при
вычитании близких величин. Они не доказывают отдельную ошибку `vdiv`, аппаратную
ошибку PS2 или проблему сохранения регистров. Точную долю каждого источника
ошибки и последствия в игровых сценах этот ограниченный probe не устанавливает.
Это отдельный численный вопрос, сохранённый как strict FAIL, а не продолжение
прежней missing-load ошибки harness.

## Компактная реализация hook

Ниже сохранён ход измерения компактного варианта. В итоговой сборке helper
используется только для двух вызовов парной correctness-проверки; последний
scalar-correctness transform снова прямой. Так убран один вызов на вершину
вне timed loops. Также удалены лишнее накопление `xs` и условное искусственное
`n++`: volatile asm с memory clobber и используемые `oc/pv` уже сохраняют
вычисления и stores. Последовательность 120 COP2-инструкций, включая 12 stores
в самом TestVU0, при этом сохранилась.

EE `-O3`: pair-only вариант занимает 3508 байт (3320 + helper 188), итог после
удаления `xs` — **3484 байта**, на 116 меньше исходного hook. Полная итоговая
сборка сохраняет базовые `_end` и `_gp`, без padding или изменения резервов.
Её diagnostic stack достигает 640 байт (caller 624 + helper 16) против исходных
608; ordinary game stack этим hook не затрагивается. Отдельное evidence:
`build/opt15-vu0/pair-helper-size/` и `build/opt15-vu0/no-xs-size/`.

Первое исправление вызывало `vu0_need`, затем при negative control повторно
встраивало `vu0_batch_load`. Дополнительный код диагностики повлиял на границу
ELF и доступный начальный размер арены, поэтому эта избыточность убрана:

- Один безусловный `vu0_batch_load` выбирает X scale как
  `(ps2hwd_dbg_flags & 256) ? P.kx * 1.01f : P.kx` и устанавливает
  `P.vu0_ld = 1`. `P.kx` скалярного эталона и `P.vu0` не меняются.
- Три вызова одиночного transform вне измеряемых циклов используют частный
  `noinline` helper `test_vu0_vertex`, вместо трёх встроенных копий. Измеряемый
  одиночный цикл вызывает `vu0_xform` напрямую; измеряемый парный цикл не изменён.
- Производственные helpers, инструкции transform, число входных вершин,
  допуски, размеры пулов и резервы не менялись.

Реальный EE GCC 15.2.0, `-O3 -G8 -mno-abicalls`, размеры машинного кода:

| Вариант | TestVU0 + частный helper |
|---|---:|
| Исходный hook с пропущенным preload | 3600 B |
| Первое корректное исправление | 3808 B |
| Только один preload | 3608 B |
| Один preload и общий helper для correctness | **3336 B** (3148 + 188) |

Таким образом, диагностический код уменьшен на **472 B** относительно первого
исправления и на **264 B** относительно исходного неисправного hook. Варианты
одного preload с ternary, локальной веткой и множителем дали одинаковые
3608 B; выбран ternary, который оставляет обычный `P.kx` без умножения.
Размеры из препроцессированных вариантов подтверждены отдельной компиляцией
окончательного исходного `ps2_hwd.c` без препроцессирования: diagnostics 0,
`PS2HWD_TestVU0=0xc4c`, `test_vu0_vertex=0xbc`.
Артефакты codegen: `build/opt15-vu0/preload-size/{sizes.json,final-build.log,final.o}`.
Размер полного linked ELF и начальная арена проверяются общей интеграцией.

Финальный EE/PCSX2 запуск находится в `build/opt15-vu0/compact/`. Все parsed
metrics normal, negative control, no-load и loaded численно совпали
с предыдущим `fixed/report.json`: `common_visible=23005`, `max_dx=1`,
`max_dy=1`, `max_dz=86`, `max_q_rel=3.61343e-05`; negative control даёт
`max_dx=278`. `diagnosis_passed=true`, `passed=false`, exit 1 сохранены.
Worst cases также не изменились.
