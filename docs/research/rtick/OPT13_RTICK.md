## Резюме (≤ 15 строк)

1. **Что измерено.** Такты EE (PCSX2, `RT_EEPROF`: тик, пары, типы, ряд по тикам), точные счётчики хоста (`RT_CENSUS`), кэш-модель (callgrind с геометрией EE), три прототипа с проверкой побитности на 4 демо: O(1)-интерполятор, горячая раскладка полей, «спящие пары». Продукт не менялся; патчи в `patches/`, применяются к main `4bce0a6`.
2. **Почему профиль плоский.** Тик D1–D3 на 90–95 % — один проход по 1000–4200 мобжам; каждый идёт через одну и ту же «толстую» модель данных (6 строк `mobj_t` из 7.4, затем сектор, FOF, таблица состояний, `switch` по 80 типам) и общий код ≈ 97 КБ (I-кэш 16 КБ). Ни одна функция не горяча, но 96 К промахов D-кэша и 55 К I-кэша на тик (D3) размазаны по всем; PCSX2 их не считает, на железе тик примерно в 1.65–2.15× дороже модели (оценка по [К]).
3. **Пара `ZMovement + CheckPosition`** = 43–46 % тика D2/D3 (1.3–1.55 К тактов; NOCLIP 750–900). **70 % пар доказуемо пустые** (0 нарушений на 1.55 М предсказаний, `tics.csv` = ПК-эталон при пропуске), но точная проверка пустоты стоит 500–650 тактов: прототип даёт на EE только **−1…−5 %** тика (D3 −0.14 М, D2 −0.11 М); −12 % достижимы лишь при проверке ≲ 250 тактов. Корректность требует `tmdrpoffceilz` как передаточной функции `(set, H)` — первая версия схемы ошиблась на этом, теневой режим поймал.
4. **Самое надёжное:** линейный поиск в `R_RemoveMobjInterpolator` — причина всех шести худших тиков D4; O(1)-удаление (S, 12 строк) **измерено на EE: худший тик 7.57 → 2.55 М**, среднее −2.8 %. Lua: один зарегистрированный хук мобжа замедляет каждый объект (+0.44 М на тик D3) — маска по типу вернёт −0.40 М.
5. **Железо (гипотезы, нужен микротест):** горячие поля вперёд −23 % промахов чтения (99 → 76 К на тик D3, ≈ −0.5…−0.8 М с предвыборкой); интерполяция 60 Гц платит +0.53 М на тик D3.
6. **Цели пользователя.** Область «логика» даёт на D3 **−0.3…−0.9 М из 5.28 (−6…−17 %)** в модели и ещё −1…−1.5 М на железе (низкая достоверность). **60 FPS при 35 TPS недостижимы на D3 принципиально:** 60·4.7 + 35·5.28 = 467 М тактов/с против 295 (и ступени vblank PAL 50/25 FPS). 35 FPS на D2/D3 — на границе (нужно −0.6 / −1.5 М из кадра), D4 — только рендерером.
7. **Побочное.** На main `4bce0a6` хост-профиль не собирается (`host_build_fix_main.patch`); RAM: после PS2-505/507/511 остатки структур уровня — ≈ 0.3–0.5 МБ на D3 (кроме `netcmds` 288 КБ — область NET).

## 3. Вопрос 1: пара `P_ZMovement + P_CheckPosition` — из чего стоимость, почему 90 % проходов пусты, и схема «спящих» пар

Вызывается из `P_MobjThinker` (`p_mobj.c:10542`: условие `!MFE_ONGROUND || momz || z != floorz …`) и из `P_SceneryThinker` (`p_mobj.c:10730`, там после пары `floorz/ceilingz/…rover` берутся из `tm*`).

### 3.1 Что стоит (измерено)

* Доля в тике [Э]: D3 **1.94 М из 4.54 М (43 %)**, D2 0.80 из 1.75 (46 %), D4 0.30 из 1.11 (27 %), D1 0.06 из 0.56 (11 %) — по 45 крупнейшим типам (таблицы 2.2–2.5).
* Цена одной пары [Э]: NOCLIP-мобж (`MF_NOCLIP|MF_NOBLOCKMAP|MF_NOGRAVITY`: ANIMALGAESEG/TOP, WATERDRIP, FLICKY_xx_CENTER, OVERLAY) — **746–896 тактов**; обычный твёрдый мобж с 4–8 линиями и 3–5 вещами в ячейках
  (SPIKE, BIGMINE, REDHORIZ, LIGHTBEAM, BOXSPARKLE) — **1.6–1.9 К**; выбросы: BIGGARGOYLE и REDSPRING **8.3 К** (30 линий и 7.5 вещей в ячейках на проход), SPRINGSHELL 4.7 К, 1UP_BOX 8.5 К.
  «≈ 2340 тактов на пару» из отчёта CORE — это D2 со сценическими парами и накладными проб; у меня средняя пара D2 = 1.55 К, D3 = 1.31 К, D1 = 1.27 К.
* Из чего пара NOCLIP-мобжа (x86-инструкции Ir ≈ такты EE: на D3 5.24 М Ir/тик у SW-агента против 5.1–5.3 М тактов [Э]; callgrind, D3, 300 тиков [К]):
  `P_ZMovement` 293 Ir (цикл FOF `P_AdjustMobjFloorZ_FFloors` 63, `P_CheckDeathPitCollide` 19, `P_IsObjectOnGround` 13, остальное — линейная проверка ~40 условий) +
  `P_CheckPosition` 603 Ir вместе с вложенными (сама функция 300, `R_PointInSubsector` 104 — это намять-хеш `ssmemo`, 49 КБ, один случайный доступ, `P_SetTarget(&tmthing)` 11, `P_GetFloorZ/CeilingZ` с наклоном, цикл FOF).
  Для твёрдого мобжа добавляется обход ячеек: `P_BlockLinesIterator` 282 Ir на ячейку, `PIT_CheckLine` ~25 Ir на линию (из 4309 вызовов на тик в D3 проходят bbox-проверку 276 и задевают 147, т. е. **97 % вызовов — вхолостую**),
  `P_BlockThingsIterator` 200 Ir на ячейку и `PIT_DoCheckThing` ~30 Ir на вещь (из 2460 вызовов на тик в D3 проходят по радиусу 324).
* Мягкого float и 64-битных делений на этом пути нет (только наклоны: `P_MobjFloorZSlope` 0.57 М Ir/тик в D3, 64-битное умножение, делений нет): вызовов из `libgcc` на пару — ноль. Стоимость — число инструкций ветвления и обращения к памяти.
* Кэш [К], D2, на вызов: `P_CheckPosition` 7094 D1-промахов/тик на 211 вызовов = **34 промаха на вызов** (x86-раскладка; для EE ×0.7 ≈ 24 → 24 × 40 = **~950 тактов**, т. е. на железе пара NOCLIP/обычная ≈ 2× дороже модели PCSX2).

### 3.2 Что делают 90 % проходов — ничего (измерено, хост [Х])

Счётчики (`RT_CENSUS`, сравнение всего `mobj_t` кроме thinker'а, ГСЧ и `tmdrpoffceilz` до/после пары), на тик:

| | D1 | D2 | D3 | D4 |
|---|---:|---:|---:|---:|
| пар на тик (мобж + декорации) | 49.6 | 519.5 | **1483.8** | 128.3 |
| пара не изменила мобж и ГСЧ | 87.7 % | 83.5 % | **90.1 %** | 85.7 % |
| …и не изменила `tmdrpoffceilz` | 86.9 % | 77.8 % | 87.5 % | 84.3 % |
| из пар — NOCLIP (обхода вещей/линий нет) | 46.8 % | 48.5 % | **59.5 %** | 21.2 % |
| сектор мобжа с 3D-плитами / с наклоном | 12 % / 6 % | 13 % / 6 % | **100 % / 32–60 %** | 0 |
Остальные 10 % — движущиеся (BIGMINE качается по синусу: `z` меняется каждый тик, `p_mobj.c:9575`; BOXSPARKLE, WATERDROP, FLICKY_08 падают) и пары первого прохода.
Побочные эффекты «пустой» пары на мир (проверено чтением `p_map.c:2039–2300` и `p_mobj.c:2274–2700`): **нет** записей в другие объекты (для NOCLIP; для остальных — только если вещь пересекает коробку по x/y и проходят флаги, т. е. не «пустой» случай),
**нет** вызовов ГСЧ, звуков, Lua-хуков (при `lua_mobjhooks_any == false`; с хуком — `LUA_HookMobjLineCollide` в `PIT_CheckLine` и `LUA_Hook2Mobj` в `PIT_DoCheckThing` стоят только после проверки перекрытия). Остаются:
(а) `tm*` — `tmthing, tmx, tmy, tmbbox, tmflags, tmfloorz, tmceilingz, tmfloorrover/ceilingrover, tmfloorslope/ceilingslope, tmfloorthing, tmhitthing, ceilingline, blockingline`;
(б) `validcount += 2`; (в) `P_SetTarget(&tmthing, thing)` — счётчик `references` у мобжа (старого `tmthing` −1, этого +1); (г) счётчик `ps_checkposition_calls`; (д) статическая `tmdrpoffceilz` — **не обнуляется** в `P_CheckPosition`, только
повышается (`PIT_CheckLine` 2027) или присваивается для плиты-«потолка» (2192, 2312); читается единственным местом — `P_TryMove` для перевёрнутых мобжей без `allowdropoff` (`p_map.c:2911`).

### 3.3 Можно ли пропускать «доказуемо»? Да, при условии — полный список входов

Аудит читателей `tm*` (grep по `src/`: 151 упоминание в 11 файлах вне `p_map.c`): **каждое чтение, кроме двух, следует за собственным вызовом `P_CheckPosition/P_TryMove/P_CreateSecNodeList` в той же функции**
(`P_ZMovement` 2490–2492, 2633–2637 — внутри ветки, начинающейся своим `P_CheckPosition`; `P_PlayerZMovement` 2884, 2918 — после `P_XYMovement/P_TryMove` в `P_PlayerMobjThinker` 3843–3849; `P_Move` в `p_enemy.c:279` — после `P_TryMove`;
`lua_mobjlib.c:536–646`, `lua_hudlib.c:421–441`, `p_user.c:10666–10673` — после своего вызова). Исключения: (1) `P_SceneryZMovement` (`p_mobj.c:3086`) читает `tmfloorthing`, который обнуляет преамбула `P_MobjThinker` (строка 10457) — пропуск пары у **другого** мобжа его не меняет;
(2) `P_LineOpening` (`p_maputl.c:457–474`, `tmx/tmy` — позиция для высот наклонов) вызывается из `PIT_CheckLine` и из `P_LineIsBlocking` (`p_map.c:3519`, скольжение — после своего неудачного `P_TryMove`), **а также из Lua** (`lua_baselib.c:1991`, `P_LineIsBlocking/P_LineOpening` с чужими `tmx/tmy`): скрипт, вызвавший их вне движения, видит `tm*` последней по времени пары любого мобжа.
Поэтому утверждение SW-агента «пропуск `P_CheckPosition` недоказуем: `tm*` читаются без собственного вызова» (opt10-SW.md, 3.18) верно только для этого узкого Lua-случая и для статической `tmdrpoffceilz`, а не для движка;
**и его можно снять целиком**: пропуск пары не «ничего не делает», а **воспроизводит записанное после-состояние** — `tmthing=O` (с `P_SetTarget`, т. е. теми же счётчиками `references`), `tmx,tmy,tmbbox,tmflags`, `tmfloorz/tmceilingz/tmdropoffz`, `tmfloorrover/ceilingrover`, `tmfloorslope/ceilingslope`,
`tmfloorthing=tmhitthing=ceilingline=blockingline=NULL`, `validcount += 2` — ≈ 40 инструкций и 7 слов в записи спящей пары. Тогда после пропуска **все глобалы тика побитно такие же, как после настоящей пары** (кроме счётчика `ps_checkposition_calls`, где пишется то же),
и аргумент про «чужие читатели» не нужен вовсе; **остаётся одна статическая `tmdrpoffceilz`, и именно на ней первая версия схемы ошиблась** (теневой режим в игре остановился на тике 142 D1: «предсказана пустота — `tmdrpoffceilz` 33554432 → 201326592»).
Она не обнуляется между вызовами и обновляется двумя способами: `если (h > tmdrpoffceilz) tmdrpoffceilz = h` (`p_map.c`, `PIT_CheckLine` и базовый сектор) и безусловным присваиванием `tmceilingz = tmdrpoffceilz = bottomheight/polybottom` (плита-«потолок»/полиобъект). Значит, её после-значение — **функция до-значения**, зависящая от истории, то есть от *других* мобжей: после пары это `set ? H : max(до, H)`, где `H` — максимум (после последнего присваивания) значений, которые пара ей предъявила.
Правило «пара ничего не изменила (до == после)» неверно: «до» могло случайно быть равным результату при записи, но не при воспроизведении. Правильная запись — пара `(set, H)` из 5 байт, собираемая шестью точками (`RT_DRP_MAX` в двух местах `PIT_CheckLine`/`P_CheckPosition`, `RT_DRP_SET` в двух местах присваивания в `P_CheckPosition`); воспроизведение — `tmdrpoffceilz = set ? H : max(tmdrpoffceilz, H)`. Читает её только `P_TryMove` для перевёрнутых мобжей (`p_map.c:2939`), т. е. поведение зависит от неё редко — но «редко» не равно «никогда», и накопленная история входит в побитность.
`validcount` только растёт и сравнивается на равенство со свежим значением (16 мест `validcount++`; сбросы меток уровня — `p_setup.c:1047,1172,3526`), так что даже без повтора приращений это безопасно.
Задержка освобождения удалённого `tmthing` (`P_RemoveThinkerDelayed` ждёт `references == 0`) при воспроизведении тоже одинакова.

**Полный набор входов пары**, которыми должна определяться «пустота» (из чтения `P_ZMovement`, `P_AdjustMobjFloorZ_FFloors/PolyObjs`, `P_CheckPosition`, `PIT_CheckLine`, `PIT_DoCheckThing`, `P_LineOpening`):

1. **Собственные поля мобжа** (≈ 43 слова): `x, y, z, momx, momy, momz, pmomz, radius, height, floorz, ceilingz, scale, destscale, flags, flags2, eflags, type, health, fuse, standingslope, target, tracer, subsector,
   floorrover, ceilingrover, state, angle (MF_PAPERCOLLISION), watertop, waterbottom, threshold, reactiontime, movecount, movedir, extravalue1/2, cusval, player, hnext, hprev, lastlook, friction, movefactor`. Рендер-поля (`frame`, `sprite`, `tics`, `anim_duration`, `old_*`, `renderflags`, `alpha`, …) пара не читает.
2. **Сектор мобжа и сектора, которых касается коробка** (`touching_sectorlist`): `floorheight, ceilingheight, f_slope/c_slope` (и содержимое наклонов: `o, normal`), `flags` (MSF_TRIGGERLINE_MOBJ), `damagetype` (яма смерти), `gravity`, `heightsec`, `ffloors` — для каждой плиты `fofflags`, высоты
   управляющего сектора (`sectors[rover->secnum]`), `t_slope/b_slope`.
3. **Полиобъекты** подсектора (`subsector->polyList`) и ячеек блокмапа коробки (`ps2_polycells`): положение, угол, флаги.
4. **Линии коробки** (только не-NOCLIP): статические `bbox/dx/dy/flags/frontsector/backsector/polyobj` + сектора по обе стороны (см. п. 2) + их FOF.
5. **Вещи в ячейках коробки** (только не-NOCLIP): положение/радиус/флаги/z соседей. Пара «пуста», только если ни одна вещь не перекрывает коробку по x/y (`PIT_DoCheckThing` отбрасывает остальных до любых побочных эффектов — PS2-176) — тогда вход один:
   «появилась вещь, перекрывающая по x/y» = перепривязка в ячейку (счётчик ячейки) или изменение радиуса (`P_SetScale`, Lua).
6. **Глобальное**: Lua-хуки мобжей (`lua_mobjhooks_any` и тип), `leveltime` (в ветках отдельных типов; такие типы — в чёрный список), ГСЧ (в «пустых» проходах не вызывается).

### 3.4 Схема «спящих пар» (pair memo) — что хранить, как проверять, кто инвалидирует

**Ключ — один непрерывный блок.** Поля п. 1 (41 поле + указатель `state`) собираются в `mobj_t` в один блок 160 Б (`-DRT_REORDER_KEY`, `patches/`): проверка — сравнение блока с записанной копией (на EE `lq/lq/xor/or` по 16 Б: 10 итераций), а не хеш. Хеш из 41 слова в прототипе стоил **1.2 К Ir** (1.45 М Ir на тик D3) — убыток; блок + `memcmp` — 125 Ir на x86 (≈ 80–100 тактов EE с `lq`, ≈ 200 с побайтовым циклом).

**Хранить** (производное состояние, в сейвы/сеть не попадает; сбрасывается при загрузке уровня/сейва/ресинке gamestate):
* на «спящий» мобж (запись заводится лениво, после второго подряд пустого прохода — чтобы не платить за мобжей, которые двигаются): копия ключа 160 Б; пост-состояние `tm*` (19 слов, 76 Б: `tmbbox[4]`, `tmx`, `tmy`, `tmfloorz`, `tmceilingz`, `tmdropoffz`, `tmflags`, `floorrover/ceilingrover`, `floorslope/ceilingslope`, `floorthing/hitthing`, `ceilingline/blockingline`, приращение `validcount`; часть выводится из полей мобжа, но хранить проще и проверяется теневым режимом); `(set, H)` для `tmdrpoffceilz`; сигнатуры `secgen` (макс. поколение секторов п. 2), `cellsig` (свёртка версий ячеек, только не-NOCLIP), `polysig` (хеш пар (индекс, поколение) полиобъектов, привязанных к ячейкам коробки и к `polyList` подсектора; **не максимум**: полиобъект, ушедший из ячеек, должен менять сигнатуру) ≈ **250 Б**; D3 ≈ 1000 спящих = **250 КБ (1.1 % арены)**; 64-битный хеш вместо копии ключа дал бы 90 Б на мобж, но проверка в 4 раза дороже и уже не «доказуема», а вероятностна;
* на сектор `UINT16 secgen[numsectors]` (D3: 5.5 КБ — целиком в D-кэше); на ячейку `UINT16 cellgen[bmapw*bmaph]`; на полиобъект `UINT32 polygen`.
* **Чёрный список** (пара читает чужие объекты или время): `MF_FLOAT` с целью — `P_ZMovement` читает `target->x,y,z,health` (`p_mobj.c:2452`); игроки и мобжи с `leveltime`-зависимой веткой; запись для них не создаётся.

**Проверка вместо пары:** (1) блок ключа = копия (и `state`); (2) `secgen[сектор мобжа и touching_sectorlist]` = записанное; (3) для не-NOCLIP: версии 1–4 ячеек; (4) `polysig`; равно → пропуск: восстановить `tm*` (`P_SetTarget(&tmthing, мобж)` — те же счётчики ссылок), `validcount += Δ`, `tmdrpoffceilz = set ? H : max(tmdrpoffceilz, H)`. Иначе пара выполняется, и если после неё ключ тот же, ГСЧ тот же и (для не-NOCLIP) ни одна вещь не прошла проверку перекрытия по x/y — запись создаётся/обновляется, иначе удаляется.

**Кто инвалидирует** (инвалидация всегда безопасная — лишний сброс лишь замедляет; опасен только пропущенный):

### 3.5 Как гарантировать побитность (и что уже проделано)

1. **Теневой режим** `RT_MEMO_SHADOW` (реализован; хост): пара выполняется всегда; если схема «предсказала пустоту», после пары сравниваются **весь `mobj_t`**, ГСЧ, `tmdrpoffceilz` по передаточной функции `(set, H)` и всё пост-состояние `tm*` с записанным — любое различие останавливает игру. Дополнительный **оракул поколений**: при каждом предсказании сигнатуры всех затронутых секторов считаются заново и сравниваются со снимком, по которому ведутся поколения (ловит пропущенного писателя). Результат: **0 нарушений на 1.55 М предсказаний** (4 демо), 0 событий «устаревшего поколения».
   *Что нашёл теневой режим сразу:* первая версия записи требовала «`tmdrpoffceilz` пара не изменила»; тест остановился на тике 142 D1 — она не обнуляется между вызовами, её значение зависит от *предыдущих мобжей*, и правило заменено на `(set, H)` (3.3). Вторая находка — по аудиту: чёрный список `MF_FLOAT`+цель.
   *Ограничение, которое надо знать:* прототип ведёт поколения сканом всех секторов в начале тика. Он корректен только пока все двигатели секторов/полиобъектов (`T_*`-потоки) стоят в списке потоков **после** всех мобжей (так во всех 4 демо — поэтому 0 событий); в общем случае (мобж создан позже, чем двигатель сектора) сектор может сдвинуться перед мобжем в том же тике. **Продуктовая версия обязана увеличивать поколение в момент записи (хуки в 86 местах таблицы ниже), а оракул — оставаться в отладочной сборке.**
   Обязательно ещё прогнать: 60 бинарных карт × 300 тиков (`core_mapsweep.sh`), 24 UDMF-карты на EE (`core_eemapsweep.sh`), сетевую игру `-netsync` (`netsync_compare.py`), Lua-мод, двигающий сектора/плиты/полиобъекты и меняющий поля мобжей (у хоста нет Lua) — **не выполнено**.
2. **Негативные контроли** (как у SW-агента; **не выполнены**): игнорировать `secgen` (должен покраснеть D3: 72.8 секторов за тик), игнорировать версии ячеек (D2/D4), сократить ключ до `x,y,z`.
3. **Живой режим** `RT_MEMO_LIVE` (реализован; хост): пара пропускается, `tm*` восстанавливаются из записи. **`tics.csv` равен ПК-эталону, FNV всех 1050 кадров каждого из 4 демо равен базе** (пропущено 38.7 К / 377 К / 1.09 М / 48 К пар). Ещё нужно: golden `ps2-head` 0 differ (`golden_full.sh`), сохранение → загрузка → дальше = те же хеши.

Ориентиры оптимизации: ключ на `lq` (−100), без счётчиков, вставка в `P_MobjThinker`, воспроизведение только отличающихся слов, сигнатуру сектора хранить одним `UINT16`, `End` вызывать только когда пара реально выполнялась и ничего не изменила (сейчас считается всегда).
Оценка для железа (кэш): пара D3 = 17.4 К D1-промахов за тик [К]; при 70 % пропусков −12 К × 0.7 × 40 ≈ −0.34 М, но запись спящего (250 Б вне `mobj_t`) и код схемы добавляют промахи (callgrind: D1 ≈ те же 79 К против 80 К, I1 +8.9 К = +0.28 М) — **на железе вклад кэша примерно нулевой**; не закладывать.

### 4.3 Почему профиль «плоский» — единая причина

Тик — это 4200 объектов × (вход через указатель → 6 строк `mobj_t` → сектор → подсектор → FOF → таблица состояний → один из 80 `case`'ов): стоимость размазана по ~25 функциям, потому что **каждый объект проходит через одну и ту же общую модель данных:
«толстый» `mobj_t` с горячими полями в разных строках, обход структур указателями, общий универсальный код на каждый тип**. Ни одна функция не горяча, но 96 К промахов D-кэша и 55 К I-кэша на тик распределены по всем. Поэтому чинить нужно модель:
(а) раскладку (горячее вместе), (б) предвыборку следующего объекта, (в) не трогать структуры, если объект «спит» (раздел 3), (г) компактный горячий код.

Измерено: D4 — 4973 вызова, **10.9 М итераций на 1051 тик (10.3 К на тик; расчётные 59 К тактов, измеренный выигрыш 36 К = 2.8 % тика)**, из них тики 516/525/1018 по 566–992 К итераций (5.4–5.9 такта/итерацию по EE-тактам) — 3–6 М тактов в одном тике; D3 7.0 К итераций на тик (40 К тактов, 0.8 %), D2 4.1 К (23 К, 1.2 %).
Изменение (≈ 12 строк): поле `UINT32 interpidx` в `mobj_t` (+4 Б: 408 → 412; на main шаг пула мобжей 416 Б, т. е. размер блока не меняется), `R_AddMobjInterpolator` пишет `mobj->interpidx = len`; `R_RemoveMobjInterpolator`: `i = mobj->interpidx; if (i < len && interpolated_mobjs[i] == mobj)` — тот же обмен с последним (`interpolated_mobjs[i] = last; last->interpidx = i; len--`), иначе (устаревший индекс после загрузки сейва — `R_InitMobjInterpolators` обнуляет список) прежний линейный поиск.

Выигрыш **измерен на EE: худший тик D4 7.57 → 2.55 М, среднее −2.8 %** (раздел 9.1а); D3/D2 −0.8…−1.2 % (оценка по счётчику). Побитность: структура списка не влияет на мир; проверка — 4 демо (golden, tics.csv) + сейв/загрузка/сетевая игра (`netsync_compare.py`), Lua `mobj_t` не видит поле. Работа **S**, риск минимальный. Патч: `patches/interp_remove_o1.patch`.

**D-г. Интерполяция (HW, 50/60 Гц) — цикл `R_UpdateMobjInterpolators` на тик (`r_fps.c:987`).** Измерено [Э]: включение интерполяции (`fpscap "60"`) добавляет к тику **+0.53 М на D3 (+10 %) и +0.25 М на D2 (+12 %)**: на объект 126 тактов копирования 24 слов в 5 строках. В HW-режиме по умолчанию интерполяция включена,
т. е. тик, измеренный CORE в software (интерполяция выключена, PS2-96), на HW на 10–12 % больше. Идея: двухслотовое кольцо вместо копирования `old2 = old; old = cur` (запись только 12 слов `cur→slot`, роль слота меняется по чётности тика): −50 % работы цикла (≈ −0.25 М на D3) и 1–2 строки на объект
(на железе ≈ −0.15 М). Требует правки ~30 мест чтения `old_*` в `r_fps.c/r_things.c/hw_*`; побитность по картинке в режиме 35 Гц — не затронута (там `old_*` не читаются). Работа M, выигрыш только при интерполяции.

**D-д. I-кэш: горячий код тика.** Горячий код ≈ 60 К инструкций x86 вызывается вперемешку; промахи I-кэша на D3 55 К/тик (≈ 40 % от всех промахов) — сравнимы по стоимости с D-промахами. Варианты: (1) PGO (`-fprofile-use` по профилю 4 демо: размещение блоков «горячее сверху», вынос редких ветвей
`switch` в холодную секцию) — эксперимент на хосте: **не делался**: хост-gcc 13.3 ≠ EE-gcc 15.2 (профиль `.gcda` не переносится между версиями), на EE нет `libgcov` (нужен запуск инструментированного ELF в эмуляторе с выгрузкой счётчиков). Вместо этого измерен «потолок»: функции с ≥ 0.1 % инструкций тика — 75 штук, **≈ 97 КБ кода EE** (по `nm -S` ELF с LTO: `P_MobjThinker` 12.8 КБ, `PIT_DoCheckThing` 16.7 КБ, `P_MobjRegularThink` 12.7 КБ, `P_ZMovement` 5.6 КБ, `P_CheckPosition` 3.6 КБ), при I-кэше 16 КБ; на них 95.7 % инструкций и 53 К из 55 К I1-промахов тика; (2) ручной вынос холодного (`__attribute__((cold))`/`noinline` для редких типов в `P_MobjRegularThink`/`P_MobjSceneryThink`/`P_ZMovement`: 79 `case`'ов `P_MobjSceneryThink` дают 33 D1- и 10.8 К I1-промахов на сценический вызов);

## 5. Вопрос 3: Lua-хуки — что стоит, когда вызываются зря, как пропускать

### 5.1 Измерено на EE [Э] (D3, `-nosound -nomusic`, один скрипт `-file X.lua`, тик на 1040 тиков; 582 вызова хука на тик, MT_ANIMALGAESEG)

| эксперимент | тик, М | разница | вывод |
|---|---:|---:|---|
| без скриптов | 5.16 | — | база |
| `addHook("MobjThinker", function() end, MT_FANG)` (тип, которого в демо нет) | 5.60 | **+0.44 М (+8.5 %)** | **один зарегистрированный хук мобжа замедляет КАЖДЫЙ объект на 50–160 тактов** |
| то же, но на MT_ANIMALGAESEG (пустая функция, 582 вызова/тик) | 6.70 | +1.10 М к предыдущему | **1897 тактов на пустой вызов хука** (`lua_pcall`, userdata, обработчик ошибок) |

Итого вызов хука с чтением 3 полей ≈ 6.6 К тактов — совпадает с «7–12 К» из отчёта LOAD; **главная цена — не `pcall`, а чтение полей через метатаблицу** (`mobj_get`).

### 5.2 Хук зарегистрирован — а вызывается «зря»: порог `lua_mobjhooks_any`

`lua_hook.h:186–191` (PS2-174): пока ни один скрипт не зарегистрировал хук мобжа, `LUA_HookMobj/Hook2Mobj/MobjLineCollide` — встроенные заглушки. **После первой регистрации (любого типа)** флаг глобален: каждый вызов `P_MobjThinker` идёт в `LUA_HookMobjSlow` →
`prepare_mobj_hook` → `init_hook_type` (`lua_settop`, `lua_getref`) → `mobj_hook_available` (две строки таблицы `mobjHookIds[type][hook]`, ~52 КБ), возвращает 0. Кроме того `P_SceneryQuick` (PS2-203, быстрый путь декорации) **выключается целиком** (`PS2_MOBJHOOKS_ANY`).
Разбор приращения по типам (D3, +0.44 М на тик): MT_SPIKE +114 тактов/вызов (1247 вызовов = +142 К), MT_DSZSTALAGMITE **+163** (192 → 355; быстрый путь потерян, 353 вызова = +58 К), MT_KELP **+164** (163 → 327, +40 К), MT_ANIMALGAESEG +53, MT_RING +54;
типы с большим числом пар и столкновений платят ещё и за `LUA_Hook2MobjSlow` в `PIT_DoCheckThing` и `LUA_HookMobjLineCollideSlow` в `PIT_CheckLine`: CRUSHCLAW +608, REDSPRING +661, BOXSPARKLE +362, WATERDROP +360, FLINGRING +2671 за вызов.

**Предложение L-1 (точное, S): вместо глобального флага — битовая маска по (тип, вид хука).** `UINT8 mobjhookmask[...]` по живой таблице типов (на main таблицы типов растут динамически, `PS2_OOR_MOBJTYPE`/`mobjHookIds` — маску вести в том же месте и расти вместе с ними; ≈ 700 Б — в D-кэше целиком), бит k = «есть хук вида k для этого типа», строка `MT_NULL` (общие хуки) проверяется одним словом `genericmask`;
`LUA_HookMobj` становится `if (!((mobjhookmask[mo->type] | genericmask) & (1u << hook))) return 0;` — то же самое, что `mobj_hook_available`, но инлайн, без вызова. `P_SceneryQuick` проверяет `mobjhookmask[type] & thinkbit` вместо глобального флага, т. е. остаётся включённым для типов без хука.
Семантика не меняется (то же условие, что внутри `prepare_mobj_hook`), побитность по построению; проверка — `lua_equiv` (`lt_hooks`, `lt_hooks2`, ветка opt12-load) и таблица выше с нулевой разницей при `MT_FANG`.
Выигрыш: **−0.40 М на тик D3 (−8 %) при любом моде с хуком мобжа** (типично: любой мод, правящий врагов); без модов 0. Мерж: `lua_hooklib.c` (opt12-load менял 2 строки), `lua_hook.h`, `p_mobj.c`.

### 5.3 Сколько стоит вызов и что можно срезать без изменения поведения (оценка по коду, подтверждается разностью выше)

Путь одного вызова (`lua_hooklib.c:649` и далее): `lua_settop(gL,0)`, `lua_getref(errorRef)`, `LUA_PushUserdata` → `lua_getfield(L, LUA_REGISTRYINDEX, "LREG_VALID")` (**строка → хеш → интернирование на каждый вызов**) + `lua_rawget` по указателю,
`call_hooks` → `call_mapped` → `get_hook` → `lua_getref` → `call_single_hook` (копии аргументов `lua_pushvalue`) → `lua_pcall` (setjmp) → результат → `lua_settop(0)`. ≈ 20 вызовов Lua API по ~90 тактов.
* **L-2 (S): `LUA_RawPushUserdata`** (main `lua_script.c:1097`, база 873): `lua_getfield(L, REGISTRY, LREG_VALID)` → `lua_rawgeti(L, REGISTRY, valid_ref)` (индекс сохранить один раз при создании таблицы, `lua_script.c:762`): экономия ≈ 150–250 тактов на каждый push (2–3 на вызов хука). **Половина идеи уже сделана в main: PS2-LOAD-18 добавил фильтр Блума для `LUA_InvalidateUserdata`** (путь освобождения блоков зоны); путь push остаётся.
* **L-3 (M): чтение полей `mo.x`** (`lua_mobjlib.c:195` `mobj_get`, 1556 тактов): `luaL_checkudata` делает `lua_getfield(L, REGISTRY, "mobj_t")` (строка → хеш) и `lua_rawequal`; `Lua_optoption` (`lua_script.c:1898`) — `luaL_checkstring`, `lua_rawgeti(registry, list_ref)`, `lua_pushvalue`, `lua_rawget`. Кэш: указатель
  метатаблицы в статической переменной (равенство `lua_getmetatable` + `lua_rawequal` с закэшированным значением без `getfield`), ключ-строка сравнивается по указателю интернированной `TString` (в Lua 5.1 строки интернированы): таблица `(TString*) → индекс` из ≈ 80 записей в статическом массиве с открытой адресацией.
  Оценка −40…−55 % от 1556 (≈ −700 тактов на чтение поля; хук с 3 полями 6.6 К → 4.5 К). Побитность: те же значения, те же сообщения об ошибках (ветка «поле не найдено» не меняется).
* **L-4 (S): `LUA_Step`** (`lua_script.c:1817`, каждый КАДР, `lua_gc(LUA_GCSTEP, 1)`): без скриптов шаг GC ничего не делает; у больших модов (куча 4.4 МБ по LOAD) шаг растёт с кучей; не измерено отдельно (колонка `snd` TICK = S_UpdateSounds + LUA_Step = 0.027 М/кадр в моём прогоне с одним хуком).
  Идея: шаг GC раз в тик, а не в кадр при 60 Гц — меняет число шагов GC, не поведение скриптов (`collectgarbage("count")` и финализаторы — те же допуски, что в PS2-LOAD-18); не рекомендуется без измерения.

### 5.4 Нужно ли пропускать вызов совсем?

Нет: вызов хука — наблюдаемое поведение (скрипт может менять любой мир). «Зря» вызывается только накладная часть для типов без хука (L-1). Пропуск вызова для типов, у которых хук зарегистрирован, но «ничего не делает», недоказуем.
Побочное: **Lua-хуки лишают смысла спящие пары** для типов с `MobjThinker/Collide`-хуками (хук может менять поля мобжа, которые входят в ключ — это ловится ключом) и любого скрипта, пишущего карту (сеттеры `sector_set/ffloor_set/…` ставят глобальный запрет на пары — раздел 3.4).

### 6.3 Предложения (все побитные по картинке; эффект на железе — оценка/гипотеза)

**R-1. Единый «рендер-снимок» мобжа для спрайтов (SoA, 32–48 Б на объект).** Что: в конце тика (или в `R_UpdateMobjInterpolators`, который и так обходит все мобжи при включённой интерполяции) писать в плотный массив строки `(x, y, z, angle, sprite, frame, flags2/renderflags, scale, spritexscale/yscale, color/skin, subsector->sector, tics-флаг)` — один проход подряд по памяти.
`R_AddSprites/R_ProjectSprite` читают массив, а не 5–6 строк `mobj_t` на объект. Выигрыш [оценка]: в D4 2700 мобжей в мире (1934 HOOP), в видимых секторах 1000–2700; −3 строки на мобж × 0.7 × 40 ≈ **−0.1…−0.2 М** на железе; в PCSX2 ≈ 0; вместе с D-г (кольцо интерполяции) — запись снимка вместо `old_* = cur` (общая работа).
Риск: расхождение снимка и `mobj_t` при изменении полей между тиком и кадром (Lua/сетевая перемотка) — снимок строится из тех же полей в точке, где их читал бы рендер (в `R_InterpolateMobjState` при 35 Гц — вообще перед кадром). Работа M. Подтверждение: golden `ps2-head`, FNV 1050 кадров ×4 демо. Конфликтует с D-а по раскладке — делать один из двух для рендера.

**R-2. Колонки через SPR или полосы (гипотеза, нужен микротест).** Идея: стены рисуются в «вертикальные полосы» шириной 64 колонки (строка кэша = 64 колонки): в SPR (16 КБ) помещается 80×200 байт, т. е. 4 полосы по 80; для полосы список команд колонок накапливается при обходе BSP (≈ 410 К/299 = 1370 команд на кадр D1 × 24 Б = 33 КБ) и исполняется по полосам — запись в SPR без промахов, затем DMA SPR → буфер.
Потенциал: до 42 % D1mw = 19.7 К × 0.7 × 40 ≈ **0.55 М/кадр D1** (если промахи записи блокируют, иначе меньше). Побитность: порядок записи пикселей внутри кадра не влияет на результат для непрозрачных стен (каждый пиксель пишется один раз, front-to-back с clip), но влияет для полупрозрачных/масок, читающих приёмник (`R_DrawMasked` после — выполняется отдельно). Риск высокий: глобалы `dc_*` в 40 местах, изменение порядка = риск для режимов `colfunc`. Работа L. **Не рекомендуется без микротеста записи (`rt_cachebench`: стык «записывающий промах EE стоит 5 или 40 тактов»).**

**R-3. Транспонированный буфер кадра (колонка = последовательные байты) — отвергнуто (расчёт):** колонки перестанут промахиваться, но спаны (45 % пикселей D1: 150 М Ir спанов против 131 М колонок) станут шагать с шагом 200 Б; суммарно промахи записи те же. Прибавка есть только если GS читает транспонированную текстуру без цены (UV-вращение) *и* большинство пикселей — колонки; для D1/D4 нет.

**R-4. Удаление I-кэш-конфликта в стенах.** `R_RenderSegLoopX` 34 КБ → разделить на 3 `noinline`-функции по вариантам (простая стена / маска / плиты + наклон) с общей подготовкой, чтобы за кадр холодные варианты не вытесняли горячий. Измерение: I1-промахов стен D1 5.5 М из 24.7 М (22 %) в `R_StoreWallRange`, 3.3 М в `R_RenderSegLoopX` на 299 кадров = **29.5 К промахов на кадр × 0.8 × 40 ≈ 0.9 М** — потолок; реалистично снять треть: **≈ −0.3 М** (оценка). Побитность: перегруппировка кода. Работа M. Пересекается с PS2-177 (который это и делал, +0.1 FPS при 368 строках, т. е. ≈ 0.25 М — **согласуется с моей оценкой по порядку**), поэтому новизна — только в том, чтобы мерить промахи I-кэша, а не такты в PCSX2, где кэша нет.

**R-5. Остальное — как в тике:** `pref` на `seg_t`/`line_t` следующего сегмента в BSP-обходе (аналог D-б; D1: `r_segs.c`+`r_bsp.c` = 33 % промахов чтения). Оценка −0.15 М, работа S, проверка только на железе.

### 6.4 Достижимо ли ≥ 35 FPS software на D3/D4 побитно, без новой архитектуры?

* **D3:** нужно −2.7…−2.9 М из 11.2. Доступно в моей области: спящие пары −0.14 М (измерено, прототип) … −0.6 М (оценка для настроенной проверки), пропуск проверки воды (P-2) −0.2 М (гипотеза), `SetThingPosition` (P-3) −0.1 М, раскладка + предвыборка −0.5…−0.8 М (только железо, гипотеза), интерполяция n/a в software. Итого **−0.9…−1.7 М → 9.5–10.3 М = 29–31 FPS**: 35 FPS **не достигается** без ещё ≈ −1 М рендера (R-4/R-5/PS2-177 дают ≈ −0.3…−0.5).
* **D4:** нужно −3.4 М из 11.8, тик даёт ≤ 0.1 М, рендер — спрайтовый (R-1 −0.1…−0.2, узлы −0.2 в `opt10-SW`): **не достигается**; нужен принципиальный пересмотр обработки HOOP/спрайтов (это область RFRONT).
* 60 FPS в software недостижимы (кадр D1 8.3 М против 4.9 М; прирост за все пункты ≈ 12 %).

### 7.2 Кто платит за тик в кадре: 60 Гц и 35 TPS

В 12 кадрах 60 Гц проходит 7 тиков (35/60 = 0.583): шаблон `T . T . T T . T . T . T`… (два подряд тиковых кадра дважды за 12). Кадр с тиком стоит `R + T`, без тика — `R` (R = рендер + звук + драйвер; из брифа: HW-кадр = R + T при одном тике на кадр):

| демо (HW) | кадр, М | T | R = кадр − T | кадр без тика | кадр с тиком | бюджет 1 vblank NTSC | 
|---|---:|---:|---:|---:|---:|---:|
| D1 | 6.7 | 0.69 | 6.0 | 6.0 (2 vblank) | 6.7 (2 vblank) | 4.9 |
| D2 | 9.0 | 2.06 | 6.9 | 6.9 (2) | 9.0 (2) | 4.9 |
| D3 | 9.95 | 5.28 | 4.7 | 4.7 (**1**) | 9.95 (**3** — 2 vblank = 9.8) | 4.9 |
| D4 | 9.2 | 1.33 | 7.9 | 7.9 (2) | 9.2 (2) | 4.9 |
**D3 — единственное демо, где тик-кадры и кадры без тика различаются на vblank: 4.7 (1 vblank) против 9.95 (2–3 vblank)** — отсюда неровная подача кадров («дёрганье») при 60 Гц-интерполяции; в остальных демо кадр без тика всё равно занимает 2 vblank, т. е. 60 Гц недостижимы по R, а не по тику.

**Предельная частота кадров при 35 TPS** (бюджет 294.9 М тактов/с на 1 EE): `FPS ≤ (294.9 − 35·T) / R`:

| демо | T | R | FPS_max при 35 TPS | FPS = 294.9/(R+T) (при тике на кадр) | чего не хватает до 35 / 60 |
|---|---:|---:|---:|---:|---|
| D1 | 0.69 | 6.0 | **45** | 44 | 60: R ≤ 4.5 (сейчас 6.0) |
| D2 | 2.06 | 6.9 | 32 | 33 | 35: нужно −0.6 М (T + R ≤ 8.43) |
| D3 | 5.28 | 4.7 | **23** | 30 | 35: нужно −1.5 М; 60: T ≈ 1.5 и R ≈ 3.3 |
| D4 | 1.33 | 7.9 | 31 | 32 | 35: нужно −0.8 М, и целиком из R |
(В «реальном» режиме 35 TPS игра выполняет 35 тиков в секунду всегда — отстающие кадры не замедляют игру, а выполняют `TryRunTics` по нескольку тиков за кадр: `d_clisrv.c:1437`, цикл `while (neededtic > gametic)`, до `TICRATE/7 = 5` тиков за вызов, `ps2_catchup` — до 17; поэтому при перегрузке кадров будет **меньше** 30, а не 30 при замедленной игре. D3: 35 тиков × 5.28 = 185 М/с остаётся 110 М/с на рендер = 23 кадра/с.)

**Следствие: «60 FPS при 35 TPS» на D3 требует суммарно 60·4.7 + 35·5.28 = 467 М тактов/с против 295** — недостижимо при любой организации (потоки, срезы, пропуск кадров), пока рендер+звук > 3.3 М и тик > 1.5 М одновременно. Это принципиальный предел, не связанный с качеством реализации; даже с тиком 0 М D3-кадр 4.7 М даёт 62 FPS на грани. На лёгких демо (D1) 60 FPS требует R ≤ 4.5 М (−25 % рендера + звука + тыла драйвера) — не область тика.
Чувствительность: каждые −1 М тика дают **+7 FPS** на D3 (35/R = 7.4) и +5.8 на D1; каждые −1 М рендера — +8 FPS на D3 при 40 FPS (∂FPS/∂R = FPS/R). Т. е. в режиме >35 FPS миллион такта тика стоит примерно столько же, сколько миллион такта рендера.

**PAL 50 Гц (консоль пользователя) и «ступени» vblank.** Показ кадра выравнивается по vblank, поэтому реальная частота — одна из ступеней: PAL 50 / 25 / 16.7 FPS (бюджет 5.9 М на vblank), NTSC 60 / 30 / 20 (4.9 М). Кадр D1 6.7 М (HW) — это 2 vblank (25 FPS на PAL, 30 на NTSC), хотя среднее время позволяет 44 FPS: чтобы получить следующую ступень, нужно уложить **каждый** кадр в 5.9 М (PAL) или 4.9 М (NTSC), т. е. −0.8 М / −1.8 М на кадр — а не среднее. Кадр с тиком дороже кадра без тика на T: на PAL при 50 кадрах и 35 тиках тик есть в 7 кадрах из 10 (шаблон `T T . T . T T . T .`), поэтому лимит определяет **кадр с тиком**: R + T ≤ 5.9 (D1: 6.0 + 0.7 — не помещается на 0.8 М; D3: 4.7 + 5.3 = 10 — в 2 vblank при 11.8 М с запасом, ступень 25 FPS).
В этой логике удешевление **худшего** тика (D4: 7.57 → 2.55 М, раздел 9.1) стоит больше, чем среднего: тик в 7.6 М в D4 — это целиком потерянный кадр (на PAL 2–3 vblank ≈ 40–60 мс «замирание»); шесть тиков > 3 М за 30-секундный прогон.

### 7.3 Интерполяция (HW, 50/60 Гц) — что она добавляет к тику [Э]

`R_UpdateMobjInterpolators` (`r_fps.c:987`) обходит все мобжи на тике, когда `R_GetFramerateCap() != TICRATE` (по умолчанию в HW): D3 **+0.53 М на тик (+10 %)**, D2 **+0.25 М (+12 %)**, D1/D4 ≈ +0.05 М. Т. е. «тик D3 5.28 М» из CORE относится к software без интерполяции; на HW 60 Гц он ≈ 5.8 М, и предел из 7.2 падает до 21 FPS при 35 TPS. Предложение D-г (раздел 4) снимает половину.
Покадровая часть интерполяции (`R_InterpolateMobjState` для видимых мобжей) мала: 31 К Ir на кадр D1 (0.6 %).

### 7.4 Можно ли выровнять кадры «нарезкой» тика? — нет (кратко)

Нарезка цикла `P_RunThinkers` на части между кадрами (порядок мобжей и результат тика не меняются) физику не нарушает, но **рендер читает живой мир**: секторы (высоты, FOF), полиобъекты, текстуры линий, мобжи — недописанный тик виден как рваная картинка. Нужен двойной буфер состояния, читаемого рендером (снимок секторов 2755 × ~40 Б + мобжей `R-1` = ≈ 0.3 М на тик плюс правка всех чтений в `r_*.c`/`hw_*`), а суммарный бюджет (7.2) всё равно превышен. Отвергнуто как нерешающее: выравнивание подачи не поднимает FPS, а цена — XL.
Дешёвая часть идеи — **убрать из тик-кадра всё, что не входит в физику**, и делать это по кадрам, а не тикам: интерполяционный обход (0.53 М D3), `S_UpdateSounds`, `LUA_Step` (0.027 М/кадр, уже покадрово). Первое — D-г.

### 8.4 Эффект на кэш и «лотерею раскладки»

Уплотнение строк реального пути (горячие поля в начало, раздел 4) важнее общего размера: у `sector_t` поля пары в 4–5 строках, у `mobj_t` в 6 (после перестановки 3.25), `line_t` 2 строки на проверку. Замечание для D-а: шаг 416 = 6.5 строки, т. е. половина мобжей начинается на границе строки, половина — со смещением 32 Б; горячая зона 156 Б перекрывает 3 или 4 строки (в среднем 3.25 — число из раздела 4).

## 11. Открытые вопросы и что измерить дополнительно (по убыванию ценности)

1. **Реальный штраф кэша EE.** Все оценки «на железе» (раздел 4, 6, 3.6) идут из x86-кэш-модели ×0.7 и штрафа 25–40 тактов. Нужно `rt_cachebench` на консоли: (а) цепочка указателей по списку мобжей (латентность промаха чтения, 8 КБ/16 КБ/64 КБ), (б) запись с шагом 320 Б (блокирует ли промах записи конвейер: определяет R-2 и 0.5 М рендера), (в) исполнение холодного кода 32 КБ по кругу (штраф промаха I-кэша), (г) `pref` на 3 строки вперёд. Альтернатива без консоли: `EnableEECache` + интерпретатор в PCSX2 (считает состояния кэша, но не такты) на прогоне D3 с и без патчей D-а/D-б.
2. **Спящие пары на EE.** Все цифры схемы — число инструкций хоста (Ir) и EE-цены типов; нужен прогон EE-сборки с блочным ключом (`RT_MEMO_BLOCK`) на D2/D3 — тик в PCSX2 + `EnableEECache`.
3. **Реальная цена `memcmp` блока 164 Б на EE** (`lq`/MMI против цикла по словам); решает 60–100 или 150–200 тактов на проверку.
4. **Хуки записи секторов (86 мест + FOF + наклоны):** оракул для них — диф-скан в тестовой сборке; нужен прогон 60 бинарных карт × 300 тиков и 24 UDMF-карт (`core_mapsweep.sh`, `core_eemapsweep.sh`) в теневом режиме, плюс Lua-мод, двигающий сектора/плиты (в этой работе не прогонялся: у хоста нет Lua).
5. **Причина пачки D3 тиков 923–933** (6.1–6.4 К вызовов `PIT_DoCheckThing` против 2.5 К): какие вещи собрались в одних ячейках — по счётчикам хоста есть только форма, не типы; нужен `RT_CENSUS` с типами по тику (дело получаса).
6. **Моды с хуками на D3-подобных картах:** L-1 даёт −0.4 М только когда зарегистрирован хотя бы один хук; нужен профиль реального мода (ловушки, враги) — ни одно из четырёх демо без Lua.

## 12. Приложение: как повторить, патчи, команды

Патчи в `docs/research/rtick/patches/` (**каждый проверен `patch -p1 --dry-run` на чистом main `4bce0a6`**):
* `interp_remove_o1.patch` — **готовое** O(1)-удаление интерполятора (D-в); единственный патч «в продукт». Те же правки уже есть в `rtick_instrumentation.patch` под `-DRT_O1` — эти два патча не накладывать вместе.
* `rtick_instrumentation.patch` — все приборы и прототипы (**только для исследования, не в продукт**): `src/rt_census.h`, `rt_eeprof.h`, `rt_memo.h` (новые) и вставки в `p_mobj.c/h`, `p_map.c`, `p_maputl.c`, `p_tick.c`, `r_defs.h`, `r_fps.c`. Флаги: `-DRT_CENSUS` (счётчики хоста, ряды по тикам, пики), `-DRT_EEPROF` (такты EE: тик, пары, типы, ряд по тикам; с `RT_MEMO_*` — стоимость проверки), `-DRT_REORDER` (горячие поля `mobj_t`/`sector_t` вперёд; раскладка `sector_t` порождена от определения main), `-DRT_REORDER_KEY` (+ непрерывный блок ключа пары), `-DRT_MEMO_SHADOW` / `-DRT_MEMO_LIVE` (+ `-DRT_MEMO_BLOCK`) (прототип спящих пар), `-DRT_O1`, `-DRT_QUIT_TICS=N` (выход после N тиков — для callgrind).
* `host_build_fix_main.patch` — **на main `4bce0a6` хост-профиль не собирается** (`tools/ps2/host_variant.sh` и все хост-проверки OPT12 не работают после слияния opt12-load/net): `ps2_loadprof.h` объявляет `ps2lp_hash_t`/`ps2lp_on` только при `PS2`, а `p_setup.c` использует их при `PS2_PROFILE`; не хватает заглушек `NetLat_*` и `ps2_nearest.c` для хоста. Патч — минимальное исправление; рекомендую внести в main независимо от этой работы.
