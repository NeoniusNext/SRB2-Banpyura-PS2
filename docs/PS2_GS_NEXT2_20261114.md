# GS metadata and CLUT construction, iteration 2, 2026-11-14

This pass compares against the cumulative source snapshot in
`build/nov14-next/baseline-src/src`, including the preceding native REGLIST/model
changes. It does not compare against the older Git HEAD. Production changes are
in `ps2_hw_priv.inc`, `ps2_hw_tex.inc`, and only `ramp_clut` in
`ps2_hw_draw.inc`. The native vertex/list/model submission code is unchanged.

## Changes and memory bounds

The two VRAM free-list arrays now store block addresses and lengths as `u16`
instead of `u32`. A GS has 16,384 blocks, so both a block address and the length
of the entire 4 MiB address space fit. End addresses and allocation/alignment
arithmetic remain wide; merged lengths cannot exceed 16,384. A compile-time
guard prevents silently increasing the supported address space past `u16`.
The same 8,193 range slots, placement algorithm, alignment, eviction policy,
texture limits and complete 4 MiB VRAM remain available. The arrays' storage is
65,544 → 32,772 bytes: 32,772 bytes of RAM metadata removed, without reducing
VRAM texture capacity. The containing structure's alignment determines the
final linked BSS saving.

CLUT generation now reserves its complete existing 72-quadword upload packet
before reading palette state, generates the 256 entries directly in that
packet's image payload, then performs the 64 in-place pairs that exchange CSM1
index bits 3 and 4. The other 128 entries are fixed points. This removes the
two static 1 KiB intermediate images from each of ordinary and ramp CLUT
construction: another 4,096 bytes of static RAM. The debug identity ordering
still works. The packet retains its complete register setup, IMAGE tag and
post-transfer TEXFLUSH; the packet size and GS operations do not change.

`pk_alloc` closes any VU chunk and obtains ownership of the complete packet
before construction. Entry generation and the permutation make no allocations
and cannot flush or rotate that buffer. The reviewed VU/ring completion paths
invalidate GS cache state or release texture-data zone tags; they do not mutate
the texture palette, screen palette or light-table data.

This reduces CPU work and EE RAM. It does not reduce texture sampling quality,
change filtering/pixels, reduce framebuffer size, compress textures, or reduce
the amount of CLUT data transferred to the GS. It makes no independent claim of
lower VRAM use or less GS rasterization work.

## Exact production-source comparisons

```sh
source /workspace/.onboarding/environment.sh
python3 -B tools/ps2/gs_next2_hosttest.py \
  --out build/nov14-next/gs-next2-host \
  --base-src build/nov14-next/baseline-src/src --sanitize --negative-controls
```

The dedicated fixture extracts actual frozen/current allocator, packet
reservation, palette, CLUT cache and ramp-cache functions. It verifies that
shared lighting/register/ramp helpers are unchanged, records source hashes,
and compares complete ring bytes, free-list entries, cache tables, hints,
loaded-CLUT invalidation and relevant counters. Ring rotation and VU completion
are mocked; EE/GS readbacks belong to the full hardware fixture/game checks.

Normal and ASan/UBSan runs both passed:

| Coverage | Result |
| --- | ---: |
| Allocator operations | 418,330 |
| Exact free-range comparisons | 203,545,414 |
| CLUT/ramp operation groups | 8,192 |
| Largest free range | All 16,384 blocks preserved |
| Maximum legal one-block fragmentation | 8,192 ranges, followed by complete merge |
| Deliberate swizzle, width, payload-address, TEXFLUSH corruptions | All four detected |

Allocation tests include low/high placement, 1..128-block alignments, NPOT
requests, failed requests, pressure, varied pool bases, reverse merging and
final coalescence. CLUT tests cover all eight palette kinds, keyed variants,
texture/screen palettes, missing and populated light-table rows, palette
generation changes, cache hits/replacements, ordinary/fog ramp variants,
pending VU chunks, and every available-space position around a 72-quadword
ring boundary. Complete ring bytes, including headers/trailers and untouched
canaries, match the frozen version.

## EE CPU measurement

```sh
python3 -B tools/ps2/gs_next2_hosttest.py \
  --out build/nov14-next/gs-next2-ee \
  --base-src build/nov14-next/baseline-src/src --ee-only
source /workspace/.onboarding/emulator-env.sh
python3 -B tools/ps2/run_pcsx2.py \
  --elf build/nov14-next/gs-next2-ee/GS_NEXT2.ELF \
  --log build/nov14-next/gs-next2-ee/run.log \
  --until 'GS NEXT2 DONE' --timeout 120
```

also produced identical full packets on the EE before the benchmark. The table
shows median CP0 cycles for 2,048 builds, nine repetitions, alternating which

Other rows isolate actual `clut_build_into`. Packet allocation/rotation use the
same production reservation function with mocked completion; actual DMA and GS
waits are deliberately outside this CPU measurement.

The preceding standalone GS suite has a known baseline-identical VU0 outcode
failure. This dedicated fixture does not exercise that kernel and does not
establish that the historical full GS suite is entirely green.
